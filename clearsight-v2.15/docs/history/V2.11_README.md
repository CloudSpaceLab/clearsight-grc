# ClearSight V2.11 — Practical workflow interactions

21 November 2026 · Interactive UI reference · Synthetic records

## Open and use

Open **clearsight-v2-demo.html**. The standalone now starts at **Work**, showing the acting person's open items and their next actions. It includes all scripts, styles and synthetic records without a CDN or installation. The **75 individual HTML entry points** use the adjacent `assets/` folder.

For a consistent browser origin, run `python3 -m http.server 8080` from this folder and open `http://localhost:8080/clearsight-v2-demo.html`. On Windows use `py -3`. Browser persistence and downloads depend on browser policy. The demonstration snapshot remains **13 November 2026**; the release date is separate.

## What changed

This increment follows the existing workflows from entry through preparation, review, correction and the next accountable handoff. It concentrates on reducing avoidable searching, backtracking, repeated input and ambiguous actions.

| Workflow | Interaction improvement |
| --- | --- |
| Work | Assigned-to-me default; overdue/upcoming/review/correction lanes; named-owner and type filters; oldest deadlines first; concrete next-action labels. Ordinary actions have a directly addressable detail page. |
| Inbox | Unresolved actionable work can be prioritized ahead of informational recency. Direct source actions and follow-up links open the exact record. |
| Assessments and forms | Respondents, reviewers and observers get the action appropriate to their identity and the current cycle. Remaining-question checks open exact fields, including grid cells and Document pickers. Revision review highlights changed answers. |
| Documents | My reviews, precise assessment review links and next-pending navigation use the existing file/version workspace. |
| Vendor onboarding | Each blocker opens the missing assignment, requested document, file approval or requirement decision. Intake corrections return to the appropriate section. |
| Branch KRIs | Review begins with a compact attention register. Exceptions, unknown observations, reasoned unavailable answers, N/A and unanswered fields remain distinguishable; links open the exact question. |
| Loss register | Field checks save the current capture step before navigation. Corrections show accepted versus proposed facts; pending receipts and reversals are surfaced before the long record. |
| RCSA, controls and risks | Prepared values are compared with current effective values. Source changes and historical conclusions are labeled; editing context leads back to the appropriate assessment. |
| Roles and access | Proposed changes show before/after and effective-access impact before applying. Person/due-state filters, dated renewals and unfinished-draft recovery simplify access review. |
| Escalations | Test the unsaved policy with missing-owner, weekend, acknowledgement and resolution scenarios. Inspect real recipients, fallbacks and business/calendar timing before saving. |
| File approvals | Routing/source blockers are visible before submission. Stale preparation can be refreshed explicitly; decisions state their effect and retain the originating workspace. |
| Privacy | Saved activity, impact-assessment and case drafts have one discoverable list. Validation links to exact steps/fields; case handling has separate Save progress and Submit for review buttons. |
| Reports | Live loss-chart drilldowns retain the selected currency, date basis and cohort. Board-pack checks lead to the relevant draft field. Frozen packs remain unchanged. |
| Search and monitoring | Search covers named records, IDs and owners within the selected location. Local monitoring checks can be run and inspected individually. |

## Shared behavior

Modal saves wait for asynchronous work to finish. A pending operation prevents duplicate submission and keeps its body inert without removing fields from FormData. Failures retain the entered values and show a focused error. A staged comparison does not pretend that its proposed change has been saved.

Unsaved modal entries are protected on Cancel, Escape, internal navigation and Back-style hash navigation. Keep editing returns to the form; Discard follows the intended navigation. Full-page workflows continue to use their existing canonical draft stores. Reload/close uses the browser's ordinary unsaved-change prompt where supported.

Correction links reveal collapsed sections and focus the actual field. Search supports arrow-key selection and Enter. Existing list-state memory is reused; generic lists expose Clear filters. Overflowing record tables become keyboard-focusable. Sticky workflow actions and quieter spacing keep the working area and primary actions together.

## Suggested review

1. Start in Work. Compare Assigned to me with Everyone in this scope; open an overdue review and return to the filtered queue.
2. Open an assigned form as its respondent, then as its reviewer. Use the remaining-items list to reach a missing grid cell or document.
3. Open a branch KRI return and switch between attention, exceptions and all questions. Inspect unavailable values separately from unanswered questions.
4. Prepare a loss, use a field check to navigate away and confirm the current step was saved. Inspect correction and pending recovery decisions.
5. Review an access change before applying it; test an escalation draft without saving it.
6. Open a vendor dossier with mixed blockers, then a privacy case. Follow each exact handoff and use the explicit save/submit choices.
7. Drill into a loss chart, inspect its original-currency source subset, and correct a board-pack publishing check without recapturing its snapshot.

The V2.10 named response history/review, unified Documents and full vendor onboarding remain included, along with the earlier workbook-aligned KRIs/loss register, governance, Inbox and board reporting.

## Verification and handoff

Run `python3 build.py` to rebuild. `docs/TEST_REPORT.md` and `tests/validation-summary.json` identify the current actual-source checks. Run `python3 verify_reference.py` on the untouched release; rebuilding or rerunning tests can change manifest hashes.

The validation executes the application JavaScript with a substituted browser shell. Real-browser layout, keyboard/screen-reader interaction, mobile overflow, file storage/download and print remain unverified because browser execution was blocked in the available environment. Historical screenshots are not evidence of the V2.11 layout.

This is an **interactive design package**, not a production deployment. Browser identities and local state demonstrate the interaction contracts. Production requires authenticated identity, server authorization, concurrency/storage controls, secure Documents and actual delivery/scheduling. No real supplier invitation or colleague notification is sent.

Start with `docs/UX_AUDIT.md`; the domain notes, shared interaction contract, architecture and test results provide the detailed implementation handoff.
