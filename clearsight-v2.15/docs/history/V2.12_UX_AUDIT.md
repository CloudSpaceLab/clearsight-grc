# V2.12 interaction review

## Working objective

Give each person an appropriate starting point, make organizational context unmistakable and complete the external-document-response handoff without duplicating records or inventing assurance conclusions.

## Findings addressed

| Observed gap | Implemented response | Verification focus |
| --- | --- | --- |
| Most actors saw the same shell and actions | My workspace, capability-filtered navigation/search, responsibility lenses, My access, read-only explanations | A lens never grants authority; explicit denies and expired grants remain effective |
| Selecting a reviewer name could substitute for acting identity in older flows | Actual actor and exact scope checks in covered preparation/review commands and modal commits | Self-review, forged names, stale modal identity and denied scope |
| External forms were internally captured with no recipient experience | Minimal exported recipient package; explicit request lifecycle; response inspection/import; reviewed canonical submission | No internal app state exported; tampering, source drift, replay, revocation and expiry |
| File reading and maintenance required too much navigation | Local previews, version selection/comparison, Details, lifecycle/owner filters and retained list context | Original checksum, exact-version lineage, permission changes during reads |
| Document owner and renewal dates lacked a clear management interaction | Reasoned metadata edits and dependency-aware archive/restore | No change to accepted assessment dates, version hashes or review history |
| Report filters and organizational boundary could become ambiguous | Explicit hierarchical context, portable filter routes, saved view roundtrips and captured board metadata | No silent scope expansion; descendant populations and export denominators agree |
| A relevant bank-wide assessment could appear to be branch assurance | Separate contained targets and broader assurance context | Original target boundary retained; no allocated branch compliance percentage |
| Viewing reports could expose authoring paths | Separate read/export/edit/publication decisions | Board/read-only actors cannot prepare or publish through visible controls or command calls |

## Interaction conventions

A workspace describes the actual person's responsibility and the selected organizational population. Named ownership is explicit. An organizational target never replaces respondent identity. Read-only views explain their limits and offer access inspection or an allowed location rather than silently hiding why the action failed.

Documents are files with versions. Their use as supporting evidence is contextual. File approval, whole-response review and requirement conclusions remain distinct and attributable decisions. A new response is not accepted because an import succeeded, and a management date is not renewed because metadata was edited.

Filters narrow a population. Whole-organization, branch, department and unit are explicit hierarchy levels. A department name repeated under different branches is not treated as a cross-bank function without a defined mapping. Reports retain the selected population, dates, currency and original target boundaries in drills, saved views, exports and snapshots.

External recipients see a separate, minimal artifact. The internal coordinator sees issuance status, exact questions/references, received response differences, provenance and the next review step. A returned response creates a new cycle/request lineage instead of overwriting its original submission.

## Design implementation

The new work uses the established type, color, spacing, glass and surface tokens. It adds compact responsibility tabs, context breadcrumbs, explicit secondary details and bounded reading areas. Document expansion stays within the page layout; spreadsheet previews retain scrollable rows/columns on narrow screens instead of turning each cell into a long card list. The same source controls remain responsible for validation and state changes.

## Remaining acceptance work

The included source-level results cover data, commands and routes. Rendered visual quality and browser interaction must be assessed in the target browser: desktop/mobile overflow, keyboard and screen-reader navigation, native dialog/focus behavior, document storage/download, native PDF rendering, Office preview fallback, external save/resume and report printing. No new browser screenshots are represented as validation.

Production implementation needs authenticated actors, server-side authorization and scope enforcement, durable audit records, file scanning/storage, concurrency protection, a hosted external assessment boundary and actual delivery infrastructure. These are integration requirements, not hidden functionality of the local demonstration.
