# ClearSight V2.13 — Premium workflow refinement

21 November 2026 · Interactive UI reference · Synthetic records

## Open the updated application

Open **clearsight-v2-demo.html**. My workspace is the default entry, with the acting person's responsibilities, assignments and next actions. The standalone contains all scripts, styles and sample records; it needs no CDN or installation. Individual module entry points use the adjacent `assets/` folder.

For a consistent browser origin, run `python3 -m http.server 8080` from this folder and open `http://localhost:8080/clearsight-v2-demo.html` (on Windows, `py -3`). Browser persistence and downloads depend on browser policy. The operating scenario remains **13 November 2026**; release date and external request expiry are separate.

## What changed

| Area | Practical refinement |
| --- | --- |
| Shared design | Calmer navy/cobalt palette, solid content surfaces, restrained glass navigation, consistent spacing, typography, borders and controls. Light and dark themes share the same status meanings. |
| Display preferences | Explicit Light/Dark and Comfortable/Compact choices. Applying them preserves the active form, draft, filters and position. Compact spacing is confined to desktop with a fine pointer. |
| Navigation and scope | More readable scope controls; tablet/phone selectors move to a dedicated second header row. Icon navigation retains accessible names. |
| My workspace and Work | Clearer identity, responsibility lenses, owner/due/source columns and next-action hierarchy. |
| Inbox | Dedicated source-action space fixes crowding; narrower layouts place actions beneath the message. Source resolution remains separate from read/acknowledgement. |
| Roles and escalation | More legible capability comparisons, assignment facts, policy levels and simulation timelines. |
| Assessment, KRI and loss capture | Stronger question/section hierarchy, readable guidance, grouped exception details and less intrusive action footers. |
| Vendor onboarding and review | Clearer step progression, capture sections, accountability facts and activation-review summary. |
| Documents | More generous reading surfaces, stronger version controls and comparison hierarchy; worksheets retain scrollable row/column relationships. |
| External recipient forms | A consistent standalone presentation with larger controls, readable instructions and responsive question cards. The original manifest, CSP, scripts and form body stay intact. |
| Reports and board packs | Stronger narrative, decision, owner and chart hierarchy; clearer source confidence and reporting context. Print styles preserve captured facts and temporarily expand analytical disclosures. |

The workbook-aligned KRI and loss models, named respondent history, mandatory independent review, unified Documents, vendor lifecycle, role/scoping guards and recipient isolation from V2.12 remain included.

## Suggested review

1. Start in **My workspace** and inspect the currently assigned responsibilities and work.
2. Use the appearance icon in the header to apply **Dark** or **Compact**. Keep a draft open while changing appearance; it should retain its contents.
3. Open **Inbox**, review an actionable notification and follow its source. Inspect the separate read/archive and source-action controls.
4. Review a Branch KRI return, a loss entry and a named assessment response. Compare question guidance, exception details, accountable identity and reviewer actions.
5. Open **Documents**, inspect an exact version, then compare versions and review Details.
6. As an authorized reporting reader, choose a branch/department, inspect the management report and open a captured board pack. Its source population and captured content remain unchanged by live filters or display preferences.
7. Inspect the isolated external form exported from a named assignment. Its recipient journey remains separate from the internal application.

Existing sample roles remain deliberately limited. **My access** explains an unavailable action; display preferences and responsibility lenses never grant access.

## Implementation and validation

`docs/PREMIUM_DESIGN_V213.md` explains the visual system and interaction decisions. The adjacent workspace, forms and reporting notes describe each adapter. `docs/ARCHITECTURE.md` retains the canonical source and permission contracts. Earlier release documentation is under `docs/history/`.

Run `python3 build.py` to rebuild, or `python3 tests/run_release_checks.py` to rebuild and run the authoritative source suites. Python 3 and a modern Node runtime are required; Node 24 was used for delivery. `python3 verify_reference.py` verifies an untouched package against its manifest. Rebuilding or rerunning checks can change covered files.

The current results and limitations are in `docs/TEST_REPORT.md` and `tests/validation-summary.json`. Actual-source checks use a substituted browser/DOM shell. Real rendered layout, keyboard/screen-reader behaviour, native file operations and print pagination remain browser acceptance tasks because execution was restricted. Historical screenshots are not V2.13 visual evidence.

This is an interactive implementation reference, not a deployed production backend. The external journey remains a minimized local form exchange; authenticated hosting, OTP, invitation delivery and remote recall require server integration. No colleague messages, supplier invitations or live integrations are sent.
