# ClearSight V2.12 — Role-aware workspaces and scoped reporting

21 November 2026 · Interactive UI reference · Synthetic records

## Open and use

Open **clearsight-v2-demo.html**. The standalone begins at **My workspace**, with the acting person's assignments, next actions, available responsibilities and access explanation. Scripts, styles and synthetic records are included; no CDN or installation is required. Individual module entry points use the adjacent `assets/` folder.

For a consistent browser origin, run `python3 -m http.server 8080` from this folder and open `http://localhost:8080/clearsight-v2-demo.html` (on Windows, `py -3`). Browser persistence and downloads depend on browser policy. The operating scenario remains **13 November 2026**; release date and external request expiry are separate concepts.

## What changed in this increment

| Area | Practical improvement |
| --- | --- |
| Role-specific entry | My workspace arranges assigned work for contributors, program owners, independent reviewers, reporting readers and access administrators. Combined responsibilities can be viewed together. A responsibility lens never adds permissions. |
| Navigation and actions | Available modules, search results and write actions follow active grants, explicit restrictions, expiry and exact source scope. My access explains the permission decision. Named program ownership and response assignments retain their existing domain authority. |
| Acting identity | Preparation and review commands check the actual acting person. Selecting somebody else's name no longer substitutes for their identity in the covered control, RCSA, KRI and privacy decisions. |
| External assessments | A named assignment can produce a separate recipient-only form package with instructions, due/expiry dates, save/resume, documents and a response download. The bank validates and imports that response into the canonical assignment; independent review remains mandatory. |
| Document reading | Richer previews for text, CSV, images and PDF; bounded Word text and Excel table previews; exact-version selection and comparison; explicit unavailable-file handling. |
| Document management | Owner, classification, tags, review/validity dates, reasoned metadata changes, scoped filtering, filtered-list return paths and dependency-aware archive/restore. |
| Dashboards and reports | Explicit bank/branch/department/unit context, hierarchy-aware populations, date/currency/period retention, saved reporting views, source drilldowns and captured board context. Broader bank assurance is identified separately from local results. |
| Reporting authority | Report read/export and draft/edit/publication are separate capabilities. A partial authorized population is not silently substituted under a broader heading. |

All previous KRI workbook capture, loss register, response history/review, vendor onboarding, Inbox, role administration, escalation and workflow interaction work remains included.

## Suggested walkthrough

1. Start in My workspace. Change the local acting identity and inspect the available responsibilities, pending work and My access explanation. Changing a lens leaves effective access unchanged.
2. As the seeded independent reviewer or CRO, open the management overview. Choose a branch, then a department/unit. Follow a chart to its source and inspect the context chips. Save and reopen a reporting view.
3. Open Documents. Filter by owner or review date, preview a file, inspect Details and compare retained versions. A file's management dates do not rewrite its assessment review.
4. In a program's named assignments, choose an external respondent and open External access. Review the exact recipient questions and deliberately selected references before exporting the separate form package.
5. In that recipient package, complete the human fields, save/resume and download the response. Back in the internal request, inspect and import it as the named coordinator, complete any remaining bank-owned checks and submit for independent review.
6. Return a response with comments, start its next canonical response cycle and prepare a linked replacement request. The previous response and review remain in history.
7. Inspect a frozen board pack after changing live filters. Its captured population, period, source facts and commentary remain fixed; current access still governs who can view or export it.

The sample role assignments are deliberately limited. Use My access to understand an unavailable action. Administration can model an explicit role assignment; the UI never promotes a person simply because they choose a particular view.

## External access boundary

The recipient deliverable is a minimized standalone package. It contains only the assigned questions, named recipient, instructions and explicitly included reference material. It does **not** contain the internal application or its complete state.

This package demonstrates the external journey without a server. It provides no authenticated hosted portal, email invitation delivery, OTP, remote revocation of already exported bytes or cryptographic identity proof. The named coordinator records provenance; a separate reviewer decides the response. A production portal must enforce the same assignment and lifecycle rules on authenticated server endpoints.

Run `python3 verify_reference.py` against the untouched delivery to verify its manifest. Rebuilding or rerunning tests can change files covered by that manifest.

Validation executes the actual JavaScript with a substituted browser/DOM shell. Real-browser visual layout, keyboard/screen-reader behavior, native PDF display, IndexedDB, recipient file downloads and printing remain acceptance tasks because browser execution was restricted in this environment. Historical screenshots are not evidence of the V2.12 layout.

This is an **interactive design and implementation reference**, not a production deployment. No colleague messages, supplier invitations or live integrations are sent.
