# Architecture — V2.12

## Runtime and distribution

The package is a dependency-free browser application with synthetic fixtures and local state. `build.py` assembles shared JS/CSS into one standalone HTML and generates individual module entry points. The standalone and `index.html` begin at My workspace; `dashboard.html` opens the scoped organization overview.

The state key is `clearsight-v2.12-demo-20261121`, with V2.11 and earlier supported-key fallbacks. Schema version remains 3. The release date is 21 November 2026; the operating scenario as-of date remains 13 November 2026. Role validity follows the scenario date. External recipient expiry is a real timestamp checked at export/import and in the recipient package.

## Adapter order

The established V2.6–V2.11 layers load unchanged in sequence through `privacy-interactions`. V2.12 then loads:

1. **role-experience** — exact capabilities, aggregate coverage, source visibility, responsibility landing/access explanation, navigation/search and selected command guards.
2. **scoped-analytics** — organization route normalization before rendering, complete reporting-population checks, target-boundary annotations, saved views and snapshot context.
3. **document-management** — document visibility and file operations consume the role API; captured report material consumes snapshot permissions; previews and metadata remain in the canonical store.
4. **external-assessments** — minimal recipient manifests, offline recipient rendering, response validation and import consume named assignments, Documents and acting-identity checks.
5. **bootstrap** — normal route/render initialization.

V2.12 makes three narrow changes in existing canonical sources: the upload command invokes pre-storage and precommit permission/context checks, and program publication writes `orgScopeIds` into the new canonical program object. The scope pin closes a path where a newer publish action had bypassed an older scope-only action wrapper. The form validator also determines optional-grid emptiness from human columns only, so preserved technical/calculated cells do not turn a blank optional human section into a mandatory answer.

## Capability contracts

`CLEAR_SIGHT_ROLE_EXPERIENCE.capability(permission, {scopeId, scopeIds, subject, makerId})` evaluates exact accountable scopes. `require` forces the actual acting user. `coverage` describes full/partial/absent access over the selected hierarchy; partial coverage is not a whole-organization grant. `canViewSubject` applies source visibility and the explicit shared-document read rule.

Named owner/respondent/reviewer checks remain domain rules. A named assignment can authorize its exact response interaction, but cannot confer unrelated document export, report publication or access administration. Direct restrictions still take precedence. Modal commit guards re-evaluate acting identity and current scope instead of trusting who initially opened a dialog.

## Reporting context

`CLEAR_SIGHT_SCOPED_ANALYTICS.context()` describes the canonical selection, ancestor path, descendants and current report coverage. `route()` carries organizational and relevant reporting settings. `applyRoute()` reconstructs valid IDs and rejects invalid paths before rendering. Scope-selector changes update the URL without allowing its previous `org` parameter to undo the new selection.

Reporting reads/exports require the complete represented boundary. A smaller authorized slice is never relabelled as the requested wider population. Programs retain the original assessment target boundary: contained targets and broader context are distinguishable. Frozen packs add captured scope/path, required boundaries, settings and source-view route without changing previously published pack bodies.

Read, export, edit and publication permissions are separate. View-only users get a captured preview instead of editable report-builder inputs. Exporting a report into Documents additionally requires document creation permission at its captured location and rechecks the source after asynchronous storage.

## Document operations

Preview obtains exact source bytes, checks the recorded checksum and rechecks actor/scope/permission/source after asynchronous work. Text and tabular output is escaped. Office extraction is bounded and does not execute formulas or render embedded objects. Original source downloads remain separately authorized.

Metadata updates and archive/restore retain document IDs, exact versions and review lineage. Management dates do not alter assessment expiry. Upload and external-import commits verify the current actor, permissions, exact location and source context after byte writes, before canonical metadata mutation.

## External request and response boundary

A request freezes the named assignment/cycle, human-question schema, instructions, recipient declaration and selected references. The exported standalone is built from that manifest and a small recipient runtime, never by copying the internal app bundle or state.

The recipient supplies a bounded response package. Internal inspection validates manifest identity, source digest, allowed field shapes, file integrity and lifecycle. Receipt import captures provenance and populates the current canonical draft. Submission then uses the existing named-response command and independent reviewer. A returned review starts a subsequent canonical cycle and linked request; previous submissions are not rewritten.

Local checks demonstrate protocol behavior; hashes in an editable browser artifact are integrity comparisons, not identity authentication. Production requires a server-issued authenticated boundary, durable source versions and an append-only receipt/audit service.

## Testing

The actual-source harness substitutes the DOM/browser shell while loading the real modules in release order. Domain suites exercise source calculations, commands, actor/scope guards, immutable histories, byte verification and external protocol. Route suites verify registered actions and destinations across authorized and blocked contexts. Source compilation and build/manifest checks are separate from behavioral tests.

Native browser rendering, file persistence/download, PDF display, focus/history, screen readers and print are explicitly not claimed as tested in this environment. The current results and suite inventory are in `tests/validation-summary.json` and `docs/TEST_REPORT.md`.
