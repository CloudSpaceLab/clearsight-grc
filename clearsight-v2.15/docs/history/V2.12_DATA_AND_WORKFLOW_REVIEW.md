# Data and workflow review — V2.12

The current package preserves the original workbook-aligned Branch KRI and loss database models and the V2.10/V2.11 response, vendor, document and interaction contracts. See the retained source mappings and domain notes for those definitions. This review records the additional V2.12 invariants.

## Identity and roles

The acting person is `recActor()`. Grants come from the canonical access-control model, including dated assignments and direct deny precedence. Role lenses and personal workspace preferences have no authority. Exact record permissions evaluate all accountable source scopes; aggregate views explain partial coverage rather than treating it as complete access.

Named program ownership, assigned respondents/coordinators and independent reviewer responsibilities remain explicit domain checks. A display name selected in a form is insufficient to perform another person's action. Metadata classification does not create an undocumented document ACL.

## Organization and reporting populations

`S.scope` remains the canonical branch/department/unit selection. Portable report routes serialize it as `org`; valid IDs reconstruct the exact hierarchy, and invalid IDs fail closed. Changing the scope selector updates the route so stale URL context cannot restore the previous location.

Report authority covers a complete selected population. The UI does not quietly drop inaccessible branches and display the smaller denominator as a whole-organization result. A target with a broader original boundary is shown as context and remains subject to access over that boundary. A bank assessment is not reallocated into a branch compliance rate.

Loss currency, date basis, date range, period, response filters and KRI cycle remain attached to the report context. Saved views restore that context. Frozen snapshots retain captured hierarchy, source-target boundaries and settings. Current access controls viewing/export; it does not recompute the frozen figures.

## External responses

The external request records its canonical assignment, current response cycle, exact human-question manifest, named recipient, internal coordinator, review responsibility, source digest and expiry. Exported recipient packages omit the internal application state and its unrelated records.

Recipient save/resume and response download are local. The internal import validates request/manifest identity, current source, cycle, revocation/expiry, answer shape, allowed human fields, file bytes and replay state. Supplied source and actual importing identity remain distinct. Import creates bank preparation on the named assignment; canonical submission still requires an independent reviewer. Acceptance does not itself conclude mapped requirements.

Returned responses and reissued requests retain their predecessor relationship. Superseded requests cannot overwrite the new canonical cycle. An exported package cannot be remotely recalled; revocation is enforced at the receiving boundary. No outbound email, OTP or authenticated recipient session is simulated as real.

## Documents

`S.governance.documents`, `S.governance.versions` and `DocumentBytes` remain the only document/byte stores. Contextual reviews keep their exact version references. Preview/download verifies original bytes and rechecks the actor, current permissions and source after asynchronous work.

Owner, classification, tags, review date and validity date are management metadata. Their edits record before/after and an accountable reason. They never rewrite the source hash, approval receipt, assessment observation or accepted response. Pending file approval and submitted assessment-document review prevent archiving until resolved.

Recipient-supplied files become canonical Documents with the supplier/request/assignment provenance and actual coordinator uploader recorded separately. Capture is bounded and format checked; it does not approve or malware-scan a file. Failed precommit capture removes uncommitted bytes. Rollback cannot delete a linked, reviewed or revised source.

## Production boundaries

All records are synthetic and persisted locally. The demonstration validates interaction and data contracts; it is not tenant isolation or a cryptographic trust boundary. Server implementation must repeat authorization and source/version checks, protect audit history, validate recipient authentication and enforce storage, scanning and delivery policy.

The current test report distinguishes actual-source model/route validation from browser acceptance work. Previous release screenshots and results remain historical.
