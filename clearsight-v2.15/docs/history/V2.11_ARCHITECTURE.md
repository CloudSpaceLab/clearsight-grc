# ClearSight V2.11 architecture

## Runtime and build

The package is dependency-free HTML, CSS and JavaScript with synthetic state. `build.py` generates 75 entry points and one fully inlined `clearsight-v2-demo.html`, starting at `work`. `assets/app.js` restores schema-3 state using a V2.11 key with V2.10 and earlier fallback. No live data, email, supplier portal or scheduler connection is implied.

Load order: seed → app → forms → experience → journeys → insights → records → document store → documents → usability → Copilot → KRI schema/branch KRI → governance → inbox → board reports → loss schema/register → workflow completion → flow polish → loss reporting → assessment tracking → vendor onboarding → unified Documents → assessment reporting → interaction core → assurance interactions → governance interactions → operations interactions → privacy interactions → bootstrap. Shared functions are adapted in this order. `build.py` and `tests/runtime_harness.js` contain the authoritative lists.

## V2.11 interaction adapters

The five interaction modules use existing source commands and stores. `interaction-core` owns shared field/error/focus/search behavior and transient modal state; the assurance, governance, operations and privacy adapters improve their domain views and exact handoffs. They do not start another render loop or create parallel approved-record repositories. The final bootstrap remains singular.

`app.js` delegates generic modal submit and action dispatch to the shared handlers when present. Promise completion is awaited; pending callbacks cannot lose their dialog, be double-submitted or accept edits underneath a captured save. Domain command validators still make all consequential decisions.

`work-item` and `role-change-review` are the only new top-level routes. Drafts, filters and report source selection use existing route/state mechanisms. Access previews run the canonical evaluator against a temporary clone and restore it; apply rechecks the compared model. Report drills intersect the captured cohort and leave frozen renderers unchanged. See `SHARED_UX_V211.md` and the domain UX notes for the interaction contracts.

## Assessments: identity, episodes and current conclusions

`S.assessmentTracking` references existing programs, targets and pinned forms. An assignment binds one named respondent and a current eligible reviewer. Organizational target, respondent, actual submitting actor and reviewing actor are separate facts. External respondents retain their identity and source/capture reference separately from the internal coordinator. Per-assignment storage keys and form bindings prevent two people responding for the same target from sharing a mutable response.

Submitted episodes retain answers, source versions, actual submitter and timestamps. Return/correction/reassignment events append history. Accepted episodes can support explicit requirement decisions; submission alone cannot. A replacement cycle preserves accepted facts until reviewed. Current readiness additionally rejects pending or stale response/source bases. Legacy unknown person, review and time fields are retained as unknown.

`CLEAR_SIGHT_ASSESSMENTS` exposes assignment, submit, review, revision, reassignment, status and requirement-decision commands plus route and reviewer-eligibility helpers. Command boundaries recheck the actual actor, current reviewer assignment, permission/scope, source definition and version. The program owner can review if eligible; an independent reviewer needs the applicable scoped approval authority. Explicit denies and self-review exclusions apply.

## Documents: one repository, contextual decisions

Canonical `S.governance.documents`, `S.governance.versions` and the existing document store own files, hashes and versions. Internal legacy `S.evidence` records remain contextual review references to those versions; they are not a second repository. Old public Evidence routes normalize to Documents and an exact review context. The canonical document workspace exposes the context alongside file approval and version history.

`docEvidenceAdd` records actual contextual submitter and reviewer separately from the original file uploader. `d210Review` is asynchronous: acceptance verifies the actual bytes and then rechecks the actor, permission, scope, record and source version before any decision mutation. `jEvidenceDecision` now returns that promise; callers must await it. Returns remain possible for an unavailable source. Accepted replacements supersede earlier contexts without erasing their decision receipts.

## Vendor dossiers and activation

`S.vendorOnboarding` owns preparation drafts, submitted intake revisions and the diligence dossier. It references existing supplier/engagement records, service programs, assessment assignments, document versions, governance approval requests and shared decision receipts. A draft has no live engagement side effect. Owner confirmation and independent risk approval precede creation of due-diligence work.

Document checklist entries link a canonical version and an exact approval request, named coordinator/reviewer, due date and validity basis. Existing completed approvals can be reused explicitly with applicability context; a new attachment alone is insufficient. Activation/resumption require an approved intake, current accepted named responses, current required document approvals and applicable Satisfied requirement decisions. The lifecycle request captures this basis and checks it again on decision.

## Work, Inbox and reports

Work items are projections of authoritative assignments, dossiers and reviews. Notifications retain exact source, revision and stage. Read, acknowledgement, archive and source resolution remain separate. Returned work stays open until its linked replacement submission. No real external recipient delivery occurs.

New assurance report snapshots include `assessmentResponses`; V2.9 `operationalLoss` remains. Reports capture names, source versions, figures, narrative and chart context. Old packs are not backfilled with live annexes. Response counts do not modify compliance denominators or automatically create requirement conclusions. Copilot uses the actual selected report or captured context.

## Financial contracts retained

Losses remain accepted/closed event records with versioned corrections. Monetary values use original-currency integer minor units. Received, independently verified and reversed cash remain distinct. Occurrence, recognition and reporting period remain separate. Closed events stay included; there is no implicit FX conversion or invented legacy recognition date.

## Production boundary

Local state and synthetic identities are a design reference, not an authenticated data-access boundary. Production must implement authenticated row-level retrieval, server-side permissions, immutable decisions, atomic/concurrent writes, secure document storage, real delivery and scheduled escalation. Actual-source tests substitute browser APIs; browser layout, persistence, downloads and print remain unverified. Earlier architecture is retained in `history/`.
