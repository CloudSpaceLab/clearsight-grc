# ClearSight V2.4 — Privacy and task-based workspaces

**13 November 2026 · Interactive design reference · Synthetic records only**

Open `clearsight-v2-demo.html` for the self-contained version. It starts in Privacy & data. No installation, CDN, font download or live connection is required. The 37 module HTML entry points share the same navigation; keep `assets/` beside them. A stable origin can be provided with `python3 -m http.server 8080` from this directory (Windows: `py -3 -m http.server 8080`).

This revises the V2.3 demo, not the production application. No repository, live tenant, vendor account or regulatory filing was changed.

## What changed

Complex registration and assessment setup now use full-page, resumable wizards. Ongoing records have dedicated workspaces. Reviews display the record/evidence alongside the decision. Small, single-purpose actions remain centered dialogs. The inline form editor is retained rather than turned into another wizard.

| Task | Interaction |
|---|---|
| Register or revise a processing activity | Six-step wizard, section entry points, local draft save and submission |
| Maintain a processing record | Overview, data flow, purposes/retention, screening/DPIA, review and history |
| Prepare a DPIA | Five-step wizard; risks to individuals, consultation, measures, owners and evidence |
| Review a ROPA record or DPIA | Full-page context and independent decision; request changes and resubmit |
| Handle rights requests / privacy incidents | Short intake, then a case workspace for investigation, review and history |
| Onboard a vendor engagement | Supplier identity → service/data → accountability → review |
| Register a risk / loss | Three-step setup, then a full record workspace |
| Start an RCSA cycle | Population → responsibility → review and launch |
| Review evidence / a requirement | Full-page evidence context and decision, preserving the existing guards |
| Recover a loss, change one field, confirm deletion | Focused centered dialog |

## Suggested walkthroughs

### Processing record and maintenance

Start at **Privacy → Register activity**. The steps are Activity; People & purpose; Data flow; Retention & controls; Screening; Review. Set an accountable unit; the top navigation scope never silently changes the draft target. Each purpose has its own basis/reference. Retention rows have a dataset, trigger, period, disposal approach and policy reference. Recipients can reference existing vendor service engagements.

Use **Save & exit**, then resume from the Processing register. Unknown screening answers are allowed to remain uncertain; they do not grant an automatic exemption. Submission creates a frozen proposed record, not a compliance conclusion.

For a populated example, open **Digital account opening → Review**. The independent reviewer can request changes or publish the register revision. Publication does not approve the legality of processing or complete a DPIA.

Open **Transaction monitoring** to see a published record. Its section-specific revision actions open the relevant wizard section. Changing a draft does not overwrite the published version. Submit, request changes, resubmit and publish to see the previous version retained under History.

### DPIA

Open **Privacy → Impact assessments → Digital account opening · DPIA → Continue assessment**. Capture context, necessity/alternatives/consultation, risks and safeguards, implementation evidence and external-obligation references. The example deliberately includes work that is not verified.

Submitting creates outstanding mitigation tasks in the existing Work queue. Internal approval is blocked when the assessment refers to an outdated activity revision, measures remain unverified, external-obligation assessment is unresolved, or the illustrative residual-risk threshold is exceeded. The owner cannot approve their own submission. Request changes or escalate rather than manufacturing a green outcome.

The 5×5 scoring and threshold are illustrative internal policies, **not legal thresholds**. The jurisdiction labels do not constitute complete rules engines for Nigeria, South Africa or the UK.

### Rights and incidents

Use **Privacy → Requests & incidents**. Intake records the received date, incident awareness when relevant, accountable scope, owner and an explicit checkpoint with its basis. A case can start before its processing activity is identified. This avoids delaying incident intake while the data inventory is being investigated.

The case workspace permits partial investigation saves. Submission for independent review requires a substantive outcome and evidence. Disclosure-response submission requires identity/authority confirmation. Closing an incident requires a recorded notification determination and supporting reference. Requesting changes does not require inventing delivery evidence. These actions record a workflow only: no response, notification or filing is transmitted.

### Operational workspaces

Risk & Losses retains scope-specific gross/recovered/net loss totals. Open a risk for its context, controls/assurance, linked lifetime loss events and work. **Register risk** and **Record loss** now have guided setup. Loss recovery remains a compact exact-amount action, with integer-kobo arithmetic and over-recovery rejection.

Vendors separates legal supplier identity from each service engagement. Registration does not activate the engagement. RCSA creation freezes a selected risk/control population; existing first-line submission and independent challenge/approval remain available.

## Preserved behaviour

The top Branch → Department → Unit scope remains visible. Clearing a level means all its descendants and clears dependent child filters. Current scope follows lists, risk/loss totals and exports. Shared templates remain reusable bank-wide; a draft or submitted assessment target does not change when navigation scope changes.

Framework adoption, original assessments, direct form editing, matrices/mixed grids, automated-source fixtures, vendor assurance, controls, evidence, reporting payloads and RCSA review continue to work. Reports remain available contextually rather than occupying a new primary navigation item.

## Files and implementation handoff

- `assets/journeys.js` / `journeys.css`: new privacy and task-based interaction layer.
- `assets/experience.js` / `experience.css`: retained direct form editing, shared scope and loss summaries.
- `assets/forms.js` / `forms.css`: retained general and integration-assessment forms.
- `assets/app.js`: shared application/state/workflows; `assets/seed.js` and `seed.json`: original synthetic domain seed.
- Privacy enrichment is initialized in `journeys.js` over the existing processing-record identities.
- `docs/UX_REVIEW.md`: interaction decisions and remaining production work.
- `docs/PRIVACY_MODEL.md`: record lifecycle, references and jurisdiction limitations.
- `docs/TEST_REPORT.md`: actual checks and explicitly blocked native-browser tests.

Run `python3 build.py` after changing source assets. It regenerates 37 entry HTMLs and the standalone file. Production implementation should use ClearSight's existing services, components and authorization model, not transplant this browser-local script as a backend.

## Boundaries

All entities, people, evidence references and framework seeds are synthetic. No licensed or complete regulatory catalog is included. Evidence is metadata only, not real files. Integrations use local deterministic fixtures; no API calls, credentials, SQL execution, scheduled jobs or notifications run.

Role switching demonstrates independent review but is not authentication. Client-side checks and snapshots are not server-enforced authorization, immutable storage or tenant isolation. The same browser can edit its own state. Local storage uses the separate key `clearsight-v2.4-demo-20261113`; V2.3 stored work is not migrated or overwritten. Storage denial falls back to session-only mode. The snapshot date is fixed at 13 November 2026.

This is not a complete privacy operations platform: automated discovery, data deletion/retention execution, consent/preference collection, regulatory submission integrations, subject-facing portals, legal deadline computation, complete transfer impact assessments and complex multi-jurisdiction applicability remain outside the demo. One accountable org unit is used per record; multi-unit impact allocation requires production expansion. New general-form observation snapshots remain separate from the older requirement-evaluation acceptance pipeline, as in V2.3.
