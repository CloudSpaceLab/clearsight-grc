# ClearSight V2.8 — Shared records and workflow ownership

Framework versions own canonical requirements. Programs own tailoring, scope and requirement conclusions. Forms collect observations; evidence acceptance remains separate from requirement satisfaction. Risks, loss ledgers, controls, RCSA and privacy keep their existing domain owners.

## Branch returns

`S.branchKri` owns cycles, definitions, draft answers, submissions and accepted snapshots. The new source-linked definition targets branches; historical unit cycles keep their original granularity. Continuous indicators remain a separate store.

`kri-schema.js` contains 51 question definitions and their source columns. `branch-kri.js` adds typed answers, conditional drafts, consistency validation, exception context and compatible read models. NGN values are integer kobo, hours are decimal, and counts are whole numbers. Boolean aggregates count adverse locations; context metrics never imply appetite compliance. Approved N/A is separate from unknown and excluded from applicable-answer denominators.

Submission freezes a revision. Review validates provenance and retains the common document/decision receipt. Accepted corrections update open remediation tasks while preserving prior accountability. Closed episodes remain unchanged; recurrence creates a linked episode. Removing a breach flags the action for independent closure verification rather than closing it automatically.

## Access and escalation

`S.accessControl` owns role policies, assignments, direct rules, recertification and escalation policies. Existing `S.governance` continues to own documents, approval requests and the demo actor selector.

Permission simulation applies default denial, explicit-deny precedence, scope ceilings, dates and separation of duties. It is an inspectable policy reference, not authenticated production enforcement. Escalation simulation resolves recipients from current demo assignments, applies scope/priority and WAT business/calendar time, and exposes unresolved routing. No scheduler or external delivery service is connected.

## Inbox and work

`S.notificationsV28` holds events and per-recipient receipts. Read, acknowledgement, snooze and archive are personal receipt state. Source records determine resolution. Stable event IDs prevent duplicates, and typed source IDs must match routes. KRI events retain source revision and remediation identity.

`CS_V28_EVENTS.emit` connects KRI and report actions to the inbox. Work items remain ordinary `S.tasks` records with owner, scope, due date and source; no second task engine is added.

## Reporting

`reportData()` remains the common read model. The reporting extension captures figures plus the source names, periods, definitions, locations, owners, actions, quality and history needed to interpret them. Published packs read captured data only, so later mutations cannot alter their figures, narrative or charts.

KRI comparisons require equivalent complete canonical definitions and the same reporting population. No trend is inferred between the legacy unit template and the new branch template. Losses retain occurrence-window and integer-kobo semantics; current risk posture uses a separate snapshot date.

## Composition

`build.py` generates 60 entry points and one self-contained HTML. Registration order is core, forms, experience, journeys, insights, records, document storage/documents, usability, copilot, KRI schema/flow, governance, inbox and board reporting. `bootstrap.js` owns the single first render after initialization.

Production integration must retain the real application's authenticated actor/tenant boundaries, authorization, revision checks, storage, append-only audit, scheduler and source integrations. The design package does not replace those services.
