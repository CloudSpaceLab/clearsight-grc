# ClearSight V2.6 — Data and workflow review

13 November 2026. This is an implementation handoff for the local prototype, not a claim that the production repository or bank tenant has been changed.

## 1. One authority per kind of record

The consolidation is a shared contract and adapter layer over the existing domain modules. It is not another set of requirements, controls, evidence decisions or compliance scores.

| Record | Authoritative content | Consumers |
|---|---|---|
| Framework / requirement version | Source obligation and default question relationships | Adoption, programs, assessments, review |
| Program / target | Adopted source versions, applicability, tailoring, assignment | Internal and vendor assessments; reporting |
| Assessment submission | Fixed form version, exact target, answers, source observations, document versions and respondent | Work, requirement review, source inspection |
| Requirement evaluation | Explicit scoped conclusion with source provenance and reviewer | Program, form-response context, assurance reports |
| Risk / control / RCSA | Existing risk identity, implementation and approved assessment | Registers, linked workspaces, risk reporting |
| Loss / recovery entry | Integer kobo and existing attribution | Risk summary, ledger, drivers, exported amounts |
| Document | Stable identity, accountable scope, owner, classification and folder | Central library and all attachment views |
| Document version | Immutable-by-workflow original bytes reference, filename, size, media type, checksum and contributor | Preview, downloads, evidence, signing |
| Document link | Exact version ID + validated record type/ID + purpose | Record attachments and document usage |
| Evidence | Version reference + program/target/question context + observed/expiry/acceptance | Evidence review and baseline requirement evaluation |
| Approval request | Captured subject/version, ordered actors, due date and state | Approval inbox and shared Work |
| Decision receipt | Actor, intent/decision, exact source snapshot/version, time and rationale | History, audit inspection and decision export |
| Published report | Frozen scope, periods, source population, figures and commentary | Management pack, document output and approval |

The typed registry resolves canonical IDs, labels, source routes and scope. Existing name-based owner fields receive compatibility accessors backed by stable user IDs. Old evidence filename/size fields are read through their version reference rather than maintained independently. Historical snapshots retain the names and values recorded at the time.

For production, use explicit typed relationships or constrained association tables with server validation and tenant-safe foreign keys. The browser registry is not a substitute for referential integrity in a database.

## 2. Shared input, output and display rules

The header controls one organizational query scope. A draft, submitted return, document version and published report retain their explicit target. Navigation never silently reassigns those records. Folder membership is organizational convenience, not an access policy.

Money remains integer minor units; gross/recovered/net figures reuse the ledger. Monthly KRI ratios remain ratios of summed underlying numerators/denominators, with approved coverage and missing values shown separately. Reporting retains separate clocks for current posture, loss occurrence windows and monthly returns.

Document lists and exports use the same query function, including scope, folder, type, state and search. Linked records show the state of their **linked version**, not the document’s latest version. Exported IDs and checksums identify exactly what a displayed row refers to. Dates/timestamps on the shared document and decision surfaces use WAT; business dates remain date-only values.

Statuses are consistent within their domain rather than forced into a misleading universal score. A file can be Approved while its evidence is stale; an assessment can be Submitted while its requirement is Not assessed; a report can be Published but still await management approval. These distinctions are intentional.

## 3. Document model and upload handling

`Document → DocumentVersion → Blob storage` is separate from `Record → DocumentLink → DocumentVersion`.

Bytes live in IndexedDB when available, with an explicitly labelled in-tab fallback. Metadata lives in the versioned workspace key. Reloading metadata without session bytes produces an unavailable-file message and blocks byte-dependent approval. No fabricated preview or successful upload message replaces missing bytes. Metadata exports explicitly exclude originals.

The upload page accepts multiple files, reports each validation error, detects identical contents within a batch/location, captures owner/scope/classification/folder and requires a change note for replacements. It checks allowed extensions, file signatures where applicable, UTF-8 text, expected Office archive members, sizes and batch bounds. Office checks do not decompress/inspect all content and are not a security guarantee.

Text is escaped before presentation. CSV supports quoted values and a bounded preview. Images use byte-backed object URLs. PDF viewing requires an explicit action; Office files remain downloads. Original downloads and approval recheck the stored checksum. Object URLs are revoked after use.

Archived files preserve their versions, links and completed decisions. Pending approval blocks archive until the request is withdrawn. Restore does not manufacture a new approval. Moving a folder does not alter version identity or organizational scope.

## 4. Review and sign-off

The simple routing choices are **Review only** and **Review, then sign off**. They use a short setup page, then a full review workspace with the exact source visible alongside the decision. They do not use a generic side drawer.

A request captures the subject, current version, file checksum or report snapshot, requester, contributor and ordered steps. The requester/contributor cannot review their own submission; reviewer and signer must be different. Only the next assigned person can act. Every substantive decision requires a note. Final sign-off additionally requires the matching typed name and explicit intent.

`Pending → Completed / Changes requested / Rejected / Cancelled / Superseded` describes the request. A completed request remains associated with its original version. A replacement invalidates pending requests and starts a new unapproved head; it does not rewrite prior links or decisions. Resubmission creates another request episode. Changed snapshots, repeated completion and missing bytes are rejected by command validation as well as reflected in the UI.

Receipts include the source version/snapshot checksum, actor ID, recorded name, decision, timestamp, reason and sign-off intent where applicable. SHA-256 is an integrity checksum, **not a digital signature or proof of identity**. Demo identity selection is not authentication. No signature image, fake certificate or claim of legal enforceability is generated.

The shared Work queue projects requests and source-domain review tasks. The inbox is another view of those same records, not a second workflow engine. Evidence acceptance, ROPA publication, DPIA decisions, privacy-case closure, RCSA approval and branch-KRI acceptance keep their own rules and emit common receipts.

## 5. Closing the custom-form evaluation gap

V2.5 custom forms could submit snapshots but did not feed the baseline requirement-review path. V2.6 makes those submissions alternative sources for the **same canonical requirement evaluation**.

A source must be an assigned, submitted form with an exact program/target binding and published field mappings to an applicable requirement. Designer previews and cross-target submissions are excluded. The reviewer sees the source definition, relevant fields, observed values and linked document versions; the existing field renderers are reused read-only.

The submission definition, answers, observations, linked versions and respondent are checksummed together. Importing an earlier local submitted record can establish a new local integrity baseline; it does not retroactively authenticate that submission. This is marked in the record.

A new conclusion is not an automatic translation of completion or a technical Pass. An independent reviewer records the result. Satisfied requires an explicit complete-objective confirmation, complete/current relevant fields, acceptable observations and available supporting originals. Heuristics and unknown/failed/stale technical sources cannot silently support Satisfied. Partial or negative conclusions remain possible with rationale. Independent acceptance cannot be supplied by the document contributor.

The result writes `program.evaluations[target][requirement]`, which is already consumed by programs and reports. Prior conclusions are retained in evaluation history when this path replaces them. The source snapshot remains unchanged. Form-response pages read the same program conclusions. A previously accepted conclusion is not erased merely because a new draft or an attempted review is incomplete.

Fresh workspaces use form seed edition 2: privileged-access fields are mapped to access objectives, unrelated branch/risk-table fields are not presented as access evidence, service availability is not labelled as a recovery test, and vendor service performance is not mapped to encryption. Supporting-only mappings remain explicitly insufficient for a complete-objective conclusion. Imported published versions are preserved, not silently rewritten.

This bridge is explicit and reviewer-driven. It is not automated legal interpretation, and mappings alone do not prove sufficient objective coverage. Arbitrary form values are still not a substitute for the governed monthly branch-KRI metric catalogue.

## 6. UX and copy cleanup

The library, attachment chooser, version page and source preview now use the same records and state vocabulary. Upload and review errors are actionable; reference-only files and missing local bytes are visibly different. Long names wrap inside their cells, and mobile document rows become readable cards instead of overlapping table text.

Headers use task-oriented descriptions. Repeated “intelligence” labels, generic traceability slogans and verbose footer warnings were shortened or moved into source views and About this demo. Necessary limitations remain adjacent to simulated integrations, signing and unscanned content. No decorative AI assistant or invented recommendation score was introduced.

Wizards remain for multi-step setup; direct editing remains for forms; full workspaces remain for investigation and review; short atomic operations use centered dialogs. The one-row logo and branch/department/unit scope is preserved.

## 7. Production boundary and implementation order

The local reference is not a replacement for the production backend. Implement the shared contracts using ClearSight’s existing records and services, then replace browser adapters with authenticated APIs.

Before real bank use: tenant-safe authorization; private/object storage; malware scanning/quarantine and safe preview conversion; least-privilege downloads; durable append-only audit records; concurrency/version tokens; transactional upload/link commits and orphan cleanup; retryable delivery; retention/legal-hold policy; and verified signers/step-up authentication or an appropriate external signing provider. Do not put credentials, original bank documents or signer secrets in prototype JSON.

Use an idempotent command layer and one accepted-evaluation projection. Preserve server-enforced separation of duties. Definitions and submitted snapshots must be versioned, with migration reviews rather than silent reinterpretation. Queue file processing and bound resource use; the browser’s whole-state render and integrity scan are not a production performance strategy.

Remaining demo limits include no live connectors, no secure external portal, no remote multiuser workflow, no background notifications, no Office conversion or content/OCR search, no enterprise legal holds, no bulk bank spreadsheets, no configurable parallel/quorum review, and no cryptographic signature service. General monthly-KRI authoring/import and automated technical-feed binding still require implementation.

## 8. Security references

The production upload checklist follows OWASP’s layered approach; extension/signature checks alone are not enough. Approval intent is tied to the exact transaction/version, rather than a generic “approve” action.

- OWASP File Upload Cheat Sheet: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html
- OWASP Transaction Authorization Cheat Sheet: https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html

These references inform the handoff; they are not evidence of security certification for this demo.
