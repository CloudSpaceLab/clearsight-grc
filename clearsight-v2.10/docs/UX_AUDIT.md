# V2.10 UI/UX audit and completion

This increment followed the user's three connected gaps through preparation, assignment, submission, review, correction, reporting and source navigation. It also retained the earlier KRI, governance, loss and operational workflow improvements.

| Observed gap | Implemented outcome |
| --- | --- |
| Assessment response identifies only the unit/vendor | Named respondent and reviewer in Program Assessments and Forms Assignments, with the target shown separately. |
| A submitter/reviewer can be chosen as free-form attribution | Submission and decision use the actual acting identity; external respondent and internal capturing person are distinct. |
| Two people share a target response | Per-person assignment stores and response bindings isolate drafts and submitted cycles. |
| New forms without requirement mappings bypass review | Every assigned submission receives a whole-response review task. |
| Accepted response is overwritten by correction | Submitted episodes and decisions remain; corrections form a new cycle. |
| Older response provenance is missing | Explicit unknown submitter/time/review labels; no backfilled identity or invented decision. |
| Documents and Evidence appear to be separate libraries | One Documents navigation and canonical file workspace; contextual Assessment reviews share the file/version history. |
| File uploader is mistaken for assessment submitter | Both named fields are visible with separate provenance. |
| Document acceptance can ignore the actual file | Byte verification and current source/actor/scope checks precede acceptance. |
| Add engagement does not start onboarding | Resumable four-step intake, owner confirmation and independent risk review. |
| Diligence is only a plan label | Approval creates a real service program, named response assignments and document requests. |
| File attachment or questionnaire submission appears sufficient to activate | Blocker checklist checks current accepted responses, independently approved documents and requirement conclusions before reviewed activation. |
| Directors cannot see person-level response bottlenecks | Response-accountability report, charts, source tables, current/history CSVs and frozen assurance annex. |

## Discoverability and continuity

The ordinary Program and Forms views expose respondent, reviewer and history actions. Vendors shows Onboard a vendor and an Onboarding view with drafts, decisions and dossiers. Documents exposes its review queue near the top of the library and assessment review tabs on the exact document. Legacy routes redirect to the same workspaces.

Each source workflow feeds Work/Inbox under the accountable internal person. Returned review work retains comments and correction links. Read/acknowledged alerts do not complete their source. The canonical source view remains the place to submit, decide or revise.

## Verification boundary

The actual-source route suite checks 73 entry routes and 10 report perspectives for complete render output, registered actions and destination names. Domain suites test identities, versions, decisions and cross-module handoffs. Source/CSS inspection and those render checks are not a browser accessibility or visual-layout certification. Keyboard/screen-reader use, mobile overflow, actual file storage/download and print need verification in an allowed browser environment.

Earlier loss and operational audits are retained in `history/V2.9_UX_AUDIT.md`, `WORKFLOW_AUDIT_V29.md` and `FLOW_FIXES_V29.md`. New contracts are documented in the V2.10 assessment, document, vendor and crossflow notes.
