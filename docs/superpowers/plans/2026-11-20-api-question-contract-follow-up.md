# API-backed form questions: remaining implementation

Status: partial. The monitoring source builder can inspect an unauthenticated HTTPS endpoint against the selected standard result type and create a keyless draft binding. It can also validate sample JSON without network access or writes. This does not configure a form question or make a source active.

## Target behavior

A form question selects a yes/no or numeric result and an approved endpoint. The response is a JSON object with a required `result` of the selected type and optional bounded text `message`. A numeric result has an explicitly configured comparison; neither a number nor a boolean is automatically a compliance conclusion. Test mode validates a supplied example without network access or writes. A live check uses the existing governed source access and records source, time, freshness and observed result separately from the assessment outcome.

## Implementation sequence

1. **Partially implemented:** REST source definitions support explicit singleton responses: one root object, fixed endpoint, no pagination or lookup, and a keyless PAGE binding. Inspection and execution reject arrays and continuation. Existing keyed-record behavior, limits and schema-drift checks remain in force. Unit and catalog tests cover changing boolean results, zero, type drift, array and cursor rejection, and tenant-scoped draft preview. The monitoring builder now selects the standard boolean or numeric contract for real endpoint inspection and creates its draft binding; the form builder does not yet configure this binding.
2. Define and implement the source activation lifecycle with verified actor, scope, current authority, maker-checker approval, version/effective-date checks, audit and transactional outbox. Do not treat draft bindings as active. Test denial, revoked authority, conflicting reviewers and rollback. Until this exists, do not represent draft monitoring checks as active.
3. Add secure credential-reference selection to the connection flow; never place credentials in URLs, browser state, logs or sample payloads. Enforce existing endpoint and network restrictions and test authenticated and denied access. Explicitly state supported authentication modes.
4. Extend the existing form field binding and adoption configuration, rather than creating a new form or integration store. Persist the approved binding revision, selected result type, comparison and freshness policy. Validate compatibility and authority on save and again on execution. Make the response message subject to explicit size, sensitivity, retention and access rules before storing or displaying it.
5. Execute through the existing source-access service. Record a timestamped observation and source revision; missing, stale, malformed, unavailable or unauthorized responses remain unknown and never produce a pass. Keep test samples out of authoritative observations. The typed singleton contract now validates the boolean/number result and bounded optional message on inspection and read, with a stable schema when the message is absent. Generic singleton schema behavior remains unchanged. Exercise authorized real HTTPS execution, failures, schema changes and tenant/entity isolation end to end.
6. Add responsive adoption and form-builder states, keyboard and screen-reader tests, source and runtime render evidence at required widths, and copy-quality checks. Keep the production cutover blocked until the documented review and authorization requirements pass.

## Existing constraints

The live endpoint path creates persistent drafts before inspection, supports only unauthenticated endpoints and produces a draft binding. Standard results use no record key; the separate other-record-fields mode retains its stable-key requirement. Monitoring requires an active current binding even to create a draft check; the builder therefore stops after saving the source binding and explicitly reports that the proposed condition was not saved. There is no supported activation path in this flow. The optional message is not retained by the existing monitoring result. These gaps must be resolved before advertising the standard contract as a working live form integration. Configured freshness now passes from the source definition into any subsequently created monitoring check rather than defaulting to 60 minutes. Source creation no longer performs a separate post-commit catalog registration; later source-configuration operations remain non-atomic and require their own recovery design.
