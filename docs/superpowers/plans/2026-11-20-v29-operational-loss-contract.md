# Operational-loss reviewed workflow: proposed implementation contract

**Status:** Draft for implementation review. These proposed routes and tables do not exist yet. This is one domain of the [full rewrite plan](2026-11-20-v29-full-rewrite-domain-plan.md), not a completed plan for all domains. No production migration is authorized by this document alone.

## Existing behavior confirmed in source

`internal/httpapi/operational_loss_routes.go` registers `GET /api/v1/losses`, `GET /api/v1/losses/{id}`, `POST /api/v1/losses`, `POST /api/v1/losses/{id}`, `POST /api/v1/losses/{id}/intervention` and `POST /api/v1/losses/{id}/recoveries`. Creation sets `ACTIVE`, and `AddRecovery` writes a `RECOVERY` or `REVERSAL` that immediately contributes to totals. `internal/oploss/postgres.go` locks the loss for updates and writes the current row, immutable loss revision/event and outbox in its transaction. Migration `000110` makes recovery rows immutable. `web/src/lossApi.ts` still calls the immediate-write paths.

This differs materially from 2.9: draft → submitted → independent accept/return; submitted corrections preserve the accepted version; pending receipts and reversals do not affect accepted totals; closure is distinct from financial reporting. Do not label the current immediate writer as reviewed.

## Proposed external contract

These contracts are additive and must be added to `route_registry.go`, the runtime OpenAPI projection, HTTP handler tests and `web/src/lossApi.ts` together. JSON examples omit transport identity: tenant, legal entity and actor always come from verified request context. An `organization_scope_id` in a draft is an attribution request and must be checked against the actor's current permitted scope. `expected_version` is an integer, and is required on every modification. All UUIDs are exact identifiers, not search strings.

| Method and path | Request | Success | Authority and state |
| --- | --- | --- | --- |
| `POST /api/v1/loss-drafts` | `{ "organization_scope_id": "uuid", "title": "string" }` | `201` `Draft` | Authenticated material command bound to verified legal entity and authorized scope; creates an incomplete initial draft. |
| `GET /api/v1/loss-drafts/{draft_id}` | none | `200` `Draft` | Source-authorized exact read; deny cross-entity, inaccessible owner and revoked source. |
| `PUT /api/v1/loss-drafts/{draft_id}` | `{ "expected_version": 1, "fields": LossFields }` | `200` `Draft` | Current draft owner or delegated performer; validates partial structure, length, scope and currency without requiring submit completeness. Whole `fields` object is a replacement, not an unguarded merge. |
| `POST /api/v1/loss-drafts/{draft_id}/submit` | `{ "expected_version": 2 }` | `200` `Submission` | Current performer; validate required fields, references and current route; freeze exact snapshot. No accepted financial change. |
| `POST /api/v1/loss-submissions/{submission_id}/decision` | `{ "expected_version": 1, "decision": "ACCEPT"\|"RETURN", "reason": "string" }` | `200` `DecisionResult` | Current independently routed reviewer; reject same-person conflict, stale source, inaccessible evidence and changed authority. `RETURN` requires substantive reason. |
| `POST /api/v1/losses/{id}/correction-drafts` | `{ "expected_loss_version": 3 }` | `201` `Draft` or `200` existing draft | Current owner; one open correction per loss; freeze base version and resume an existing authorized correction without a duplicate. |
| `POST /api/v1/losses/{id}/recovery-proposals` | `{ "expected_loss_version": 3, "kind": "RECEIPT"\|"REVERSAL", "amount_minor": "10000", "effective_date": "2026-11-20", "reference": "string", "reverses_receipt_id": null, "evidence": [] }` | `201` `RecoveryProposal` | Performer; active accepted loss, matching original currency and source scope. `REVERSAL` requires an exact receipt ID. Money is a decimal string of integer minor units to avoid JavaScript precision loss. |
| `POST /api/v1/loss-recovery-proposals/{proposal_id}/decision` | `{ "expected_version": 1, "decision": "ACCEPT"\|"RETURN", "reason": "string" }` | `200` `RecoveryDecisionResult` | Independent current reviewer; accept inserts one immutable effective ledger row and updates accepted loss version in the same transaction. Return leaves financial totals unchanged. |
| `POST /api/v1/losses/{id}/closure-proposals` | `{ "expected_loss_version": 4, "residual_treatment": "string", "open_actions_treatment": "string" }` | `201` proposal | Performer; blocks while a financial proposal is pending. The absence of open actions is established from their owner, not a browser flag. |
| `POST /api/v1/loss-closure-proposals/{proposal_id}/decision` | `{ "expected_version": 1, "decision": "ACCEPT"\|"RETURN", "reason": "string" }` | `200` result | Independent current reviewer; acceptance records a closure episode without deleting the financial loss or completing actions. |
| `POST /api/v1/losses/{id}/reopen` | `{ "expected_loss_version": 5, "reason": "string" }` | `200` current loss | Current authorizer; retain closure episode and require a substantive reason. |

`LossFields` is a bounded JSON object with `code`, `title`, `event_type`, `cause`, `description`, `gross_amount_minor` (decimal-string integer), `currency` (ISO 4217 uppercase), `occurred_at`, `discovered_at`, `recognized_on` (nullable calendar date), `reporting_period` (nullable `YYYY-MM`), `organization_scope_id`, `account_classification`, `loss_group`, `transaction_reference`, `transaction_particulars`, `regional_bank`, `directorate`, `risk_id` (nullable), and `evidence` (array of exact authorized artifact/version references). Null is allowed in a draft. Submit validation requires values specified by the approved bank policy, validates `discovered_at >= occurred_at`, positive gross for an actual loss, explicit near-miss classification if supported, recognized/reporting period consistency or explanation, and exact source membership. It must not infer dates or risk links. Before coding, make the bank-policy-required set and near-miss semantics explicit in the OpenAPI schema and tests; they are not established by this repository inspection.

`Draft` returns `{id, version, state, base_loss_id, base_loss_version, fields, updated_at}`. `Submission` returns `{id, version, state, draft_id, base_loss_id, base_loss_version, submitted_at}`. `DecisionResult` returns `{submission_id, decision, loss_id, loss_version, decision_id}` on acceptance, with `loss_id` nullable on a returned initial submission. `RecoveryProposal` returns `{id, version, loss_id, base_loss_version, state, kind, amount_minor, currency, effective_date, reverses_receipt_id}`. `RecoveryDecisionResult` returns `{proposal_id, decision, loss_id, loss_version, recovery_id}` with `recovery_id` null on return. IDs of reviewer/actor and route decisions are server-generated and must not be accepted from body fields.

The existing error envelope uses `httpx.WriteError`. Reuse `401 sign_in_required`, `403 approval_required`/scope errors, `404 loss_not_found`, `409 loss_version_conflict`, `422 loss_invalid` or `loss_recovery_invalid`, and `503 authority_unavailable`. Introduce stable codes for stale proposal/source and missing route only after checking current error conventions; never return raw SQL, protected source titles or a success-shaped response on denial. A committed material command must not return failure solely because a later projection refresh fails.

### Compatibility boundary

Do not change semantics of old `POST /api/v1/losses` or `/recoveries` while older clients can still invoke them and claim that the new independent-review invariant holds. Before enabling reviewed workflows, either upgrade and block all old material writers with a documented capability/version gate, or deploy a server-side policy that rejects the old commands for entities using the reviewed workflow. Reads may retain legacy response shape during migration. Test old and new API clients together; legacy writers must fail closed rather than bypass review. Do not silently reinterpret existing recovery entries as approved proposals.

## Data model and transaction requirements

The existing `operational_losses` row requires complete non-null fields, so an incomplete first draft cannot be represented by setting its existing status to `DRAFT` without a schema redesign. Add a separate bounded draft owner; upon first acceptance, atomically create the existing loss identity/current row and link it to the proposal. For corrections, retain the existing accepted row until acceptance.

Proposed additive tables, migration number to be allocated after checking the current migration ledger:

| Table | Required columns and constraints |
| --- | --- |
| `operational_loss_drafts` | `id uuid PK`, `tenant_id`, `legal_entity_id`, nullable `base_loss_id` and `base_loss_version`, `owner_principal_id`, bounded `fields jsonb` object, `state` (`DRAFT`,`SUBMITTED`,`CANCELLED`), `version bigint > 0`, timestamps. Composite tenant/entity foreign keys; actor FK. Partial unique index on `(tenant_id, legal_entity_id, base_loss_id)` where `base_loss_id IS NOT NULL AND state='DRAFT'`. Check that `base_loss_id` and `base_loss_version` are both null or both set. |
| `operational_loss_submissions` | `id uuid PK`, tenant/entity, draft ID and draft version, nullable base loss/version, bounded immutable `snapshot jsonb`, `snapshot_sha256`, submitter principal, submitted time, state (`SUBMITTED`,`ACCEPTED`,`RETURNED`), `version`. Scoped FKs; unique `(tenant_id, legal_entity_id, draft_id, draft_version)`. Preserve immutable snapshot even when decision state changes. |
| `operational_loss_review_decisions` | ID, tenant/entity, submission ID/version, decision, reviewer principal, route/policy version, reason, decided time. Append-only; unique decision per submitted version; reviewer must differ from submitter subject to current segregation policy. |
| `operational_loss_recovery_proposals` | ID, tenant/entity/loss, base loss version, kind, amount as positive `bigint`, currency, effective date, optional original receipt, exact evidence refs, maker, state/version/times. FK to exact loss and, for reversal, exact recovery within same tenant/entity/loss. Only accepted decisions create ledger effects. |
| `operational_loss_recovery_decisions` | Append-only decision with proposal/version, reviewer, route version, reason/time and optional resulting recovery ID. Unique decision per proposal version. |
| `operational_loss_closure_proposals` and `operational_loss_closure_decisions` | Same scoped proposal/decision pattern with base loss version, residual/open-action treatment and prior closure episode references. Append-only accepted closure/reopening history. |

Keep existing `operational_loss_recoveries` as the financial ledger; add a nullable self-reference for the exact original receipt on **new** reversal entries through a forward migration, with same-loss/scope FK and a constraint that applies to newly reviewed entries. Do not fabricate links for historical reversal rows. Record legacy provenance explicitly and keep the old ledger immutable. Add only indexes justified by exact access paths: scope plus maker/state/time for draft lists, scope plus subject/state/time for review work, and exact receipt links for reversal lookup. Run `EXPLAIN (ANALYZE, BUFFERS)` against representative cardinality.

Each acceptance transaction must: (1) re-read verified scope and lock the relevant loss, submission/proposal and exact source rows; (2) check expected versions, current source visibility and current authority route in the transaction; (3) enforce segregation and financial capacity including pending reservations; (4) append the immutable decision and promote one accepted loss revision or insert one ledger entry; (5) append domain event, outbox event and required maintenance job in the same transaction; (6) commit once. No external service call or derived metric calculation may turn a committed command into a reported failure. Define lock ordering as loss → proposal → referenced receipt → source to avoid deadlocks, and test concurrent acceptance.

Decision and draft events need distinct idempotency keys. Repeating an accepted decision with the same command key returns the original result; a different request for a decided version returns conflict. The existing `operational_loss_events` uniqueness is one event per loss version, so draft/review events that do not advance that version cannot be inserted under the same key: give proposals their own append-only event identity or explicitly advance a distinct proposal version, while retaining the existing ledger's revision semantics. Do not overload the loss event sequence.

## Reporting semantics and migration gate

For reviewed-only totals include accepted/closed loss revisions and accepted receipt/reversal entries only, one original currency at a time. A pending correction does not replace the accepted record. Distinguish occurrence, recognition, explicit reporting month and cash effective date. Expose exclusion counts for missing basis and pending/unreviewed items. No implied FX, compliance conclusion or cash receipt from narrative.

The existing dataset has no proven independent-review receipt in this inspection. A bank owner must decide whether historical `ACTIVE` records and recoveries remain in a separately labelled legacy cohort, undergo remediation or have externally evidenced approval. Until that policy is recorded, do not include them in a reviewed-only cohort or label them independently approved. The migration must not drop existing totals: preserve the legacy view with its old inclusion rule while presenting the new reviewed view separately. Record migration schema version, exact scope, before/after counts and gross/recovery/net per currency. Preserve voided and previous versions. Test backup/restore and a compatibility-reader rollback; after new decisions exist, rollback must not delete or rewrite accepted history.

## Remaining decisions

The bank must define legacy inclusion, required submitted fields and review/closure policy. The repository must be inspected further to determine the exact reusable decision/authority transaction interface, source-evidence schema and worker maintenance contract. Consequently the table descriptions above are a concrete design, **not executable SQL or a fully code-ready slice**; final DDL, source-specific access predicates, route descriptors and exact DTO schemas must be resolved and tested before implementation.
