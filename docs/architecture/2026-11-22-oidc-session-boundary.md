# OIDC session boundary and material responses

OIDC staff sessions use SCS and the existing PostgreSQL `web_sessions` table. The row key is the SHA-256/base64url hash of the cookie token; `Actor.SessionID` is a separately generated value in the encoded session and cannot be used to look up that row. External evidence-capture sessions are separate purpose-bound credentials, not staff sessions. Signed-gateway mode does not use `web_sessions`.

The PostgreSQL SCS adapter classifies the request's original cookie hash before SCS loads the request. An idle refresh of that token updates an existing unexpired row only; it cannot insert a deleted or expired token. A new or rotated token uses insert-only semantics. Logout and rotation delete the original unexpired row atomically; if another request has already removed it, the operation fails instead of claiming success or issuing a replacement. The original hash is held only in server request context and is neither an identity proof nor a customer-visible identifier. No additional session table or migration is required. SCS gob session values register `time.Time`, which is used for the OIDC session issue time.

An old in-flight HTTP response may still overwrite a newer browser cookie with the old, unusable token; this can require the user to sign in again. Refreshing the old request cannot recreate its deleted database row. Tests cover both logout/rotation orders, stale idle commits, expiry/cleanup, new-token collision and cookie parsing, but do not prove every browser/network ordering.

SCS attempts idle refresh before writing a handler response. A database error during an ordinary unchanged-session refresh must not turn a committed action into an apparent failure. The PostgreSQL adapter treats that refresh as best effort only for the original token when the decoded outgoing session values and absolute deadline equal the exact loaded session, the requested expiry does not exceed that deadline, no logout or rotation was attempted, and a logger is available. It logs a fixed warning without session data and leaves the previously stored idle expiry unchanged. Missing or undecodable baselines, changed data or deadlines, new or rotated tokens, logout, and absent logging retain explicit errors. A stale response can still replace a newer browser cookie with an unusable old one, and a failed refresh can cause earlier sign-in expiry.

The original cookie hash is not currently revalidated by assessment write or replay statements. Before enabling decisions, define and verify a transaction-visible binding between the authenticated OIDC principal, exact session and stored token, including revocation/rotation committed before the decision statement, expiry, cleanup, alias/scope changes and concurrency. The separate signed-gateway mode has no durable local session row and must specify assertion validity, gateway revocation and the ingress timestamp/skew boundary explicitly; it must not be silently treated as an OIDC session. The assessment gate remains closed until those contracts, other supported origins and independent end-to-end evidence are complete.
