# Matter decision transaction boundary

Status: design and one prerequisite implemented; Matter decision controls in the new work detail remain unavailable.

## Current command

`matter.decision.record` loads the Matter and determines the current decision, target responsibility and materiality in `lifecycleCommandPolicy`. The HTTP guard resolves that authority before `RecordDecisionLifecycle` appends the decision. `PostgresRepository.ApplyMatterEvent` later opens a transaction, locks the Matter, checks tenant/entity and expected version, and writes the decision projection, event and outbox. It does not resolve authority under that transaction. A route or delegation can change after the guard and before the decision write.

The HTTP authority lookup now uses the same `continuity.CurrentDecisionForType` function as lifecycle validation. Previously their different Unicode case comparisons could select the Matter for authorization while lifecycle validation selected an existing Decision. A failing-first regression covers this exact mismatch. Sharing the selector removes that difference; it does not close the transaction race.

`continuity.DecisionAuthorityRequirement` now derives the current Matter or Decision target, lifecycle responsibility and priority-adjusted materiality in one place. Both command preparation and decision lifecycle validation use it. It is only a requirement, not an authorization result: the future transaction must derive it again from the version-checked locked Matter and resolve the current route. Tests cover case-folded exact decision selection, a first proposal and invalid transitions; they do not establish transaction or concurrency safety.

## Smallest safe boundary to implement

1. Preserve the existing lifecycle policy: derive the responsibility and minimum materiality from the requested target, use the greater of that value and the locked Matter's priority, and resolve the current Decision for that type (or the Matter for a first decision). Continue rejecting invalid transitions, forged actors, tenant/entity mismatches and self-review or conflicts where required. The exact Matter version protects against changes to the source decision while entering the transaction.
2. After acquiring the exact Matter lock and checking the expected version, take one database decision instant. Re-evaluate the verified session and the complete applicable route, actor status, entity scope, delegation, authority grants and segregation against that instant and a single database snapshot. Record the exact route/policy version and actor with the decision. Perform no network or object-storage request while the transaction is open.
3. Append the decision projection, event, outbox and existing maintenance work in that transaction. If any write or authority check fails, roll back all of them. An ambiguous commit is an unknown outcome; clients must reload the exact Matter and not blindly retry.

Do not simply put the existing multi-query `Resolve` in a READ COMMITTED transaction and call it atomic. Its reads can see different committed route states. `ResolveMany` already evaluates routes in one SQL statement and supports `authority.WithPostgresTransaction`. A PostgreSQL prerequisite test confirms that it sees an assignment revocation committed after an earlier subject lock and prior authority read, using a decision target at materialities 4 and 5; the test uses a representative row lock, not a Matter command. This is not a Matter command test or proof of full parity: check all route selectors, delegation, grants and segregation at each required materiality, and bind verified session and source version to the same command before use. The current `authority.PostgresReadRouteSQL` is fixed at materiality 3 and is not a substitute for that proof. Do not add a second decision store or a tenant-wide writer lock by default.

At the proposed statement-snapshot decision instant, a revocation committed before the statement must deny the action; a concurrently committed revocation is ordered after that decision. If a bank requires revocation to defeat an already-started decision instead, that workflow requires an explicitly chosen, narrower serialization protocol and tests. No current implementation establishes either guarantee for Matter decisions.

The general batch resolver fills an omitted `At` with application time before executing SQL. Therefore its single snapshot alone is insufficient: a scheduled route, delegation, principal, grant or session expiry can occur between that timestamp and the statement. The PostgreSQL resolver now has an unwired transaction-only `ResolveCurrent` method that reuses the batch SQL with `statement_timestamp()` for route predicates and returns that instant with the selected rule and policy version. It rejects a missing transaction; PostgreSQL tests cover a route expired since a caller-supplied time and parity for selected review scenarios. A command must still check its verified session against this instant and at insertion, derive the exact locked subject and fail closed for a missing or ambiguous route or an actor absent from the effective candidates. The current Matter event payload does not include the selected rule or policy version, so the audit record must also be extended and reconstruction tested before this path is complete. No current Matter or response-review write uses this method yet.

PostgreSQL parity checks now cover named DECISION routes, entity- and decision-type-scoped delegation, wrong-object delegation, materiality 4 and 5 delegation and grants, conflicting top routes, and selected rule/policy provenance. They do not prove all role, position, lifecycle, concurrency or session behavior. Both the governance scope decoder and the database trigger currently reject `DECISION` as a delegation object type. An entity- and decision-type-scoped delegation can still resolve, but an exact DECISION-scoped delegation cannot be created. Do not silently widen that contract: each lifecycle transition appends a new Decision ID, so an exact delegation would cease matching the next lifecycle target. Define and test that consequence in simulation and impact preview, independent approval and rollback before changing the scope contract.

## Required PostgreSQL proof

Use two independent connections and deterministic lock barriers. Verify: a revoked or superseded route committed before the decision instant denies with no decision, event, outbox or maintenance record; a current authorized route permits exactly one versioned decision; a Matter version change conflicts; an expired session, invalid entity, missing or ambiguous route, revoked or out-of-scope delegation, segregation conflict and forged actor all fail closed; higher-priority route changes and scheduled expiry are handled at the declared instant; and any event/outbox failure rolls the entire transaction back. Test a concurrent decision against revocation under the declared ordering, idempotent recovery after an unknown commit, and equality between the relational predicate and the existing resolver for named, role, position, delegation and grant routes at each supported materiality. Execute the complete workflow against a migrated isolated database before enabling the decision control.
