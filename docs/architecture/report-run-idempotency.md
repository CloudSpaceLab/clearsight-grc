# Report run request receipts

`POST /api/v1/reports/runs` accepts an optional UUID `idempotency_key`. For a keyed request, the server binds the key to the verified tenant, legal entity and principal and a SHA-256 fingerprint of the definition ID, pinned version and normalized parameters. Reusing the key with different content returns a conflict. A different principal cannot read another person's receipt. Requests without a key retain the existing behavior.

PostgreSQL migration `000145` creates the receipt table. A transaction-scoped per-key lock serializes creation; the run, outbox event and receipt commit together. Receipt replay returns the recorded run even if the definition subsequently changes. The memory repository follows the same key and fingerprint rules. The down migration refuses to discard existing receipts; rollback must preserve their data and deploy compatible readers before removing support.

The v2.10 Reports workspace remains unrouted while dataset visibility is being verified. Generation is separately disabled. Its isolated implementation persists a pending key before sending, retries that key after reload, and uses an exclusive browser Web Lock across tabs. It fails closed when storage or Web Locks are unavailable, and retains the completed marker until the person explicitly requests another report. A synthetic browser harness exercises simultaneous tabs and a lost response; an HTTP-to-PostgreSQL test separately verifies concurrent requests, replay, conflicting payload and verified actor. These are not a browser-to-production integration test.

Before release, deploy and verify the migration, verify dataset-specific report metadata and download authorization, run an authenticated browser against PostgreSQL with real worker/outbox processing and failure recovery, define retention for receipts and report artifacts, and capture responsive and denied-state evidence. Browser storage loss or a different device cannot recover a pending key without a separate server-side discovery mechanism. Independent actions in different browser profiles or devices do not share a Web Lock and may create separate runs.
