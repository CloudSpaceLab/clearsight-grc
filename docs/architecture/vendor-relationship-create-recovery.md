# Vendor relationship creation recovery

The repository contains an internal, scope-bound create receipt and version precondition implementation. A receipt binds tenant, legal entity, request key, verified actor and request digest to the original creation result. PostgreSQL serializes matching request keys and writes the relationship, audit event, outbox event and receipt in one transaction. Reuse locks the exact scoped source relationship and vendor and checks both expected versions inside that transaction. Memory storage applies the same checks under its write lock. Receipts are retained for the relationship lifetime; migration rollback is blocked while they exist.

This is not an exposed recovery contract. The HTTP handler rejects keyed creation and relationship reuse until current authority resolution and revocation are synchronized with the creation transaction. The v2.10 UI hides reuse and continues to treat an unconfirmed ordinary create as unknown. The existing unkeyed create remains available; it cannot be retried safely without checking for duplicates. Callers must not rely on the internal receipt implementation until the authority boundary and an end-to-end recovery contract have been tested and exposed deliberately. Existing callers that sent `existing_relationship_id` now receive an unavailable response rather than an unsafe reuse.

PostgreSQL receipt replay checks that the stored vendor and relationship agree on tenant, entity and vendor identity, and that the embedded relationship ID matches the receipt's separately stored relationship ID, before returning the identifier representation used by the already-scoped retry. This permits a later retry scoped by the alternate slug or UUID representation without altering the original receipt. PostgreSQL integration cases cover the alternate representation and an ID mismatch but have not been executed without `TEST_DATABASE_URL`. The authority boundary and end-to-end recovery contract still prevent exposure of keyed recovery.
