# Program read-scope boundary

The Program review digest and exact Program reads now apply the existing Program scope to the verified principal in the repository query. Program lists and summaries apply the same predicate before limits and keyset cursors; Matter summary linked-Program counts and Program filters apply it before counts and page selection. The Memory adapter follows the same scope rule. A restricted Program denied by the current PostgreSQL read cannot be returned through the former post-create cache; the create service already returns its committed Program if its immediate reread fails.

The digest's subsequent checkpoint, baseline and bounded event reads independently recheck Program scope. A checkpoint lookup distinguishes a permitted Program with no checkpoint from a denied Program; scoped event reads likewise distinguish an empty history from denial. A missing or denied baseline aborts the digest. The reads are separate database statements, not one transaction snapshot; the tests establish denial when scope changes before each protected read, not linearizable revocation through response delivery. Recorded baseline calculations are loaded with the snapshot when reconstructing the visible fingerprint.

This is not complete system-wide Program isolation. Program report rows and their source-population boundary in `internal/reporting/program_matter_postgres.go` require an explicit reporting-access policy and independent principal-scope audit. Their existing report authorization and tenant/entity restrictions remain unchanged; do not assume the Program list predicate applies to reports or expand report access based on this change. Other cross-domain Program counts and references also require review. The Program checkpoint decision gate remains closed.

Until report access is defined end to end, creating Program reports or Matter board briefs and downloading their existing artifacts return unavailable. Program report owner options are also unavailable. Queued runs of these two datasets are stopped before reading source rows and receive the terminal `program_scope_unavailable` failure code; existing files are retained but cannot be opened through the report service. Idempotent creation receipt recovery for those datasets is also unavailable. Other report datasets retain their existing rules. The UI keeps an uncertain request key without offering an unsafe retry and identifies affected ready reports as unavailable.

Filtering generation by the original requester alone is insufficient: a requester may lose access before or after generation, and `REPORT_DOWNLOAD` currently allows another person in the legal entity to open an artifact. Existing immutable artifacts cannot be safely re-filtered at download. The approved policy must specify requester and downloader visibility, revocation, cross-principal sharing, source population and high-water behavior, queued/partially generated runs, and treatment of previously created files. Report definition/run metadata still uses the existing global `PRIVACY_READ` restriction and needs its own dataset-aware audit; this containment does not establish that those metadata are Program-scoped.
