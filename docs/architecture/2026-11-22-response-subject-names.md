# Completed response subject names

The completed response list and detail do not currently include a subject name. Response visibility does not itself prove permission to read that subject: `completedResponseDiscoverySQL` includes a vendor response-review route, while third-party origins use document workflow authority. Do not join or return a subject name solely because a response is visible.

A future bounded projection should share one verified subject-read predicate with the corresponding Program, Matter and vendor service detail endpoints, apply exact tenant/entity and subject identity inside the repository query, and return no name when the subject is missing, retired, inaccessible or of an unsupported type. Use a left join or correlated lookup after the response scope is established; do not issue per-row browser lookups or filter after pagination. Do not substitute an identifier as a name.

Before release, PostgreSQL and HTTP tests must cover public and restricted Programs and Matters, vendor owners and non-owners, independent response reviewers, third-party origins, deleted or retired subjects, wrong entity and tenant, revoked access, malformed subject types, exact response detail and keyset pagination. Demonstrate parity with each subject detail route and ensure names are never returned where that route denies access. Add response list and detail UI tests for available and unavailable names. The legacy response suite also includes field-level assessments, which remain unavailable pending the separate field-assessment containment prerequisites.
