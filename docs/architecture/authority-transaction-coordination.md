# Coordinating authority changes with material commands

**21 November reassessment:** The tenant-wide epoch protocol below is an incomplete proposal, not an enabled coordination guarantee. Active SCIM, delegation-creation and policy-revision writers no longer acquire its partial lock. The only command-side users are private, unregistered internal-response operations; they remain gated. This avoids imposing contention across a tenant's unrelated work and a new provisioning dependency without a complete participating writer set. A replacement must explicitly define and test the authority decision instant, concurrent revocation behavior, verified scope and transactional audit before those operations can be enabled. Entity-scoped advisory locks and ordinary row/version checks continue where already required.

Status: implementation required; this document does not enable internal response routes. The current transaction-bound authority lookup is not sufficient to serialize a material command against every authority change. This also applies to a form transition that relies on the same resolver.

Migration `000152` and the PostgreSQL tenant fence helpers remain as unused experimental infrastructure for private commands; they do not establish authority coordination. They have no complete writer coverage, database backstop or time-validity guarantee. Active governance revision and delegation writes retain their verified tenant UUID and existing transactions without taking the epoch lock. Their existing scope, maker-checker and audit protections remain. No route may be enabled on the assumption that this experimental protocol coordinates authority changes.

On 21 November, `TestPostgresTenantAuthorityFence` and `TestInternalPostgresWorkspaceIdentityVersionProvenanceAndRollback` passed against a separately initialized PostgreSQL 18 cluster with the current migrations. These targeted results cover the epoch lock and the listed workspace identity, rollback and eligibility cases; they do not cover all authority writers, source-recipient revocation, time-based expiry or the database bypass backstop, and they do not enable the private routes.

Private PostgreSQL internal-response save and submit now resolve the verified actor's tenant to one UUID and take the shared epoch lock before workspace and eligibility locks, pass the pinned scope to the authority lookup, and include the epoch in their transactional event. These paths remain unregistered: the other writers, database enforcement and time-validity rules are not complete. The associated unit tests verify scope pinning and fail-closed ordering; PostgreSQL execution and contention tests remain unverified without `TEST_DATABASE_URL`.

For shared response documents, the transaction-bound PostgreSQL artifact loader now locks the exact artifact and matching source-recipient row together, and rechecks recipient eligibility after a concurrent revocation completes. A two-connection test passed both command-first and revocation-first orderings on an isolated PostgreSQL 18 database; the existing external shared-workspace integration test also passed. The exact source recipient can differ from the acting recipient. Internal save and submit validate answered artifacts through this loader before their writes, and a submitted artifact cannot be attached if that validation fails. External workspace draft save now re-reads the locked request and validates merged answers through the same transaction-bound loader before writing. Isolated PostgreSQL tests verify that revocation-first rejects the draft with no edit, event or outbox, while command-first keeps revocation waiting and commits one edit, event and outbox. Internal routes remain gated: comprehensive internal-command/outbox rollback and lock-order tests, database enforcement and the complete authority writer inventory are still required.

## Failure and scope

`internal/evidence/internal_workspace_postgres.go` locks the request, workspace, recipient, principal and matching eligibility rows and resolves authority through the same PostgreSQL transaction. `internal/evidence/postgres.go` does the equivalent for an internal document upload. Those row locks do not prevent a new, higher-priority route, a grant, a segregation rule or a delegation from being inserted, nor do they synchronize all changes to existing route inputs. `internal/authority/postgres.go` reads effective routes, assignments, principals, positions, roles, bindings, legal entities, delegations, grants and segregation rules. Recipient eligibility additionally reads SCIM users and sources, directory groups, members and role bindings in `internal/evidence/recipient_candidates_postgres.go`. A missing matching row is meaningful, so locking only rows returned by those queries cannot close the race.

The existing governance advisory locks are not a common protocol: policy activation and delegation activation use entity-oriented locks; other transitions and background expiry do not consistently acquire them, and policy revision uses another key. The effective-route refresh in migration `000014` rebuilds routes for a tenant. An entity-only fence is therefore insufficient. A reader-only fence, a final recheck without a matching writer fence, or a serializable reader against ordinary read-committed writers is not a replacement.

## Proposed transaction contract

Implement a shared PostgreSQL helper in `internal/authority` with an API equivalent to:

```go
// verifiedTenant is resolved from the verified identity to one immutable tenant UUID.
func LockTenantAuthorityForCommand(ctx context.Context, tx pgx.Tx, verifiedTenant uuid.UUID) error
func LockTenantAuthorityForMutation(ctx context.Context, tx pgx.Tx, tenant uuid.UUID) error
```

The first takes a shared transaction-scoped fence and the second an exclusive one on the same tenant. The fence must last to commit or rollback and fail closed if the tenant cannot be resolved. Resolve slug or UUID to a single tenant UUID using a bounded indexed lookup; never derive it from a request body. Multi-tenant maintenance operations acquire exclusive fences in deterministic UUID order before authority or eligibility rows are locked. Tenant-wide fencing is intentional: wildcard assignments, tenant-wide roles and the route rebuild can affect multiple legal entities. Measure contention before considering finer-grained locks.

A practical starting implementation is an indexed `tenant_authority_epochs(tenant_id primary key references tenants, version bigint not null)` row. Bootstrap one row per existing and new tenant. The command helper selects that row `FOR SHARE`; the mutation helper selects it `FOR UPDATE` and increments the version in the same transaction. Missing rows are errors, never implicit successful authorization. A shared advisory-lock implementation is possible but only if the database also prevents unfenced writes; neither API alone enforces the protocol. Do not expose the helper as complete until bypass prevention and the complete writer matrix below are implemented and verified.

For an internal save, submit or upload, begin the transaction, acquire the shared fence **before** locking the workspace or eligibility rows, lock and reload the request and subject, obtain fresh database time, resolve the exact actor and request using `authority.WithPostgresTransaction`, then validate and write the material record, event and outbox in that transaction. Enforce verified tenant, entity, recipient and performer throughout. Persist the epoch and resolved route version with the audit record. A form transition follows the same ordering before locking its form or transition rows. Existing material commands using this resolver require an inventory and migration to the same protocol before it can be called a general authority guarantee.

Time can invalidate eligibility without a database write. Define and implement the authorization instant explicitly: sample `clock_timestamp()` after the fence and subject locks are acquired; resolve all effective dates at that instant, and reject if the transaction crosses the earliest applicable authority or eligibility expiry before its final material write. This requires the resolver to return a conservative validity deadline for the selected route, effective origins, grants, delegations and relevant exclusions. No deadline may be inferred from only the winning principal. Test scheduled activations as well as expiries. An ambiguous commit must remain an unknown outcome, not a reported denial or a blindly retried command.

## Writer inventory to fence

Acquire the exclusive fence before other locks, before mutation, and in the same transaction as audit/outbox. At minimum cover:

* `internal/governance/postgres.go`: `CreatePolicy`, `TransitionPolicy`, `ActivatePolicy`, `CreateDelegation`, `TransitionDelegation`, `ActivateDelegation`, `ActivateDueDelegations` and `ExpireDueDelegations`. The single-statement delegation creation must become a fenced transaction. Batch jobs must partition or acquire all affected tenant fences in stable order before selecting rows for update.
* `internal/governance/policy_revision_postgres.go`: `CreatePolicyRevision` and `ActivatePolicyRevision`, including effective-route refreshes triggered by policy/version writes.
* `internal/access/admin_postgres.go`: SCIM source create/rotate/revoke and group-role binding create/retire; organization-scope approval and `applyOrganizationScopeRevision` where it affects eligibility. `internal/access/admin_position_postgres.go` and `admin_position_role_postgres.go`: position and role-binding decisions and apply paths. Include restores and cascades.
* `internal/scimapi/postgres.go`: user and group create/replace/delete, `replaceGroupMembers` and `syncPrincipalIdentity`. Obtain the fence once at each outer transaction boundary; do not lock after principal or membership rows.
* Any direct or future writes to `routing_policies`, `routing_policy_versions`, `effective_authority_routes`, `responsibility_assignments`, `delegations`, `authority_grants`, `segregation_rules`, `principals`, `org_positions`, `role_templates`, `position_role_bindings`, `legal_entities`, `scim_sources`, `scim_users`, `directory_groups`, `directory_group_members` and `directory_group_role_bindings`. Include the organization hierarchy and the relevant Program/Matter scope changes that affect recipient eligibility. Existing subject and request row locks remain necessary; the fence does not replace them.
* Bootstrap/import paths `cmd/seed-bank-reference/form_policy_authority_seed.go`, `cmd/seed-bank-reference/source_employees.go`, `cmd/api/demo_postgres.go`, migrations, administrative SQL and any external provisioning job. Deployment tooling must follow the same protocol or run with commands disabled under an exclusive maintenance lock. Search SQL migrations, scripts and jobs again at implementation time; the Go source inventory alone is not proof of completeness.

Enforce coverage at the database boundary, not by convention alone. One candidate is DML triggers that update the appropriate epoch row transactionally as a backstop, together with runtime-role restrictions on disabling triggers and `TRUNCATE`. Application writers still acquire the exclusive fence **first**: a trigger that waits only after taking an authority row lock can deadlock with readers. Backstop-trigger deadlocks must abort safely and be observable; they do not establish a clean lock order. Design separate insert/update/delete statement triggers with transition tables where appropriate, handle cascades and parent deletion, and acquire all affected tenant rows in UUID order. Tables without a direct tenant key, including policy versions, need an unambiguous tenant mapping even during deletes; establish and test it rather than guessing. Reject cross-tenant moves or fence both old and new tenant. Verify ownership, bulk SQL, trigger recursion and the tenant bootstrap path. If complete database enforcement cannot be achieved, keep the feature gated.

## Required verification and rollout

1. Add real PostgreSQL tests using separate connections and deterministic lock barriers, not sleeps. For every writer class, test command-first (writer waits; command commits under the old state) and revocation-first (command waits, resolves again and denies). Cover higher-priority route and wildcard grant insertion, deletion, route refresh, delegation chains, segregation, SCIM source/user/group/membership changes, position/role and Program/Matter scope changes. Verify exact tenant/entity, named recipient, route version, rollback, audit and outbox.
2. Exercise multi-tenant batches, old/new tenant attempts, direct SQL and cascades, rollback, failed or missing epoch, deadlock handling and concurrent retry. Test changes that activate or expire while a command is blocked. Prove existing commands do not acquire locks in an incompatible order. Re-run end-to-end response, document scan and review tests with actual PostgreSQL.
3. Load-test concurrent authority changes and material commands by tenant, recording lock wait, timeout and deadlock rates and p95/p99 latency. Set operational alerts and a rollback procedure. Keep transactions short; no network or object-storage calls while holding the fence. Reconcile any object stored before a denied or uncertain transaction using durable cleanup/recovery.
4. Deploy epoch bootstrap and database enforcement together with all writers; audit deployment roles and every integration before enabling any command reader. Validate the migration and rollback on a representative copy. Enable internal endpoints and form-transition actions only after the full writer and temporal matrix passes, including the non-PostgreSQL mode or an explicit production prohibition for that mode. In-memory tests alone are not evidence of this guarantee.

Until those conditions are met, internal response and internal document upload handlers remain unregistered. The existing private components and handlers are not a production-ready workflow.
