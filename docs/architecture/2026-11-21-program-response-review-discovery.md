# Program response review discovery: implementation boundary

Status: private Program source implemented; HTTP endpoint is not registered. A form response visible to a person is not necessarily a response they are entitled to review. The existing actor-work endpoint covers workflow assignments and selected proposal work; it does not provide a complete response-review population. The existing completed-response endpoint combines ordinary read access and a reviewer discovery path, so its results cannot be labelled a review queue.

The private Program-review reader returns a bounded page of current, unreviewed Program response revisions for a verified person and exact tenant/entity. Its repository query checks Program visibility, reviewer route and respondent independence before pagination and rechecks session expiry at statement time. The proposed receipt labels its coverage `PROGRAM_RESPONSE_REVIEWS` and names the tenant, entity and principal; submitter names are resolved only from recorded identities in that entity, with missing names omitted. A cursor is scoped to the actor and entity; each page rechecks current eligibility. The memory adapter reports unavailable. It does not include Matter, vendor or third-party-origin reviews, nor does it turn a list item into decision authority. The handler remains unregistered because the SQL predicate duplicates the authoritative resolver and complete parity across supported and malformed routes has not been established; it may not be presented as a safe approval inbox yet.

An isolated PostgreSQL integration test exercises pre-limit filtering, a route revoked between pages, restricted Program scope, submitter and named recipient exclusion, expired session, and access to exact response detail, answers, documents and review action for final and provisional revisions. Reviewer-route parity is covered only by the separately listed cases below; production-scale cardinality, EXPLAIN/load evidence, complete route parity and a unified approval source remain open. There is no dedicated current-response `(tenant, entity, created_at, id)` index; the existing scoped review-history index supports the reviewed exclusion. Measure representative workloads before selecting an index and rollout strategy. Retain append-only review history under its existing policy; this view adds no persisted queue or retention policy.

## Existing behavior and gap

`internal/evidence/completed_response_postgres.go` applies its discovery predicate before the page limit. Its reviewer-derived branch is limited to `VENDOR_RELATIONSHIP` responses with non-third-party origins; regular Program and Matter responses instead depend on their subject visibility. Exact response detail and `readResponseAssessmentMaterial` separately enforce their own visibility predicates. Expanding only the list predicate would create links that fail at detail and risks bypassing a restricted Program. `TestPostgresReviewerDiscoveryDoesNotBypassRestrictedProgram` verifies that a reviewer route alone does not reveal a restricted Program response and that both list and detail deny it, while the Program owner can read it. This test is a security baseline, not a completed named-review workflow.

## Smallest viable Program path

1. Define a bounded Program response-review source from current `FINAL` or `PROVISIONAL` immutable response revisions and active distributions, scoped to the verified tenant, legal entity and person. Use the existing response, request and distribution joins and validate request/distribution subject, exact form ID and version, exact response revision, and Program existence and legal entity. Exclude archived, revoked, superseded and mismatched sources. An approval is pending for a particular revision; a response revision with an existing whole-response review is not a new pending response. A later revision is considered independently.
2. In that repository query, before keyset pagination and `LIMIT`, apply both the Program's existing restricted-subject visibility predicate and the `forms.response.review` reviewer route. Exclude the actual submitter, the named internal recipient and the historical submitted recipient. Bind the actor from verified request identity; require the session to remain valid at the database statement time. Treat missing, ambiguous, expired or unavailable authority as denied, not as a broad read. Return only summary metadata, not answers or documents.
3. Reuse one equivalent authority and scope predicate for the exact response-detail and review-material readers, rather than authorizing the list by one rule and detail by another. Keep the material command's own fresh authority, independence, expected-version and transactional audit/outbox checks. A successful list result is never a decision capability.
4. The existing `authority.PostgresReadRouteSQL` is a translated predicate, while the authoritative resolver is separately implemented. Establish and test parity for scoped assignments, wildcard/specific precedence, multiple candidates, role and position scope, ambiguous routes, delegations, grants, segregation and effective dates before treating it as the review access boundary. Do not replace this with a hard-coded reviewer ID or role. Prevent the resolver and source predicate from drifting, preferably by reusing a single relational authority contract.
5. Expose a bounded actor-scoped page with a scope-bound keyset cursor and an explicit `PROGRAM_RESPONSE_REVIEWS` coverage label. It must not claim to contain all approvals, fabricate counts or merge into existing actor-work totals. Subsequent page requests re-evaluate current authorization; revoked rows may disappear. Provide an exact response link only after matching detail permissions are verified. Persist no separate approval queue when the response revision and its review history already establish the pending state.

## Required proof before enabling

Use a migrated isolated PostgreSQL database and real identity, authority and source records. Seed multiple Programs, two legal entities and two tenants, reviewed and unreviewed revisions, self-submission, delegated reviewer, conflicted and expired routes, restricted Program grants and mismatched request/distribution/recipient records. Verify a limit of one filters scope and authority before pagination; exact detail and decision see the same permitted sources; denied entries never affect cursors or counts; revocation and session expiry apply between pages; and previously reviewed versus newly submitted revisions have correct pending state. Exercise missing/ambiguous routes, higher-priority changes, delegation and grant parity, authority service failure, and concurrent subject or assignment changes with deterministic transaction barriers. Test an EXPLAIN plan and representative cardinalities with the existing indexes; add an index only if measurement demonstrates the need. Verify the memory adapter either enforces the same contract or fails closed.

Matter and third-party-origin reviews remain unavailable as a universal inbox until their individual subject and route boundaries pass. The Program source above is partial and does not by itself establish production acceptance.

The isolated PostgreSQL `TestPostgresResponseReviewerReadRouteParity` compares the current read predicate with the normal and batch resolvers for an exact whole-response named reviewer, missing/unassigned route, scoped delegation, minimum and maximum materiality, decision and object-type constraints, grant, ambiguous assignment, role and entity scope, segregation and expired delegation. Those cases pass. A failing-first test exposed that all three paths previously ignored delegation materiality limits; the paths now share the same limit predicate and reject malformed limits. This narrow comparison does not establish the other route, scope or timing cases above and does not authorize enabling Program discovery.

## Simplest shared-authority path

The existing `ResolveMany` implementation is one PostgreSQL query, but it takes a JSON array, creates request indexes and returns selected route and candidate rows. Material decisions currently use a separate `Resolve` / `Simulate` implementation. Embedding the batch query in the Program list alone would therefore still create a second interpretation of the write authority; the existing subset of parity tests cannot rule out all over-authorization.

Extract the route-selection, ambiguity, delegation, grants and segregation CTEs into one reusable relational definition that accepts a typed request row source. Make the ordinary single-request resolver and the batch resolver consume that same definition, then feed the Program source's exact response IDs and verified context into it before pagination. The Program query must still apply subject visibility, source lineage, current revision, respondent conflict and session checks independently. Keep one decision timestamp and immutable route receipt, and do not introduce a queue table or hard-coded approver. Test regular, batch and paged reads against the same fixtures for every supported selector and strategy, multiple or ambiguous routes, roles and positions, scoped delegations, effective dates, grants, conflicts and malformed persisted scopes. Use real PostgreSQL transaction barriers for revocation and session expiry, compare candidate sets, and test list/detail/decision parity. Run `EXPLAIN (ANALYZE, BUFFERS)` and a representative high-cardinality load test before selecting an index and enabling the route. A statement-scoped source is not a substitute for proving the exact decision transaction's own authorization boundary.

The delegation object, exact target, decision type and materiality predicates now share one internal SQL fragment across individual, batch and private read resolution. PostgreSQL tests exercise matching and excluding target scopes and compare the three paths for the previously listed cases; Program and vendor discovery plus document-import actor reads were also retested. This removes one source of drift, not the remaining duplicated route-selection, legal-entity, grant and segregation implementations. The Program endpoint remains unregistered until their equivalence and performance are established.
