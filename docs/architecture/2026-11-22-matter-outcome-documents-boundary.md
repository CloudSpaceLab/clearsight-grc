# Matter outcome Documents — implementation boundary

Outcome results currently accept `evidence_references` as arbitrary JSON. The result command does not validate a document occurrence, its usability or the acting reviewer's current document authority. The Matter aggregate, point-in-time history and command responses can return those references to a reader who may not have access to the referenced document. The v2.15 result form therefore sends an empty reference list and does not offer document selection.

Protected Documents are immutable submitted occurrences, identified by submission, field, artifact and response revision. `DistributionService.GetExactDocument` applies the current actor's tenant, entity and principal scope; the PostgreSQL implementation currently executes through the evidence repository pool. The outcome command uses a separate continuity transaction for the result, append-only event and outbox. A preflight exact read cannot prove access at the result transaction's commit boundary, and a browser selector cannot authorize a material command.

A safe implementation needs a bounded typed occurrence reference, an exact document authority check within the same database transaction as the result/event/outbox, and equivalent fail-closed memory behavior. It must also prevent unrestricted reference metadata from leaking through every Matter aggregate, command receipt, point-in-time history and activity surface; document resolution must recheck the current reader's exact document authority and avoid revealing hidden versus absent occurrences. The result receipt must confirm the scoped references without making a post-commit authorization failure look like a command failure. A migration must preserve historical result evidence and audit events without broadening access.

Before exposing the picker, add tests for forged or cross-tenant/entity references, restricted response and document subjects, revoked or expired actors and concurrent revocation, ambiguous occurrence IDs, unsafe or unavailable artifacts, delegated reviewers, atomic rollback and unknown commit outcomes, exact authorized/denied reads, historical reconstruction and parity across PostgreSQL and memory. The picker should use a bounded authorized population with explicit continuation and preserve the manual/no-document path. No schema or endpoint is claimed ready by this note.

## Reuse assessment

There is no small drop-in transaction-scoped authorization path today. `continuity` already depends on `evidence`, so a shared low-level evidence query need not introduce a Go import cycle. However, `GetExactDocument` uses a pool-backed query, and vendor-response access additionally depends on `assessmentReadAuthority` and `ReadResponseAssessment` before that query. Passing a transaction to the SQL alone would not re-evaluate that authority or protect against a concurrent revocation. Both the single-event `ApplyMatterEvent` and compound `ApplyVerificationResultBundle` paths would need one transaction-aware validator, including the exact identity and current authority/session boundary and equivalent memory semantics.

There is also no single existing read wrapper that protects all returns: the normal Matter read decorates an embedded aggregate, point-in-time history writes an aggregate directly, and many mutation handlers write aggregate receipts directly through `writeContinuityResult`. Events and activity must be audited separately. A small safer design is to keep new document occurrence references outside the public aggregate in a bounded relational result-to-occurrence link, create links in the result transaction, and resolve them only through a narrowly scoped result-document endpoint that first authorizes the exact Matter/result and then the current reader's exact occurrence. The write receipt can confirm the resulting relationship without exposing it to unrelated Matter readers. Historical free-form references need an explicit migration and disclosure policy, not conversion by guessing at identifiers. Whether restricted/absent links can be represented without an existence signal must be settled before implementing the endpoint.

To make this implementable: expose the existing exact occurrence predicate against a transaction-capable query interface; bring the assessment reviewer route/session and any required visibility locks into that transaction; route both ordinary and compound outcome commits through the same bounded validator; add memory parity; create the result-to-occurrence relation and indexes with an expand/contract migration; introduce one actor-scoped resolver returning only authorized occurrences; remove new references from public aggregates, public event responses and receipts while retaining protected, reconstructable link events; and audit all existing Matter, historical and event readers for legacy reference handling. The result/event/outbox and link insertion must commit atomically. An actor-scoped resolver alone is insufficient if raw identifiers remain in another response.

The first prerequisite is now implemented internally: the existing PostgreSQL document query accepts either the pool or a caller's transaction and keeps the same bounded exact-occurrence selectors. A real PostgreSQL test demonstrates that an exact query on a transaction sees an uncommitted subject-scope restriction while a pool read still sees the previously committed state; it also checks exact-field isolation and rejects missing selectors. This does not lock or re-evaluate identity, session, route or revocation, and it is not wired to outcome commands or exposed as an attachment feature. No migration is appropriate until the reference and protected-history contracts are settled.
