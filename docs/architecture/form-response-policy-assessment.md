# Response policies and completed bank assessments

Date: 2026-09-08. Scope: the vendor forms and assessment design, section 3.

Forms Policies uses the existing response-policy lifecycle and canonical Automation Policy table. Contextual creation (`create_automation_policy: true`) creates the typed response-policy revision and its canonical automation guardrail in one transaction, using the server-generated revision identity for both records. Existing selected guardrails remain independently managed. Revising a policy creates a new draft and independent simulation/approval cycle; it never edits an active definition. In-memory composition shares the canonical autonomy repository with response policies.

The contextual guardrail derives eligibility, action class, rollout, issue limits and outcome check from the response-policy draft. Activation still checks the exact approved guardrails and current authorizer, subject owner, issue owner, reviewer and service performer. An approved contextual guardrail can become active only with its approved typed policy in the same repository transaction. Conflicts roll back both records. Suspension affects both; rollback creates a new governed revision and preserves compensation review.

The form-scoped automation selector reads at most 100 current canonical revisions after checking the verified tenant, legal entity and exact active form with automatic scoring or a bank-review rubric. The PostgreSQL query repeats legal-entity/form scope and excludes superseded canonical revisions. Supported subjects are named Vendor services, Programs and Issues and changes. Editing an existing selected guardrail's limits, result basis or timing starts a new contextual guardrail draft. No IDs or JSON are required for normal setup.

`eligibility.result_basis` is optional: omission retains AUTOMATIC. BANK_ASSESSED uses a stored assessment summary whose state is ASSESSED, score is FINAL, final flag is true and all required assessments are complete. The configured coverage threshold applies to that assessed result. New UI drafts for forms with manual or combined review default to completed bank assessment. Manual-only forms with scoring mode NONE can create BANK_ASSESSED policies when a weighted review rubric is present; they cannot create automatic policies. Automatic scores and original answers remain unchanged.

The existing scored-event publisher also handles FORM_RESPONSE_ASSESSED. Provisional assessment events do not execute policies. An assessed event identifies its assessment version; superseded results are ignored. The material PostgreSQL transaction locks the response and distribution and checks the latest assessment again before writing. In-memory execution holds the assessment store read lock through the policy commit. Immutable execution and failure receipts retain basis/version. Reconciliation jobs retain the result occurrence time and assessment version, use the existing leased retry flow and can recover a current final assessment whose policy receipt is absent.

Execution identities include the assessment version. Replays reuse the receipt; corrections produce a new receipt. Automatic and bank results for the same response, subject and issue type reuse an open adverse episode. Execution-history membership preserves reuse even when another automatic response has since updated that issue. A subsequent bank correction retains that issue. Outcome checks and independently verified closure remain unchanged. A new score cannot silently close an issue.

The policy detail shows the last 50 execution-operation records, result basis and time. This configuration read does not expose answers, protected subjects, response identifiers or linked issue identifiers. The scoped policy and existing revision list remain the authorization boundary for these operational facts.

Migration 84 adds result-basis/version metadata, scoped execution-history and exact form-choice indexes, and extends receipt/reconciliation uniqueness. No material history is deleted. Downgrade fails transactionally when preserving assessment history makes the old uniqueness contract impossible.

Verification: Go policy/autonomy tests; actual PostgreSQL 18.6 policy integration suite including contextual transaction conflict rollback, legal-entity choice isolation, automatic/bank issue reuse and corrected bank results; six policy-editor tests; policy view/API tests; copy-quality regression; TypeScript compilation. Browser render evidence is recorded with the parent vendor-assessment delivery; this document does not assert a rendered state was inspected.

Automatic scored-response events may include the exact consumed `request_id` and `request_version` for collection receipt reconstruction. The publisher validates and forwards this bounded identity/version pair, while continuing to reject unknown payload fields. Both values must be present together and the version must be positive. Historical events without the pair remain replayable. The consumed request version is provenance; a later request revision does not invalidate the immutable scored response or replace its version.
