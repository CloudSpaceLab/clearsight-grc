# Vendor finding creation boundary

The v2.15 vendor assessment intentionally keeps finding creation unavailable. The existing deficiency command creates the restricted Matter and its event/outbox in one continuity transaction, then links that Matter to the assessment and vendor in a separate third-party transaction. It attempts compensation after some returned link failures, but a process interruption between commits can leave an unlinked Matter. Authority is resolved before those transactions and is not re-evaluated in their commit boundary. This does not meet the material-command transaction and current-authority requirements.

The HTTP creation route returns an unavailable response in every environment until the atomic command is implemented. The private service remains covered by tests but has no production caller. It rejects a Matter whose legal entity differs from the assessment, and PostgreSQL applies the same entity/type/trigger proof before both a new link and a replay. The PostgreSQL trigger comparison also uses the stored text type; the prior UUID comparison failed at runtime. These safeguards do not make finding creation atomic.

Before enabling creation, one governed transaction must re-evaluate verified actor/session and current reviewer route, lock and validate the assessment version and legal entity, create or idempotently recover the restricted Matter, write both canonical links, append the Matter and assessment events and outbox messages, and commit once. A durable request identity must permit recovery from an unknown commit without inventing a duplicate or cancelling a linked finding. Add equivalent memory behavior and real PostgreSQL tests for interruption/rollback, concurrent retries, delegation and revocation, cross-entity isolation, replay, and actor-scoped reads. Existing orphan records need an explicit reconciliation approach that does not delete or silently relink them.
