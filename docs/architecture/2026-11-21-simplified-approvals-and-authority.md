# Simplified approvals and authority

Status: design direction and incremental implementation, not production acceptance. This decision responds to the request to simplify authority and make approvals a first-class experience. It supersedes the proposal to expand a tenant-wide fence to every authority writer as the default implementation. Existing routes remain gated until their individual command and read guarantees are demonstrated.

## User outcome

A person sees the work assigned to them, the record and version requiring a decision, the requester, due date, relevant documents, and the decision they are authorized to make. Review, approval, sign-off and completion retain their distinct meanings. A returned item includes a reason. The record shows the decision, actor, time and version. Unknown data and unavailable actions remain explicit; a workflow assignment is not automatically an approval.

The Work & Approvals experience should reuse the existing actor-scoped work source and exact record screens. It must not create a parallel approval queue or claim an empty or complete approval population until the backend provides one. The current work endpoint covers workflow assignments and selected proposal work, not every approval. Counts and filters must retain that coverage. Links and decisions are enabled only where a current authorized destination and command exist.

## Decision boundaries

* Routine drafts, uploads and ordinary assignment work require verified identity, tenant/entity scope, ownership or assignment and the relevant record version. They do not acquire a bank-wide coordination lock merely because approval exists elsewhere. Upload storage and cleanup still require their own durable recovery design.
* Material reviews and approvals re-evaluate the applicable versioned route, actor eligibility, scope, delegation and independence for the specific decision. They write the decision, its source version, actor, route/policy receipt, audit event and required outbox in one transaction. An authorization read followed by an unprotected write is insufficient.
* Prefer a single database statement that evaluates current eligibility and performs the version-guarded decision and transactional event writes using the same PostgreSQL statement snapshot. Its authorization instant is the start of that statement, after any necessary subject locks are acquired. A revocation committed before that instant must be observed; a revocation concurrent with the statement is ordered after the decision for this contract. This ordering must be explicitly tested with independent connections and is not established for existing commands merely by adopting this document.
* A workflow that cannot express all route inputs and writes in one statement must select and document another proven transaction strategy. A sequence of READ COMMITTED queries, a final recheck, or an independently resolved route is not equivalent to one snapshot. Where institutional policy requires revocation to win against an already-started decision, use a narrower shared serialization point for that workflow and its relevant policy changes; measure and test it. Do not add a tenant-wide writer protocol by default.
* Take database time at the decision boundary, and use it consistently for actor, route, delegation and grant validity. Do not call external services or object storage while a decision transaction is open. Idempotency, conflict handling and unknown commit outcomes must preserve existing records and prevent a duplicate decision.

The existing whole-response review route is registered and writes its review, event and outbox in one transaction. It also resolves reviewer authority inside that transaction, but uses multiple reads at READ COMMITTED; its ordering against concurrent authority changes has not been proven. This design does not imply that route already satisfies the preferred single-statement boundary. Internal respondent save, submit and upload remain unregistered.

The response-review command rechecks session validity after resolving the reviewer route and uses that instant for the review timestamp. A PostgreSQL test covers a session expiring during route resolution and verifies that no decision, event or outbox is committed. This check uses the service clock; it does not freeze route inputs, provide a database-clock decision instant or establish ordering against a concurrent authority change.

The individual resolver, batch resolver and scoped read predicate now use one grant-limit check. An absent limit and an integer between 0 and 5 retain their meanings; malformed values, JSON nulls, non-object limits and unsupported keys make that grant ineligible. The mere presence of such a grant still activates the grant boundary, so an invalid grant does not become an unrestricted route. If no other eligible grant remains, the resolvers return no route and the scoped read excludes the row. Existing valid grants are unchanged. A real PostgreSQL regression checks matching and excluded ranges, boundary values and malformed values across all three resolution paths.

**Deployment compatibility:** `authority_grants.limits` historically accepted arbitrary JSON, and previous resolution ignored unknown keys and treated some null or string values as unrestricted or numeric. No writer or schema in this repository defines supported keys beyond `min_materiality` and `max_materiality`; product requirements mention possible future amount and duration limits. Before deployment, inventory existing grant JSON types and keys, and identify null, string, non-integral, out-of-range and unsupported values. Have the bank's authorized policy owner review any affected grants and provide explicit supported replacements; do not remove or reinterpret an unknown restriction automatically. Unsupported keys remain denied until their semantics are implemented and tested. This preserves safety but can make existing malformed or unsupported grants unavailable until corrected.

The PostgreSQL review insert also checks the verified session expiry against `clock_timestamp()` in the insert statement. An isolated database test with an application clock behind the database verifies that an already-expired session writes no review, event or outbox. The timestamp on the recorded review remains the service's post-resolution time. This guard does not make the separate source and authority reads a single snapshot or resolve concurrent authority revocation.

The existing PostgreSQL authority resolver now has an unwired transaction-only `ResolveCurrent` method using the shared batch query and database statement time; it returns the selected route and evaluation instant. It is not exposed through `authority.Service` and is not used by the review command. Adding it to that interface alone would also affect its non-PostgreSQL implementations and existing test adapters, and calling it before the review insert would still leave two separate statements. Neither change by itself meets the decision boundary above.

Whole-response review decisions are temporarily disabled by default, including PostgreSQL production and hosted demo. Scoped history remains readable and `may_review` is false. Explicitly configured non-production in-memory demo composition can enable the existing decision flow without bypassing reviewer authorization; the service rejects this opt-in for any non-memory store. PostgreSQL integration tests exercise underlying transaction code through a test-only direct flag and do not enable it in runtime composition. The route remains registered but denies writes until the transaction boundary is proven. The current route receipt stores rule ID and policy version but not source policy ID; a colliding rule/version cannot be reconstructed uniquely. Persist a backward-compatible source-policy receipt and verify historical interpretation before enabling material decisions.

The separate Program review checkpoint acceptance command is also unavailable: the HTTP handler denies the write and Program operations mark it unavailable, while the review digest remains readable. Its preflight reviewer route is not re-evaluated inside `RecordProgramReview` after the Program lock, so it needs the same transaction-time authority, session and route-receipt proof before the action returns.

For the review command, first lock and version-check the exact response and distribution, then use a single statement that evaluates the full current reviewer route and verified session, rejects respondent conflict, and inserts the review with the same database instant and selected rule/policy receipt. The existing transaction must then append the matching distribution event and outbox or roll back all three. Preserve the verified actor and entity, current response revision and review version; no request-supplied reviewer or timestamp may replace them. A missing transaction or unsupported authority implementation must deny rather than fall back to a preflight result. Test the actual command with independent PostgreSQL connections and barriers for a route or delegation revocation before the decision statement, concurrent revocation under the documented ordering, a session expiring during authorization or before insertion, a changed response/distribution version, conflicting or ambiguous reviewer, duplicate submission, and event/outbox failure. Compare the exact route and policy receipt with the current resolver for named, role, position, delegation, grant and segregation cases. Only then connect the new boundary and enable its decision action.

## Alternatives considered

1. **One scoped decision statement per supported command (preferred):** keeps the decision instant and atomic write explicit and avoids coupling every directory change to every command. It requires careful reuse or compilation of the actual resolver semantics, bounded queries, and proof that all required event/outbox writes share the statement or transaction.
2. **Tenant-wide authority epoch:** can serialize cooperating commands and authority changes, but requires every writer and bypass path to participate, increases contention and adds infrastructure. The current partial implementation cannot establish that guarantee and must not be treated as complete.
3. **Role check before a separate write:** is simple but can act on stale or incomplete authority and cannot enforce independent review reliably. It is not acceptable for material decisions.

## Incremental changes and acceptance

First remove partial fence dependencies from active paths where no enabled command benefits, without enabling currently gated workflows or erasing retained records. Preserve existing identity and scope checks. Then select a concrete approval or response-review command and implement its scoped decision boundary, including real PostgreSQL concurrency tests: revocation committed before the statement, concurrent change, missing/ambiguous route, conflict, expired delegation, maker-reviewer conflict, stale version, rollback, and duplicate submission. Test the actual applicable route semantics rather than substituting a fixed assignee or broad role. Record any exception where stricter revocation ordering is required.

Connect the approval experience to that exact authorized source only after list, detail and command are available for the same tenant/entity and actor. Test approved, returned, pending, denied, stale, unavailable, keyboard and narrow-viewport states. Historical events retain their original interpretation; a display or routing change does not rewrite prior decisions. Do not claim production acceptance until operational, access, source and workflow evidence is retained.
