# Simplified approvals and authority

Status: design direction and incremental implementation, not production acceptance. This decision responds to the request to simplify authority and make approvals a first-class experience. It supersedes the proposal to expand a tenant-wide fence to every authority writer as the default implementation. Existing routes remain gated until their individual command and read guarantees are demonstrated.

## User outcome

A person sees the work assigned to them, the record and version requiring a decision, the requester, due date, relevant documents, and the decision they are authorized to make. Review, approval, sign-off and completion retain their distinct meanings. A returned item includes a reason. The record shows the decision, actor, time and version. Unknown data and unavailable actions remain explicit; a workflow assignment is not automatically an approval.

The Work & Approvals experience should reuse the existing actor-scoped work source and exact record screens. It must not create a parallel approval queue or claim an empty or complete approval population until the backend provides one. The current work endpoint covers workflow assignments and selected proposal work, not every approval. Counts and filters must retain that coverage. Links and decisions are enabled only where a current authorized destination and command exist.

## Decision boundaries

* Routine drafts, uploads and ordinary assignment work require verified identity, tenant/entity scope, ownership or assignment and the relevant record version. They do not acquire a bank-wide coordination lock merely because approval exists elsewhere. Upload storage and cleanup still require their own durable recovery design.
* Material reviews and approvals re-evaluate the applicable versioned route, actor eligibility, scope, delegation and independence for the specific decision. They write the decision, its source version, actor, route/policy receipt, audit event and required outbox in one transaction. An authorization read followed by an unprotected write is insufficient.
* Prefer a single database statement that evaluates current eligibility and performs the version-guarded decision and transactional event writes using the same PostgreSQL statement snapshot. Its authorization instant is the start of that statement, after any necessary subject locks are acquired. A revocation committed before that instant must be observed; a revocation concurrent with the statement is ordered after the decision for this contract. This ordering must be explicitly tested with independent connections and is not established for existing commands merely by adopting this document.
* A workflow that cannot express all route inputs and writes in one statement must select and document another proven transaction strategy. A sequence of READ COMMITTED queries, a final recheck, or an independently resolved route is not equivalent to one snapshot. Where institutional policy requires revocation to win against an already-started decision, use a narrower shared serialization point for that workflow and its relevant policy changes; measure and test it. Do not add a tenant-wide writer protocol by default.
* Take database time at the decision boundary, and use it consistently for actor, route, delegation and grant validity. Do not call external services or object storage while a decision transaction is open. Idempotency, conflict handling and unknown commit outcomes must preserve existing records and prevent a duplicate decision.

The registered whole-response review command is disabled for PostgreSQL production and hosted demo. Scoped history remains readable and `may_review` is false. Explicit non-production in-memory demo composition may enable its existing authorization-checked flow; the service rejects this opt-in for non-memory stores.

The individual resolver, batch resolver and scoped read predicate now use one grant-limit check. An absent limit and an integer between 0 and 5 retain their meanings; malformed values, JSON nulls, non-object limits and unsupported keys make that grant ineligible. The mere presence of such a grant still activates the grant boundary, so an invalid grant does not become an unrestricted route. If no other eligible grant remains, the resolvers return no route and the scoped read excludes the row. Existing valid grants are unchanged. A real PostgreSQL regression checks matching and excluded ranges, boundary values and malformed values across all three resolution paths.

**Deployment compatibility:** `authority_grants.limits` historically accepted arbitrary JSON, and previous resolution ignored unknown keys and treated some null or string values as unrestricted or numeric. No writer or schema in this repository defines supported keys beyond `min_materiality` and `max_materiality`; product requirements mention possible future amount and duration limits. Before deployment, inventory existing grant JSON types and keys, and identify null, string, non-integral, out-of-range and unsupported values. Have the bank's authorized policy owner review any affected grants and provide explicit supported replacements; do not remove or reinterpret an unknown restriction automatically. Unsupported keys remain denied until their semantics are implemented and tested. This preserves safety but can make existing malformed or unsupported grants unavailable until corrected.

The gated PostgreSQL response-review transaction locks the exact response and distribution, then composes the shared current authority route with the version-guarded review insert in one READ COMMITTED statement. The statement checks verified actor and session, current subject visibility and respondent independence, and records database statement time and the selected source, rule and policy version. Migration `000153` preserves null receipts on historical rows and refuses rollback after a new receipt is recorded. The event and outbox remain in the same transaction. Direct Program, Matter and vendor relationship origins are supported by this private path; third-party origins fail closed.

Independent PostgreSQL tests cover pre-statement route revocation and replacement, respondent conflict, subject access revocation, entity and session expiry, concurrent review versions, event/outbox failure, migration rollback, tenant alias collisions and a lost-response retry followed by scoped history. A retry with the same expected version conflicts instead of returning an idempotent command receipt; history alone cannot prove which of two identical attempts committed. The existing preflight still resolves authority separately and can deny an otherwise valid decision. The PostgreSQL review transaction uniquely resolves the verified tenant slug or UUID before passing scoped material to its existing callbacks; ambiguous aliases fail closed. These tests do not yet establish every delegation, segregation, concurrent revocation and unknown-commit case for the complete command. The command and its UI remain disabled until independent security review and the remaining transaction and operational proofs are complete. The transaction-only resolver is not exposed through `authority.Service`.

The separate Program review checkpoint acceptance command is also unavailable: the HTTP handler denies the write and Program operations mark it unavailable, while the review digest remains readable. Its preflight reviewer route is not re-evaluated inside `RecordProgramReview` after the Program lock, so it needs the same transaction-time authority, session and route-receipt proof before the action returns.

Before enabling the response-review decision, complete real PostgreSQL command tests for named, role, position, delegation, grant and segregation parity, concurrent revocation ordering, stale source versions, and unknown commit recovery. Establish third-party-origin semantics, verify deployment of the additive migration and retain independent review evidence. Missing routes, ambiguous routes and unsupported authority adapters must fail closed.

## Alternatives considered

1. **One scoped decision statement per supported command (preferred):** keeps the decision instant and atomic write explicit and avoids coupling every directory change to every command. It requires careful reuse or compilation of the actual resolver semantics, bounded queries, and proof that all required event/outbox writes share the statement or transaction.
2. **Tenant-wide authority epoch:** can serialize cooperating commands and authority changes, but requires every writer and bypass path to participate, increases contention and adds infrastructure. The current partial implementation cannot establish that guarantee and must not be treated as complete.
3. **Role check before a separate write:** is simple but can act on stale or incomplete authority and cannot enforce independent review reliably. It is not acceptable for material decisions.

## Incremental changes and acceptance

First remove partial fence dependencies from active paths where no enabled command benefits, without enabling currently gated workflows or erasing retained records. Preserve existing identity and scope checks. Then select a concrete approval or response-review command and implement its scoped decision boundary, including real PostgreSQL concurrency tests: revocation committed before the statement, concurrent change, missing/ambiguous route, conflict, expired delegation, maker-reviewer conflict, stale version, rollback, and duplicate submission. Test the actual applicable route semantics rather than substituting a fixed assignee or broad role. Record any exception where stricter revocation ordering is required.

Connect the approval experience to that exact authorized source only after list, detail and command are available for the same tenant/entity and actor. Test approved, returned, pending, denied, stale, unavailable, keyboard and narrow-viewport states. Historical events retain their original interpretation; a display or routing change does not rewrite prior decisions. Do not claim production acceptance until operational, access, source and workflow evidence is retained.

### Response-review retry boundary (gated implementation)

The gated PostgreSQL and in-memory review paths now support a scoped request key. PostgreSQL rechecks current route, session and subject visibility in the receipt query, while the review, request key, event and outbox commit together. The client retains only the key, decision, expected version and response revision in account-scoped session storage; comments are re-entered after a reload. A reused key against another response returns forbidden without revealing the original receipt. The retry button explicitly states that it may submit the same decision, and missing account scope blocks submission. A definite initial validation rejection clears the pending attempt; uncertain outcomes remain pending. This remains unexposed in PostgreSQL runtime pending independent review and the outstanding route, historical-state and recovery proofs.

The existing report-run receipt is not directly reusable as an authorization check. It finds a receipt by tenant, entity, principal and key; response review additionally requires current session, current scoped subject visibility and the current reviewer route before returning a historical result. The material route middleware and preflight resolver perform separate reads and do not provide that single-statement proof. Returning a receipt solely because the key, actor or request matches would disclose review data after access is revoked. The currently gated command instead returns a version conflict after a lost successful response; scoped history may help the reviewer recover, but cannot distinguish two identical attempts.

Implement the minimal durable retry on the review row, not a second work queue or authority service:

1. Add a nullable UUID request key with a partial unique index on `(tenant_id, legal_entity_id, reviewer_id, request_key)` for non-null keys. Existing rows remain null. Refuse down migration when keyed rows exist. Check the next migration number against the integrated branch before allocating it.
2. Require a random UUID `Idempotency-Key` for new production review submissions. Bind a key to the exact canonical response revision, expected version, normalized decision and normalized comment. The immutable review row already records these fields: compare them directly, with `version = expected_version + 1`, rather than storing another copy or relying on an unhashed ambiguous concatenation. A reused key with a different request returns conflict without disclosing the existing record. The verified session provides the actor; request-body actor fields remain ignored.
3. Under the existing response/distribution locks and READ COMMITTED transaction, share the existing authority graph and scoped subject predicates between decision insertion and a parameterized receipt query. The receipt query must in one statement resolve the current exact route and eligible reviewer, check active entity, verified session expiry against database time, unique tenant alias, actor and current subject visibility, then return only the same actor's matching receipt. It must reject unsupported origins and ambiguous routes. Historical response status must be handled deliberately: a retry is a read of the prior decision, so its visibility and authority must be evaluated at retry time even if the response has since been superseded; do not silently reuse the new-decision `is_current` predicate without specifying the recovery consequence.
4. Check for an existing matching key after obtaining the existing subject lock and before rejecting an outdated expected review version. Serialize same-key requests across different response IDs within the same tenant/entity/actor using a transaction-scoped key lock, or another narrowly scoped proven equivalent; preserve the unique index as a final guard. A same-key race with differing inputs must produce at most one decision and no receipt disclosure. Store the key with the initial review insert in the same transaction as its event and outbox. Handle uniqueness conflicts without treating them as successful writes, and never return failure after a known commit because of a subsequent derived refresh.
5. The client generates one key per submitted decision, retains the key and exact submitted payload through an uncertain result, and does not generate a replacement on retry. Recovery must remain explicit: reload and retry only the same payload and key; edits require a new attempt after the previous outcome is resolved. Scope any browser persistence to verified account and response, clear it on a confirmed receipt or explicit abandonment, and prevent another account from retrieving an old receipt. A successful HTTP result must still match the response ID, revision, version, decision and review ID before it is treated as committed.
6. Add real PostgreSQL tests using separate connections for commit followed by lost response and exact-key retry; simultaneous same-key requests; differing payload, response, actor and entity reuse; uncommitted first-attempt rollback; revoked or replaced route; delegation and grant expiry; subject access revocation; expired session; tenant UUID/slug collision; historical/superseded response; event/outbox rollback; and a retry after a later decision. Assert one review, event and outbox and no leaked receipt on every denial. Add HTTP and browser tests for stable key retention, recovery after reload, malformed/mismatched receipts, and account changes. Keep production and PostgreSQL demo decisions disabled until this proof and the remaining route-parity checks pass.

The gated Program checkpoint writer now uses a five-second transaction deadline and records the database insertion time consistently in the checkpoint, event and outbox. Real PostgreSQL coverage verifies a blocked Program lock, timeout without writes and retry. The decision gate remains closed: transaction-time authority and OIDC session proof, current-route receipt, and routed recovery remain outstanding.
