# Archer Requirements Cross-Check

**Reference data — not legal advice.** This document records how the requirements in the supplied `Fidelity Bank_Archer (1).xlsx` workbook relate to ClearSight capabilities as of 24 September 2026. It is a scoping and planning aid for bank stakeholders. It does not assert that ClearSight, or the bank's use of it, achieves compliance with any law, regulation or framework. Status labels describe ClearSight's documented and implemented capability, not the bank's outcome.

## How to read the statuses

- **Covered** — ClearSight has a documented use case and implemented workflow that satisfies the requirement's business outcome.
- **Partial** — a material part is covered now; the remaining part is tracked as a bounded extension.
- **Blueprint** — the underlying use case is documented in the catalogue and architecture is supported, but the required depth is not implemented in the current release.
- **Gap** — no current ClearSight use case or implemented workflow satisfies the requirement; a new capability would be required.

The `UC-###` identifiers link to [`use-case-catalogue.md`](use-case-catalogue.md). Catalogue entries marked **Expansion** or **Enterprise** are documented and architecture-supported but not implied as implemented in the first release; the rows below state which part is implemented today.

## Correction history

- **24 September 2026:** An earlier version of this cross-check described the #28/#29 implementation as a covered “central ROPA population with audit and role-scoped access.” That statement was inaccurate at the time: `ROPA-CURRENT` was a Program requirement, and `ROPA-COVERAGE` was an evidence contract whose population was the JSON label `active_processing_activities`; no processing-activity records existed. The current rows below describe the register implemented since that correction and do not carry the earlier claim forward.
- **24 September 2026:** #21 was previously marked **Covered** from a documented, unchecked journey. The separate PIA-screening aggregate and DPO-routed workflow are not built, so #21 is recorded as **Blueprint** rather than treated as implemented capability.

## Implementation note

The register is implemented in [`internal/ropa`](../../internal/ropa), with its schema, scope constraints and immutable-history triggers in [`migrations/000092_ropa_register.up.sql`](../../migrations/000092_ropa_register.up.sql). The scope and deferred Tranche 2 work are recorded in the [ROPA design](../superpowers/specs/2026-09-23-ropa-register-and-reporting-design.md) and [Tranche 1 plan](../superpowers/plans/2026-09-23-ropa-register-and-dashboard.md); the design's correction section records the pre-tranche baseline, while the current code and migration implement the later tranche. The existing system-activity CSV/NDJSON export is separate from #26's configurable exception/compliance report builder. This note records code and test implementation, not rendered or behavioural acceptance: acceptance evidence for `UC-PRIV-01` and `UC-REPORT-01` has not been produced.

## Relationship to current work

- Requirement 17 overlaps the Branch KRI register work ([design brief](../design/2026-09-22-typed-response-display-and-branch-kri-register-design.md)). The seeded branch register now holds one response per branch instead of duplicated rows, so location-owned KRI updates and new indicator events are supported; the remaining gap is per-branch parameter and threshold configurability.
- Requirements 21/22 remain separate privacy work: the PIA-screening and DPIA-register aggregates are not built by this ROPA tranche, although the programme's DPIA journey is documented. A maintained DPIA register and go-live closure gate remain open.
- Requirements 26, 28 and 29 now have a code-implemented ROPA register foundation. The separate system-activity CSV/NDJSON export is not a configurable ROPA report builder; automated review cycles/reminders and collaboration notifications remain deferred. Rendered and behavioural acceptance evidence for the ROPA surfaces has not been produced.
- Requirements 5, 9 and 30 are deliberate gaps: certificate recertification tracking and central consent management are not in the current release scope and are not implied anywhere in the product catalogue. The separate breach register (#24) and DPIA register (#22) are also not built.
- This cross-check is reference data for scoping, not a legal or compliance statement. Statuses are snapshot on the stated date and change as use cases are implemented.
