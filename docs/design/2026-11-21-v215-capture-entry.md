A direct email-verified invitation sends a code only after the recipient opens the request and the server returns exactly one recipient. A delivery failure retains that recipient and offers a manual retry. Ambiguous direct recipients and duplicate invitation parameters fail closed. Invitation fragments are removed before capture opens. Session, request, distribution and assurance must match the returned workspace during initial access and conflict recovery; unsupported question types continue to block submission. A verified code followed by an unavailable or mismatched workspace reports the request unavailable rather than asking the recipient to reuse a consumed code.

Fixtures do not establish real email delivery, server authorization, backend scope, screen parity, dark-theme behavior or production acceptance.

The production access endpoint deliberately returns the same generic failure for an invalid, expired, exhausted or unavailable challenge. Therefore the interface cannot truthfully distinguish expiration from exhausted attempts. It offers code verification retry or a request for another code, subject to server controls. `TestDistributionAccessOTPFailureContractAndRecovery` verifies indistinguishable service failures and recovery after expiration, while the routed HTTP regression in `TestVendorWorkHandlersUseVerifiedRelationshipAndReturnTruthfulDeliveryState` verifies identical no-store 401 responses for wrong, exhausted, consumed and unknown challenges. The old expired/exhausted status codes existed only in static fixtures and are not emitted by the production handler.
