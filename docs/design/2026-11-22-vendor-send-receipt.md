# Vendor assessment request receipt

Sending an assessment request can prepare the request before invitation delivery completes. The UI now confirms the assessment and vendor scope, pinned form, request origin and deadline before presenting the returned delivery state. A prepared request with no issued access remains distinct from a delivered invitation. No capture token or secure link is displayed. A send error may occur after preparation, so the form requires an assessment reload before another attempt; access-denied responses clear the assessment and require a fresh scoped read.

Synthetic form, unconfirmed-receipt and prepared-without-access states are retained in `docs/evidence/2026-11-22-vendor-send-receipt/` at 1440, 768 and 390 pixels. The evidence script checks that an unconfirmed submission cannot be resent and that each state avoids horizontal overflow. The preceding vendor detail baseline is in `docs/evidence/2026-11-22-vendor-completion-receipt/`. These fixtures do not establish real email delivery or production authority. Legacy vendor request and due-diligence suites remain until their other material scenarios are migrated.

An invitation ID alone does not prove email delivery. Both initial requests and clarification requests now return `DELIVERY_UNKNOWN` for that inconsistent stored state; the UI requires a reload and does not label either request sent. Synthetic clarification delivery-unknown states are retained at all three widths.
A reported delivery is shown as sent only when its delivery receipt has a valid delivered status and timestamp. An invitation with a failed or uncertain email outcome is described as delivery not confirmed, including replacements and clarifications. The retained evidence includes that state at each viewport.
