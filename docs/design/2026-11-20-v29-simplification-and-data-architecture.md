# ClearSight 2.9: friction, simplification and data architecture

**Status:** Proposed design, 20 November 2026. This document extends the [replacement and debloating plan](2026-11-20-v29-rewrite-and-debloat-plan.md). Recommendations are design decisions to validate, not claims of implemented behavior. Preserve the dirty working tree recorded in the parent plan.

## 1. What simplification means

Make routine work require fewer questions, handoffs, duplicated records and inconsistent screens. Keep a single accountable owner for each business fact, decision and artifact. Derive views and counts from that owner, and add storage or workflow machinery only for a distinct durable business requirement. Maintain verified identity, scope, independent authority, source provenance, immutable material history and outcome verification.

The 2.9 reference is the requested experience authority. Its visual composition and purpose guide the target; do not reproduce synthetic actor switching, sample values or prototype-local persistence. A reference field or step that repeats known data is a candidate for prefill or progressive disclosure. Resolve changes to the reference flow explicitly in the domain brief, preserving its visual language and the user's intended outcome. No review or evidence requirement is removed merely to improve a click count.

The repository's existing [ease-of-use standard](../product/ease-of-use-standard.md) already calls for routine tasks within five minutes of active effort, a saved and correctly routed next state within five minutes for complex work, source-backed prefill, focused questions and one next action. These are acceptance objectives to measure with representative users, not results already achieved.

## 3. Friction register and design response

The reference remains the layout benchmark; the following responses are proposed task-level adaptations, subject to domain review and rendered verification.

| Priority / friction | Simplified task design | Guardrail and measurement |
| --- | --- | --- |
| P0: Re-entering entity, branch, owner, vendor, control or evidence already known in context. | Carry authorized context into the destination; look up exact existing records first; prefill sourced values and show only unresolved or changeable fields. One explicit correction path for an incorrect source. | Do not silently infer an owner, legal scope or legal conclusion. Measure repeated entries per journey and source-lookup latency; verify redaction and stale values. |
| P0: User must choose among modules or repeat navigation to act on an assigned item. | One Work entry opens the exact source record and the permitted current action, with return to the filtered queue. Home, Inbox and reports link to that same task/source; they are not separate queues. | Source and current authority are rechecked; a notification being read does not complete work. Test direct link, Back, reload, changed authority and deleted/inaccessible source. |
| P0: Manually choosing an approver for every routine submission. | Resolve the current route from scope, role, position, materiality, conflicts and delegation; show the proposed responsible route and gaps. Ask for human selection only when policy permits a real choice. | No hard-coded approver or implicit approval. Missing/ambiguous route blocks the material command with a recovery path; reroute on changed authority. Measure manual routing decisions and blocked-route recovery. |
| P0: Complete questionnaire for a narrow evidence need. | Search current authorized evidence and prior responses, carry provenance, and request only missing/stale/contradictory fields; reuse a suitable response where policy allows. | A previous upload or response is not accepted evidence or an approved conclusion. Test expiry, access loss, rejection, source version changes and separate reviewer acceptance. Measure questions asked and repeated uploads. |
| P1: Loss capture requires all classifications and detailed investigation before a user can save. | Save a scoped draft with the minimal stable facts; progressively request financial and investigation fields for submission. Prefill date/scope only when sourced; make risk link optional. | A draft is excluded from accepted totals. Required recognition/reporting distinctions, duplicates, financial precision and independently reviewed decisions remain mandatory at their relevant transition. Measure time to saved draft and return rate. |
| P1: A reviewer has to reconstruct what changed across submissions. | Open the exact submitted revision with changed fields, pinned sources, current authority and a single decision area. Keep prior accepted facts visible during a correction. | Difference view must not replace access to full source or permit stale approval. Test concurrent changes, revoked evidence and returned/resubmitted work. Measure navigation and active review time. |
| P1: Separate intake, review, recovery, action and reporting experiences make a loss hard to follow. | One loss record exposes the current financial state and the actor's next valid action; deeper tabs/links show evidence, cash ledger, action and history. Use exact-source Work links. | Financial acceptance, cash verification, action completion and outcome verification stay separate; no closure or correction silently updates another conclusion. |
| P1: Every governance configuration is exposed as a large matrix at once. | Start with role/policy purpose, scope and effective route; progressively disclose detailed grants, exception windows, simulation and impact. Reuse templates and explain only actual policy conflicts. | Maintain all configured distinctions, simulation, maker-checker, effective dating, rollback and audit. Do not replace authorization with a simplified client-side role matrix. |
| P1: Inbox and Work duplicate attention and create notification noise. | Show actionable source work in Work; Inbox retains recipient messages and read/acknowledgement state. Group repeated notifications by exact source and version when doing so preserves required notices. | Delivery, read, acknowledge, snooze, source resolution and completion are different facts. Mandatory notifications cannot be suppressed; recheck source visibility before rendering protected content. |
| P1: Reports require re-creating filters and manually assembling source facts. | Start from authorized source-backed perspectives, preserve scope/date and disclose distinct date bases; let a prepared pack capture one immutable source boundary and editable management narrative. | Distinguish a live view, an export run and a published pack; do not claim unsupported totals, mix currencies or silently refresh a published pack. |
| P2: Duplicate summary cards, default tabs, long descriptions and nonfunctional controls crowd first view. | Keep the reference hierarchy but show only decision-relevant verified information and one dominant next action; remove repetitive copy and hide unsupported operations until a valid recovery path exists. | Never hide required limitations or unknown coverage. Test first useful content, partial/denied states and 390–1440px layouts. |
| P2: A long flow loses progress or forces a restart after a conflict. | Autosave bounded drafts where appropriate, offer save/exit, restore route and source context; on conflict show changed facts and allow an authorized rebase. | Drafts carry scope, owner, version, expiry/retention and access controls. Saving is not submission; never auto-merge a material decision or silently overwrite another user. |

Set actual baseline values in discovery. Instrument consented, privacy-safe timings and counts without recording invitation tokens, protected content or personal responses. For each task collect number of fields asked, repeated facts, navigations, authority choices, saves, returns, time to a saved next state and completion/return rate. Compare the same actors and scenarios before and after; do not optimize by removing necessary checks. Apply the existing five-minute objectives, investigate failures and record exceptions for inherently complex work.

## 4. Simplified ownership model

The recommended default is the existing modular monolith and one authoritative PostgreSQL database, with the existing API, worker, object storage and transactional outbox. Do not introduce microservices, an event broker, a separate workflow engine, event sourcing everywhere, a second ledger or a new generic entity framework merely to implement 2.9. Split workloads only after measured capacity, isolation or regulatory requirements justify it.

| Fact or capability | Preferred owner | Other surfaces consume | Avoid |
| --- | --- | --- | --- |
| Principal, position, scope, permissions, delegation and route | Existing identity, organization and authority modules | Shell context, domain commands, Work visibility | Frontend role truth or a second 2.9 access-control store. |
| Program, requirement, control implementation and material operating history | Existing continuity / Program owners; catalog owns shared definitions/links | Frameworks, controls, assessments, reporting | Copying controls per screen or treating a catalog definition as an implementation or test result. |
| Reusable form definition, assignment, capture and immutable response | Existing monitoring / form / evidence capture contracts | Assessments, vendor collection, branch returns, RCSA | A separate questionnaire engine for every screen. Extend only where question types or submission semantics truly differ. |
| Evidence request, artifact version, inspection and review | Existing evidence and document owners, with exact source permissions | Programs, controls, vendors, privacy, losses | Upload copies or independent acceptance flags per consumer. A link does not grant access. |
| Risk and RCSA membership, assessments and challenge | `internal/risk`, `internal/rcsa`, plus existing form and Matter links | Risk, RCSA, Work, reporting | A separate local risk rating or duplicated RCSA cycle. |
| Loss and financial events | `internal/oploss` as evolved by the financial-lifecycle design below | Loss register, Work, loss insights, reports | Prototype-local drafts/ledger as a second source, direct total editing or an inferred verification decision. |
| Vendor identity and relationship | Existing vendor / `internal/thirdparty` owner | Vendor review, forms, evidence, reports | A lifecycle-specific copy of vendor identity or duplicated assessment truth. |
| Current executable work | Existing workflow projection extended by explicitly supported source kinds | Home, Work, source detail | A second generic task queue or treating projection rows as authority. The source command owns completion. |
| Decision and authority | The owning domain's decision and the existing governance / authority contracts as applicable | Review, activity, reports, audit | A generic approval record that independently changes the domain or a Matter created for every simple review without a domain reason. |
| Notification and recipient receipt | Existing notification delivery/receipt owners | Inbox and badge | Equating read/archive with source completion, or storing a second mutable copy of the source state. |
| Live metrics / historical reporting | Existing bounded metric and reporting owners | Home, Insights, Reports | A dashboard-specific ledger, source-wide in-memory authorization, separate untraceable counts or an expensive permanent snapshot for every view. |
| Files and durable report artifacts | Existing artifact abstraction and versioned object storage | Evidence, source review, report downloads | Storing file bytes repeatedly in business rows or granting access through a copied attachment. |

### Use the lightest correct data representation

- **Current fact:** one indexed, scoped current row owned by the domain. Material changes are versioned and events retained where the existing contract requires them.
- **Draft:** a versioned, scoped, access-controlled draft only if resume or collaboration is required; do not put unfinished facts in the accepted row. Keep a base version, bounded payload and an explicit expiry/retention rule. Submission records an immutable basis and validates it again.
- **Decision:** keep a distinct receipt when a decision has independent authority or historical meaning. Include decision, actor from verified context, time, policy/route version, exact subject/version and rationale when required. Reuse an existing governed decision mechanism when it supports those semantics, rather than creating a generic approval framework in advance.
- **Work:** a derived, idempotent task projection of the owning source. Define typed source identity, source revision, actor visibility, current routing, stable deduplication key and reproject/cancel rules. A projection must be rebuildable and may be stale; command execution always reads current authority and source.
- **Notification:** a recipient-scoped delivery/receipt pointing to a source and optionally a source revision. Keep only delivery and recipient state there. Authorize the source at read/open time.
- **Metric:** a bounded authorized query by default. Persist a projection only when query cost, cross-domain consistency, source-membership drilldown or temporal reconstruction requires it; specify source version, coverage, freshness, deduplication, retention and repair. Do not precompute every card separately.
- **Snapshot:** use immutable retained source boundary and artifacts for published decisions/board packs. A temporary export, a cached live metric and an approved/published pack have different retention and authority; do not conflate them.

## 5. Loss workflow: concrete target and migration

### Existing behavior and mismatch

The current `Loss` has one current `ACTIVE` or `VOIDED` row, a versioned snapshot and event history. A recovery or reversal is an immutable positive minor-unit entry; `AddRecovery` validates version/currency/limits and immediately includes it in the derived recovered amount. Existing readers and metrics therefore cannot safely assume that a historical entry carries independent review merely because it exists. The 2.9 reference instead requires draft, submission, independent acceptance/return, correction, receipt verification/reversal and closure with accepted-only reporting. These must be reconciled, not overlaid in React.

### Proposed minimal model

Keep `internal/oploss` and the existing scoped loss identity. Design an additive migration and service contract around:

1. A **draft/proposed revision** attached to a loss identity, with base accepted version, author, draft version, source metadata and bounded draft values. Permit incomplete draft fields without weakening submitted/accepted validation. Define one active proposal per loss unless a reviewed use case requires parallel proposals.
2. A **submitted immutable basis**, including exact financial and source facts, classification, currency, distinct occurrence/discovery/recognition/reporting dates, source references and required action treatment. Submission resolves the review route from the current policy; it does not change accepted totals.
3. An **independent decision receipt** bound to that submission and route version. Accept promotes the submitted facts atomically to the current accepted loss version; return keeps prior accepted facts and starts or resumes a linked correction. Recheck source, scope, authority, conflicts and expected version inside the material transaction.
4. A **recovery proposal and decision** using the existing loss financial ledger as the durable owner. A pending receipt or reversal reserves capacity according to a documented concurrency rule but does not change verified totals. Only an independent acceptance appends or activates an effective immutable financial entry; reversal references the exact original receipt and effective date. Lock the relevant loss/ledger state and enforce aggregate limits in the same transaction.
5. **Closure/reopening** as a reviewed, versioned lifecycle distinct from financial write-off and action completion. Preserve open-action/residual treatment and previous closure episodes. Determine whether an existing governed decision can represent each receipt without adding duplicate state.

This is a logical model, not a final SQL schema. Design foreign keys, immutable constraints, indexes, transaction ownership, outbox and job requirements in the domain implementation plan. Verify exact proposed lifecycle against policy and existing workflows before changing tables.

### Legacy migration and deployment

- Inventory production counts and values by scope, status, currency, recovery kind and version before migration. Take a restorable backup and record schema/data revisions and the current report definitions. Reconcile totals per currency and exact record before and after.
- Do **not** synthesize an independent decision or reviewer for historical `ACTIVE` losses or recoveries. Assign an explicit legacy/unreviewed provenance and preserve existing facts. Decide and document, with authorized business owners, whether legacy facts remain in a separately labelled historical reporting cohort, require remediation, or have an evidenced existing approval basis. The default until that decision is resolved is to avoid labelling them newly reviewed or including them in a reviewed-only cohort.
- Introduce additive reads and schema first; deploy compatible readers and review commands behind controlled routing. Coordinate old writers: block or upgrade direct loss/recovery mutations before claiming the new acceptance invariant. Backfill only sourced fields; unknown recognition/reporting dates remain unknown. Avoid dual authoritative writes.
- Verify prior accepted/historical cohorts, pending exclusion, reversal references, race conditions, zero/near-miss treatment, original currencies and large integer limits. Every report must identify its inclusion rule and source version. Reconcile live loss views, metrics, drilldown and captured pack to the same cohort.
- Rollback before enabling new writes may revert application routing and additive schema. After new decisions or financial events exist, roll forward or use a tested compatibility reader; never delete new history to downgrade. Retain old data and explain any reporting-basis change. Define the exact deployment gate and rollback proof in the loss tranche.

## 6. Domain simplifications and dependencies

1. **Forms → RCSA and KRI:** inspect whether existing form versions, distributions, response revisions and draft policies cover branch return questions and per-risk RCSA draft/resume. Extend form contracts with typed source references and version guards only where needed. Keep the cycle's frozen membership in `rcsa`; do not duplicate answers into a separate authoritative cycle store. Test definition changes, N/A, source coverage and independent challenge.
2. **Controls → Programs and RCSA:** map reference control definition, implementation, operating test and effectiveness to `controlcatalog` and Program implementations. Reuse identity and links where semantics match. A test must bind the implementation version, and a changed definition must not inherit its prior current conclusion. Add a new test-result owner only if existing assurance objects cannot represent it; do not overload a generic approval as a control test.
3. **Vendor review → existing relationship and evidence:** re-use relationship identity, form submissions and evidence sources; add a versioned lifecycle decision only for missing independent activation/review/suspension/exit transitions. Select existing evidence and display freshness instead of requesting the same certificate again. Separate vendor lifecycle state from assessment and assurance conclusions.
4. **Privacy → ROPA, cases and impact:** map each reference journey to `ropa`, protected Matter/case and document capabilities. Reuse common workflow primitives without forcing sensitive case data into general Work or inventing a new privacy store by default. Restricted source metadata must remain filtered even in notifications and counts.
5. **Work/Inbox → source adapters:** first list supported source kinds in the actual current query and projection code, including evidence and any newer adapters beyond the architecture document. Extend projection/read filtering and source commands in the same slice. A reference review enters Work only when its source grants access and a current executable action exists. One source transition drives task reconciliation and notification resolution; duplicates and event replay converge.
6. **Reports → live query, export, pack:** inspect subsequent report migrations and worker implementations before choosing reuse. A board pack needs durable snapshot membership, source definitions, dates, management narrative and artifact retention; if existing runs cannot meet that contract, extend reporting with a clearly owned published-pack aggregate. Do not require a new governed report definition merely to open an authorized live view; maintain approval where a policy requires publication or configuration approval.
7. **Administration → shared policy machinery:** map the 2.9 role matrix and escalation editor to real identity, scope, authority, delegation and automation policy contracts. Reuse simulations and versioned maker-checker lifecycle; expose a concise task-first view while retaining the detailed policy and impact preview. Do not implement 48 independent client-only permissions as a replacement for server authority.

## 8. Execution, verification and gates

### Discovery deliverables before engineering

1. **Route/action inventory:** enumerate all 67 reference entries and every current route, including nested Configure, external capture and old notification links; for every enabled action record exact source, command, actor, expected version, result, unsupported state and target. Mark facts verified in source separately from assumptions and tests still needed.
2. **Friction walkthroughs:** run representative loss recording/review, evidence reuse, RCSA, vendor review and board reporting with authorized fixtures; record baseline measures from §3 and the first failure to reaching a saved state. Include preparer, independent reviewer, owner and authorized reporting user, plus an access-denied/degraded scenario.
3. **Data lineage map:** trace selected records through HTTP route → verified actor and authority → service → repository transaction → event/outbox → Work/notification projection → metric/report → artifact. Record all writes and consistency boundaries; audit existing indexes and data shape with bounded queries on sanitized representative data.
4. **Architecture budget:** measure initial and lazy bundle, CSS, route request counts, p50/p95 time to useful content and command/read latency, DB query plans, projection lag, worker backlog and test duration. Define realistic targets after baseline and production-volume estimates, preserving existing performance SLOs.
5. **Decision briefs:** publish one per domain with exact current/source mapping, proposed contract and schema, removal list, data migration, retained capability, risk, acceptance scenarios and named owner. Identify which changes to reference flows reduce repeated effort and why.

### Slice gates

- **Design:** source/runtime same-screen comparisons, full page anatomy and reference hashes; responsive replacements and task-focused copy; evidence-backed friction improvements.
- **Behavior and security:** positive, stale, partial, denied, concurrency, revocation, delegation, cross-tenant, source-access and recovery cases; actual server commands and exact source return. A control cannot claim success from client state.
- **Data:** transaction and idempotency tests on PostgreSQL, audit/event/outbox atomicity, provenance and point-in-time reconstruction, source-to-report parity, legacy reconciliation and rollback/roll-forward rehearsal. Inspect policy and semantics before removing a distinct durable record.
- **Usability:** measure real active effort for representative actors against the existing five-minute standard; retain the reason and recovery for any unavoidable extra step. Verify keyboard, accessible names, touch targets, reduced motion and error states at 1440/1280/1024/768/390.
- **Operational:** bounded queries and cardinality, permissions before limit, worker retry/replay and lag, graceful unavailable dependencies, observed bundle/performance budgets, no protected data in logs, and migration monitoring. A green UI test does not prove production outcome or acceptance.

### Open decisions requiring evidence

1. Which existing legacy losses and recovery entries have independently verifiable acceptance evidence, and how should each reporting cohort be labelled? Do not change historical totals or manufacture decisions without a bank-approved migration policy.
2. Which reference actions are genuinely independent approvals under the bank's policy and which are ordinary saves, checks or notifications? Apply the current versioned route and segregation rules; do not hard-code a universal approval chain or remove a required authorization to save clicks.
3. Which current source kinds and document artifacts are already supported by Work, review and reporting in the actual deployed revision? The code and schema inventory must precede reuse claims.
4. Which prototype fields are mandatory for the bank's actual loss, KRI or control process, and which can be sourced, deferred or conditional? Preserve 2.9 objectives and document intentional task-flow adaptations.
5. What are actual population sizes, concurrency, observed latency and supported deployment capabilities? Use measured data to decide whether a projection, index, job or storage change is necessary; avoid premature infrastructure.
