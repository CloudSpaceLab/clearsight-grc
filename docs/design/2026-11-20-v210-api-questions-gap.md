# Live API questions: implementation gap and delivery plan

Status: **not implemented**. A v2.10 form question cannot yet be configured as a governed, executable API check. The existing local validator `web/src/apiCheckSample.ts` checks examples only. It neither contacts an endpoint nor saves, approves, runs or connects a check. It must not be presented as a live integration.

The stateless `sourceaccess.QuestionTester` can validate a sample without network access or inspect an unauthenticated public HTTPS endpoint with a bounded GET, returning only validity and timestamp. Sample, live and singleton question reads reject duplicate response fields and invalid UTF-8 before interpreting a result. Its test transport denies private, link-local and special-use destinations, rejects mixed public/private DNS answers, dials the validated IP directly and verifies the connected peer; ambient proxies are disabled. This is public-network egress only. Private bank APIs require a separately governed and verified network policy; they cannot be enabled by a form field. The existing general catalog REST adapter retains its previous transport and does not itself enforce these restrictions; do not route new live question tests through it without an approved destination policy. The tester has no credential support or catalog integration and must not be exposed as an active check. The exported constructor always uses the restricted transport; custom transport injection is package-private for controlled tests. No test result creates an observation or assessment.

The live format test reports a successful HTTP response with malformed JSON, trailing JSON or a non-JSON content type as an invalid response format. HTTP failures, timeouts, blocked destinations and oversized bodies remain unavailable. Its checked timestamp is recorded after the endpoint request completes. The test does not return the response body or interpret either outcome as an assessment decision.

The independent `web/src/v210/APIQuestionSample.tsx` component validates a sample locally and explicitly identifies that no endpoint was contacted. It is not mounted in the application while question configuration and the live test remain unavailable. The local validator rejects duplicate top-level keys and enforces the same 64 KiB input bound as the service; it does not contact an endpoint or establish approval or execution readiness.

The test-audit foundation defines a reservation before an endpoint call and an immutable result after it. The PostgreSQL store serializes attempts across instances per legal entity, using the database clock and limits of ten per principal and sixty per entity in a rolling minute; the in-memory implementation exercises concurrent reservations for non-production tests. Audit entries hold only scoped identifiers, authority route/version, mode and outcome, never endpoint, response, sample or credentials. Migration `000142_api_question_test_audit` provides the audit tables and refuses rollback when audit records exist. The [registered format-test endpoint](../../api/form-question-tests.md) checks the verified person, exact entity-scoped draft, question and enforced form-owner authority, reserves before running, and refuses a successful response if the outcome cannot be audited. It rejects body-supplied identities and duplicate request fields. It does not create a binding or observation. PostgreSQL 18 integration verifies the migration and concurrent limit against two store instances in an isolated schema. Audit retention, partitioning and capacity limits still require an approved operational policy before rollout; live tests remain restricted to public unauthenticated HTTPS.

## Verified current behavior

- The REST adapter accepts a singleton JSON object containing `result` as a boolean or finite number and an optional bounded string `message`. Other properties are rejected (`internal/sourceaccess/rest_json_read.go`, `rest_json_question_contract_test.go`).
- `web/src/sourceConfigApi.ts` creates a Source, Connection and View in separate commands before inspecting a real endpoint; a later failure can leave drafts behind. The helper now returns known committed draft identifiers in a sanitized error and does not create a redundant reference connection; unknown outcomes still require lookup before retry. API-question endpoints reject query strings and fragments. It configures unauthenticated connections and does not provide an atomic creation receipt or safe cleanup.
- A newly created Binding is a draft. Source catalog lifecycle transitions and maker-checker services are not implemented, as recorded in `docs/architecture/connected-source-access.md`. A draft must not be represented as an approved or running check.
- Capture requests have exact Binding references, but `internal/formcontract.Field` and `web/src/monitoringTypes.ts` do not model a form-template question binding. `web/src/v210/Capture.tsx` currently blocks questions with source bindings. Neither an existing request binding nor a source inspection establishes a reusable form-question configuration.
- The adapter can use secret references; the convenience creator accepts only `authentication: NONE`. There is no tested v2.10 setup flow for selecting a protected credential reference, and no current UI action should collect a password or token.

## Proposed contracts

These are proposed contracts, not current endpoints. Final schemas must be recorded in `api/runtime.openapi.json`, and every command must use verified identity, scoped authority, optimistic concurrency and one transaction for authoritative records, events and outbox.

1. **Create a versioned check draft.** `POST /api/v1/forms/templates/{form_id}/revisions/{version}/api-checks` accepts an `Idempotency-Key` header and `{field_id, name, endpoint: {origin, path, fixed_query}, result_type: "BOOLEAN"|"NUMBER", credential_ref?, freshness_minutes}`. Return `{check_id, version, status:"DRAFT", template_id, template_version, field_id}`. Resolve the exact form revision and field within the verified entity. Reject URL userinfo, fragments and credentials in query values; never accept request headers, bearer values or unrestricted request templates. Validate and connect destinations under a governed network policy; the public-only question test transport is a starting point, not a policy for private bank endpoints. The idempotency key is bound to actor, entity, action, template revision and a canonical request digest; identical retry returns the original receipt, while a different body conflicts.
2. **Test without recording an observation.** `POST /api/v1/forms/api-checks/{check_id}/tests` accepts `{expected_version, mode:"SAMPLE", sample:{result,message?}}` or `{expected_version, mode:"LIVE"}`. SAMPLE validates the supplied JSON in a bounded process without network access, writes no Source observation or assessment result, and returns only `{mode, valid, errors[]}`. LIVE performs one bounded GET against the saved draft using server-side credential resolution; return `{mode, outcome:"VALID"|"INVALID"|"UNAVAILABLE", checked_at, result_type, errors[]}` and a minimal audit receipt, not raw response body, secret, authorization header, URL query or a compliance conclusion. Test requests cannot mutate the form, create a passing result, schedule a check or bypass endpoint policy. Rate limits, timeout, response size, redirect, DNS rebinding and destination restrictions apply identically to runtime. A failed test never implies a failed control.
3. **Review and activation.** An exact draft may be submitted with version and rationale for independent approval. Preview the impact on assigned form revisions and existing assessments; capture conflicts, delegation and the governing authority route. Approval by an eligible checker creates an effective-dated Connection/View/Binding revision and a pinned form-question association atomically. Preserve prior revisions, maker/checker, policy versions, simulation, impact, rollback and audit. Commands must fail closed on missing routes or stale versions. Do not activate through a UI-only state.
4. **Execute.** A form assignment pins the approved check and Binding versions. The existing runtime/monitoring owner performs bounded, idempotent reads and stores observation, timestamp, source revision, completeness and execution receipt separately from human answers and reviewer decisions. Timeout, schema drift, stale data and missing authorization yield an explicit unknown/unavailable state; none implies a passing requirement. Local or test-mode inputs must never enter production observations.
5. **Cancel, cleanup and recovery.** `DELETE /api/v1/forms/api-checks/{check_id}/draft?expected_version=N` cancels an unapproved draft only when the server proves no external references or effective revisions exist; audit the cancellation and schedule bounded cleanup of draft-only backing resources. Do not delete shared Sources, immutable revisions, observations, submitted answers or approved configurations. A periodic leased cleanup job can expire abandoned unreferenced drafts under a documented retention policy. Show committed creation receipts if a derived inspect or cleanup later fails; an uncertain client must look up the idempotency receipt before retrying.

## Data changes

Add a relational API-question configuration owned by the form domain: tenant/entity IDs, stable check ID, exact template ID/version and field ID, result type, draft version/status, referenced Source/Connection/View/Binding revisions, freshness policy, maker/checker, effective interval and audit timestamps. Use foreign keys and exact entity-scoped indexes; add uniqueness for an effective field/configuration and idempotency receipt. Store credential **references only** using the existing protected secret mechanism; no raw credentials, endpoint query secrets, sample payloads, invitation tokens or access tokens in form rows, logs, analytics or fixtures. Existing form versions and immutable submissions remain untouched. Use an additive migration and an idempotent backfill only for previously approved, provably scoped configurations; otherwise leave the association absent. Rollback must preserve any approved configuration and review history.

## UI and verification

The v2.10 question configuration should expose answer type, HTTPS endpoint, a separately selected authorized credential reference, freshness and a sample JSON editor. The sample action is labelled **Test sample** and explicitly reports that the endpoint was not contacted. A distinct **Test endpoint** action calls the bounded LIVE test and labels its timestamp; an unavailable endpoint is not a failing assessment. The draft, approval state, version and any inability to submit for approval are visible. A checked example, successful inspection or locally stored endpoint must not be called an active integration.

Required tests include typed `false` and numeric zero, malformed/extra fields, bounded messages, rejected credentials in URL, prohibited destinations and redirects, DNS rebinding, response limits and timeout; immutable form revision and tenant/entity isolation; unauthorized credential references and secret redaction from logs/receipts; duplicate concurrent creation, same-key/different-body rejection and lost-response retry; partial creation and cleanup recovery; maker-checker conflict/delegation/revocation/effective dates; no live call or observation from SAMPLE; exact revision pinning and stale/conflicting approval; runtime unknown/stale/schema-drift handling; and no assessment conclusion from a technical observation. Run HTTP, service and PostgreSQL integration tests with the migration; add keyboard and responsive evidence for the complete configured, denied, draft, test-failed and approved states. No production cutover until these checks and a real authorized end-to-end flow pass.
