## Creation gap

The existing `AssessmentDeficiencyService.CreateDeficiency` authorizes the exact assessment and uses a stable trigger key, but creates the Matter and links it to the assessment in separate calls. `continuity.PostgresRepository.CreateMatter` and `thirdparty.PostgresRepository.LinkAssessmentDeficiency` each start and commit their own transaction. A link failure invokes best-effort reconciliation and compensation; a crash or compensation failure can leave a committed unlinked Matter. This does not satisfy the contributor requirement that a material command, authoritative changes, append-only events and required outbox work share one transaction. The v2.10 UI therefore withholds creation despite the existing endpoint.

To enable creation safely, introduce a compound deficiency command that resolves verified identity and the current reviewer route, derives the restricted Matter scope and canonical trigger key, and rechecks the current assessment version, review state, relationship and routing at execution. The Postgres implementation must use one `pgx.Tx` to insert the Matter and its continuity event/outbox, create or verify the canonical relationship link and assessment-deficiency link, update the assessment version, and insert the assessment event/outbox. Expose transaction-aware continuity insertion as a shared contract rather than copying event construction or opening a nested transaction. A stable trigger key must reconcile retries to the same exact Matter without accepting mismatched actor, entity or assessment. An unknown commit outcome must be resolved by exact bounded lookup; do not report failure after a confirmed commit.

The memory implementation requires a corresponding compound operation across the Matter and assessment stores with deterministic lock ordering and staged validation before mutation. It must either publish all authoritative records and events together or leave all unchanged; compensating events are not a substitute. Preserve existing Matter visibility and event consumers. The existing schema's trigger and relationship-link constraints should be verified before deciding whether a migration is necessary; any new index must be idempotent and tenant/entity scoped.

Required tests cover unauthorized and revoked reviewers, wrong tenant/entity, stale assessment, invalid state, duplicate trigger replay, mismatched replay payload, concurrent version changes, and failures after each row/event/outbox write and at commit. Assert that a failure leaves no partial Matter, relationship link or assessment event, and that a committed-but-unconfirmed response reconciles to one result. Run both memory and real PostgreSQL tests with a configured integration database, plus the existing review/read and event-projection regressions before exposing an enabled creation action.
