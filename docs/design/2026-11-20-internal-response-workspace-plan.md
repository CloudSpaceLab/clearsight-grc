# Authenticated internal form responses

**Status: partial implementation; assignment action remains unavailable.** The new `FormAssignment` component is not an end-to-end assignment flow until the release gate below is complete. This document does not authorize an external capability route to be created for an employee.

Internal-assurance provenance and guarded migration `000141_internal_response_assurance` are implemented. Memory and PostgreSQL operations recheck the named recipient, scope and current eligibility under locks, and persist actor-attributed revisions, audit events and outbox events. PostgreSQL integration tests cover submission concurrency, rollback on outbox failure, and revocation of Program/Matter scope, positions and the directory eligibility chain. The reverse ordering is tested for Program/Matter scope, position and directory source. An in-memory HTTP handler test covers read, save, stale submit, forged identity fields and a successful response receipt. These handlers remain unregistered: the production material authority route, full HTTP-to-PostgreSQL and browser flow, remaining revocation interleavings and release checks below are not complete. The v2.10 respondent workspace and assignment components remain isolated.

## Existing gap

`POST /api/v1/forms/distributions` creates a named internal `TO` recipient, a request and a shared workspace. The authenticated `POST /api/v1/evidence/requests/{id}/submissions` handler calls `evidence.Service.Submit`: its memory and PostgreSQL repositories create an immutable capture submission and mark the request submitted, but do not create a `capture_response_revisions` row or the distribution workspace's versioned review history. It must not be presented as a substitute for the distribution submission operation.

`DistributionAccessService.GetResponseWorkspace`, `SaveResponseWorkspace` and `SubmitResponseWorkspace` produce the correct versioned workspace and revision, but accept an external bearer capability. `validateMemoryWorkspaceAccess` and `loadPostgresWorkspaceState` require a persisted, unrevoked external route and session. `insertPostgresWorkspaceSubmission` writes `MAGIC_LINK` with null `submitted_by`; `appendPostgresWorkspaceEvent` and `appendPostgresScoredResponseEvent` write null `actor_id`. An internal principal must not be represented by a fabricated route, token or external session, and a successful internal response must not be recorded as link possession or email verification.

## Contract and identity

Add authenticated routes to `internal/httpapi/form_distribution_routes.go`, separate from the `/api/v1/evidence/session/*` capability routes:

| Method and path | Input | Result |

Use `identity.Require` on every handler. Only a non-service verified principal in one explicit legal entity may proceed; derive tenant, entity and principal exclusively from that identity and ignore/reject body/query identity overrides. Do not accept a session token, principal ID or authority route from the browser. Return the same generic not-found/unavailable response for wrong tenant, entity, recipient, revoked/closed request and missing record. Apply `secureNoStore` to each route, do not log answer values or credentials, and retain the existing response body limits. A failed create/save/submit must not claim that a transaction failed if its outcome is unknown to the client.

Add `DistributionService.GetInternalWorkspace`, `SaveInternalWorkspace` and `SubmitInternalWorkspace` with a request ID and command payload only; obtain `identity.Actor` from context inside the service, not caller-provided fields. Introduce a distinct private `internalWorkspaceActor` or tagged `workspaceActor` containing the verified actor and exact request/recipient/distribution IDs. Keep the external `DistributionAccessSession` variant and its existing route/session validation unchanged. Never coerce one variant into the other. Use `RespondentRequest` to remove administrative/source internals before returning request data. Reuse `normalizeSaveWorkspaceInput`, `normalizeAttestationFieldIDs`, `validateWorkspaceAnswerSet`, `buildResponseRevision`, and the existing conflict response; add a distinct internal assurance value rather than mapping verified employee identity to `EMAIL_VERIFIED`.

`GetForRequest` can resolve an exact request to its distribution; it is only an initial lookup. Both stores must revalidate, inside the same locked operation that reads or changes workspace state: identity tenant and entity match the distribution, workspace, recipient and request; the recipient is an active internal `TO` whose `principal_id` is the verified actor; the request recipient names the same principal; the recipient's request ID is exact; distribution/workspace are open; request is ready or in progress and before deadline; the assignment and principal remain active; and the caller remains entitled to the assigned request under the existing subject-access policy. Deny missing services, ambiguous identities and every cross-tenant/entity match. Lookup and scope filtering belong in repository queries, not a broad load followed by browser filtering.

## Store changes and transactions

Extend the private `responseWorkspaceStore` and `workspaceAnswerValidationProvider` contracts with internal variants or refactor their arguments to an explicit discriminated `workspaceActor`. Implement the same checks and results in `MemoryDistributionAccessStore` and `PostgresDistributionStore`. At the PostgreSQL boundary add an internal variant of `loadPostgresWorkspaceState` that joins the exact distribution, workspace, internal recipient and request, filters by verified principal/tenant/entity, and locks those rows for PATCH and POST. It must not join `capture_access_routes` or `capture_distribution_sessions`. Recheck current assignment, request version and recipient state after locking. The memory implementation must perform equivalent checks while holding the existing store/repository locks, including on the final mutation, rather than trusting the earlier read.

For each save, run field validation and sequence conflict checks before writing. Persist each edit and workspace version plus the distribution audit event and outbox record in one transaction. For an internal submit, revalidate current request, source collection and artifact eligibility inside the same transaction; validate complete answers and attestations; write the `capture_submissions` row with channel `INTERNAL` and `submitted_by` equal to the verified principal; bind eligible artifacts; supersede the former current response revision; insert exactly one new revision naming the actual recipient and principal; update workspace version; append distribution event and scored event plus their outbox records; then commit once. Set distribution-event `actor_id` to the verified principal. Return the receipt only after commit; derived projections run through the outbox and cannot cause a committed submission to be reported as a failure. Mirror the same atomic outcomes in memory.

For internal submission use **exact workspace version equality** initially. Existing `memoryWorkspaceSubmitVersionUsable` and `postgresWorkspaceSubmitVersionUsable` allow a stale expected version only for contiguous edits from the same external session. Do not compare only principal IDs or allow two browser sessions belonging to one person to fast-forward each other's edits. A later session-bound fast-forward requires a verified, revocable authenticated-session identity and separate tests; it is not necessary for this implementation. Preserve external fast-forward behavior unchanged.

## Tests and release gate

### Outstanding authority and document boundary

The internal save and submit service methods require a server-configured performer authorizer. It resolves `EVIDENCE_REQUEST:{request_id}` for `forms.response.save` or `forms.response.submit`, checks the exact verified person and scope, and records the returned policy version and rule in the material audit/outbox event. PostgreSQL resolution uses the material transaction. Tenant slugs are reconciled with the scoped request lookup before authority resolution. These measures do **not** serialize changes to the authority route with the command.

An entity-level advisory lock exists for some governance operations, but authority can change through other policy, delegation, directory, role and principal changes. Before exposing internal commands, define the decision instant and concurrent-revocation semantics for the exact command, and implement a transaction-bound authority decision that meets them. Compare a single consistent authority snapshot or atomic decision-and-write with narrower record-level coordination where required; do not assume a tenant-wide writer protocol is necessary. Verify policy replacement, higher-priority route insertion, grant and segregation changes, delegated authority revocation, role and directory changes, principal suspension, concurrent commits, rollback and failure recovery with independent PostgreSQL transactions. A transaction context or a reader-only advisory lock alone does not establish these semantics.

SCIM user and group changes do not depend on the unfinished tenant epoch protocol. This avoids coupling provisioning and suspension to an incomplete, tenant-wide lock. Internal response routes remain unavailable: their existing private command code must not be enabled until a complete, transaction-bound authority decision and documented concurrent-revocation semantics are implemented and verified. The absence of a SCIM fence is not a claim that those private commands are safe to expose.

The private v2.10 response component supports ordinary file and photo fields through an unregistered internal workspace document handler. Its private service rechecks the named recipient, request, subject eligibility and performer route under the memory locks or PostgreSQL transaction that inserts the artifact, scan job, audit event and outbox event. PostgreSQL tests cover successful provenance, recipient revocation after object upload, and rollback on outbox failure; the corresponding uploaded object is removed on those failures. An uncertain transaction commit retains the uploaded object rather than deleting potentially committed evidence, and the UI blocks a blind upload retry. The authority-writer race described above remains open. Object-store deletion failure is currently best-effort and has no durable cleanup job; an uncertain commit also needs a durable reconciliation mechanism. Before enabling internal capture, close those gaps, test cross-scope upload and required-document submission end to end, and verify document conflicts. Unsupported source-bound and other document field types continue to fail closed.
