# ClearSight 2.9 UI replacement and system simplification

**Status:** Proposed design for review, 20 November 2026. No implementation or production acceptance is implied.

Detailed friction analysis, target data ownership, loss migration and execution gates: [Simplification and data-architecture design](2026-11-20-v29-simplification-and-data-architecture.md). That companion develops and qualifies this program plan.

## Decision and outcome

Replace the current customer-facing application experience with the layouts, navigation, interaction patterns and journeys in `clearsight-v2.9`, completing missing designs in the same visual language. The reference is the authority for the desired experience; existing contracts may change to serve it. Retain the institutional controls, data and functional capabilities required for safe operation. A prototype interaction is a product requirement to implement and verify, not evidence that its local JavaScript is a production service.

This instruction supersedes the October reference as the layout authority for future replacement work. The October source and its evidence remain historical records. Update `AGENTS.md`, `DESIGN.md`, the docs map, reference-integrity checks and the cutover register together in the first implementation tranche; do not silently edit the archived source. Existing copy, security, scope, accessibility and acceptance rules continue to apply. Where reference copy conflicts with the global customer-copy rule, rewrite the copy without changing the intended task.

## Evidence and limitations of this assessment

- The inspected working tree is based on `910598ff1` and includes extensive pre-existing uncommitted changes, including the untracked 2.9 package. They are part of the baseline; no reset or overwrite is authorized by this plan. Capture a content-addressed baseline and establish ownership before editing overlapping files. A commit identifier alone will not describe that baseline.
- `clearsight-v2.9/verify_reference.py` reported 199 files verified. Its route manifest lists 67 entry points. The package reports 139 model/workflow checks and 76 route/action checks with a substituted DOM; it explicitly does not claim current browser layout, storage, download or print verification. Its historical 2.7 screenshots are not 2.9 visual proof.
- `web/src/App.tsx` coordinates hash routing, cross-workspace selection, scope changes and evidence loading. `web/src/appRouting.ts` defines the existing URLs and legacy aliases. `web/src/main.tsx` separately gates internal sessions and external capture. Removing the shell without preserving these boundaries would break real journeys.
- `web/src/appStyles.ts` imports 17 global style entry points, including historical fixes and both enterprise and approved shells. The root of `web/src` alone contains 58 CSS files totaling 444,711 bytes; additional feature CSS exists below it. This shows a consolidation opportunity, not proof any particular selector is unused. Large owners include `VendorsWorkspace.tsx`, `VendorDueDiligence.tsx`, `App.tsx` and `staticDemo.ts`.
- The backend is a Go modular monolith with API and worker processes and PostgreSQL ownership documented in `docs/architecture/application-architecture.md` and `docs/architecture/durable-schema-ownership.md`. Existing route files establish risk, loss, RCSA and reporting functionality. Their existence does not prove equivalence to every 2.9 transition. Map exact service, repository, transaction and permission behavior before claiming reuse or a gap.
- Prior October work is recorded as partial layout integration with 0/19 whole screens accepted. It includes valuable behavior and evidence, but is not a 2.9 acceptance baseline. No browser or database tests were run for this design assessment.

## Target architecture

### Experience and routing

Keep React, TypeScript and Vite. Build one 2.9-derived shell and one route registry, with domain-owned route definitions, typed parameters and explicit permissions. Keep existing deep links and notification targets working through tested aliases or redirects. A direct link must resolve to the same authorized record, preserve relevant entity and return context, and work through reload, Back and Forward. The shell owns verified session presentation, entity selection and navigation; a domain owns its selected record and query state. External capture remains a separately bounded entry point, even when styled consistently.

Derive a small shared foundation from the reference: tokens, typography, shell, responsive navigation, fields, buttons, tabs, tables, status, overlays and focus behavior. Adapt existing accessible contracts rather than shipping a second component library. Screen composition belongs to the domain, with layout-specific rules where needed. No live screen imports prototype seed data, local authorization, synthetic actor switching or prototype state. Remove obsolete styling only as its last consumer is replaced.

The reference has 67 route entry points; some are views or states of the same underlying domain and do not require 67 independent applications. Preserve each distinct destination and its primary task. Existing product workflows not represented in the package require an inventory and a designed destination, rather than silent deletion.

### State and contracts

Each domain owns its query adapters, state transitions and presentation components. The server remains authoritative for material state. UI state may hold selections, filters and unsent drafts only when their persistence and sensitivity are explicit. Server reads return authorized, scoped records with versions, relevant permissions, freshness and honest partial/unknown states. Commands use verified actor and scope, optimistic version checks, current authority evaluation, atomic business state, audit/outbox and required jobs. Avoid adding a frontend-only parallel store for an existing business object.

Extend the current Go domain and PostgreSQL schema when the desired workflow needs new durable concepts; reuse existing evidence, forms, Work, governance and reporting owners where their semantics match. Add a distinct model only where ownership or lifecycle genuinely differs. Preserve historical records and source versions, and provide backward-compatible API/route transitions until consumers are migrated. Changes to money, authority or recorded decisions require explicit data and rollback designs before migration.

### Data, access and reporting

Never convert sample records into customer facts. Existing tenant, legal-entity, group, protected-record and invitation boundaries apply to every redesigned surface and backend endpoint. Do not infer a compliance conclusion from a task, upload, source observation or prototype state. Counts identify their population, scope, freshness and denominator; missing information remains unknown.

Loss reporting requires separate original currencies and occurrence, recognition, reporting-period and cash dates. Prototype requirements for drafts, independently accepted revisions, received and independently verified recoveries, reversals, closure and frozen report snapshots need a transaction-level comparison against `internal/oploss` and reporting before implementation. Existing create, update, recovery and intervention routes are confirmed; equivalence to those richer workflows is not yet established. Preserve legacy values and provenance, without inventing recognition dates, authority decisions or recovery receipts.

## Debloating strategy

Debloat by removing duplicate ownership and obsolete paths after replacement is proven, not by deleting domain behavior or evidence wholesale.

1. **Measure baseline:** record customer and evidence entry import graphs, route/asset ownership, production and lazy chunk sizes, CSS bytes/selectors, startup/network timings, and test duration. Record the dirty-tree snapshot and tool versions. Separate generated artifacts, fixtures, historical evidence and production dependencies.
2. **Consolidate shell and state:** extract navigation, scope and domain entry boundaries from `App.tsx`; remove duplicate route parsing and selection state only once deep links and history tests demonstrate equivalent behavior. Preserve separately scoped external capture.
3. **Consolidate design:** inventory global CSS imports and shared control variants. Migrate each domain to the new tokens/components, then remove selector families and style files only after dependency search, build-graph checks and rendered regression confirm no remaining consumers. Replace dated fix layers with owned rules; do not use a new global override to hide conflicts.
4. **Split by behavior, not file size:** separate large workspace coordinators into domain routes, data adapters, focused views and commands when their boundaries are clear. Preserve existing meaningful tests, especially authority and negative-path coverage; combine only tests proven redundant.
5. **Isolate non-production code:** inspect the actual import graph of `staticDemo.ts`, fixtures, evidence entry and build scripts. Retain customer/evidence isolation and only delete or relocate demo machinery after proving whether it is used and replacing any supported demo journeys. Do not remove historical proof merely to reduce source size.
6. **Retire safely:** require an owner, reference/route search, runtime/build reachability, replacement, data/URL impact, tests and rollback for every deletion. Do not delete schema tables, migrations, audit events or object versions as UI cleanup. Backend consolidation needs an independent retention and migration decision.

Set numeric improvement targets after measuring the actual baseline; track initial JS/CSS, route-level transfer, time to useful content and test duration as well as source complexity. A reduction must not come from removing required behavior, accessibility, authorization or recovery tests.

## Implementation sequence and release gates

Each stage ships as small reviewable vertical slices, with its own concrete design/implementation plan and retained evidence. Backend work may precede a screen when needed. A slice is not complete merely because it resembles the reference.

1. **Baseline and authority:** preserve the dirty tree; pin the 2.9 manifest and per-entry source hashes; capture old and reference renders at 1440, 1280, 1024, 768 and 390 in both applicable themes; inventory current routes, API actions and data owners. Update the authority documents and replace obsolete October-only checks with equivalent 2.9 integrity and coverage checks. Resolve conflicting reference designs and all unmatched current routes in the matrix.
2. **Shared platform:** implement shell, navigation, theme, responsive replacements, shared primitives and route aliases; verify session, entity scope, invitation entry, permissions and keyboard behavior. Keep old feature routes working through the transition.
3. **First complete vertical slice:** use the loss register because 2.9 starts there and provides the most explicit source and review contract. First document current `oploss` and financial/reporting parity, migration needs and historical data treatment. Deliver intake → submit → independent review/return → correction → verified recovery/reversal → closure and reconciled reporting as separately reviewable increments, with disabled/honest unavailable states until each action is real.
4. **Connected work:** migrate Work, Inbox, approvals, evidence and documents early enough that loss and subsequent domains have exact source handoffs, notification destinations and review/verification paths. Use one canonical work/decision owner.
5. **Domain replacement:** deliver Programs/Frameworks, Forms/assessments, Vendors, Risk/Controls/RCSA/indicators, Privacy, Reports, and Settings/integrations in dependency order established by the capability matrix. Each tranche includes all reference entry points for its selected journey, relevant existing capabilities, and removal of superseded implementation after verification.
6. **Cross-domain completion:** prove role-separated source-to-decision-to-outcome journeys, current and historical reporting, access revocation, exact link recovery and degraded operation. Reconcile all 67 source entries and all current routes. Remove temporary compatibility code only after consumer and retained-link evidence permits it.
7. **Release:** run migration rehearsal on representative sanitized data, reconciliation, capacity and recovery tests; approve rollback and feature routing; deploy by domain with monitoring. Release acceptance requires named reviewers and separate visual, accessibility, authorization, transaction, data and operational evidence. Maintain a route-by-route register until every entry and retained capability is accepted.

## Per-slice acceptance

- **Experience:** same-screen source/runtime pairs and anatomy, useful first viewport, navigation and responsive replacement at all five widths; light/dark where affected; no horizontal overflow; touch targets, focus, reduced motion and screen-reader labels verified. Document any designed extension and why it follows the reference.
- **Behavior:** each enabled control does the stated action; search, filters, paging, direct links, browser history, saved drafts, loading, empty, partial, stale, denied, conflict, offline/degraded and recovery states work. Guides and errors do not block primary actions. Run copy-quality and affected workflow tests.
- **Authority and data:** test actual verified actors, tenant/entity isolation, conflict, delegation, revocation, stale versions, concurrency, source access, atomic commit/audit/outbox and point-in-time reconstruction. Test unauthorized API reads directly, not just hidden UI controls. Record the outcome of the material command separately from derived calculations.
- **Domain:** demonstrate source-to-record and source-to-report reconciliation, currency/date boundaries, independently reviewed outcomes and migration of pre-existing data where relevant. Use representative but explicitly isolated sample fixtures; do not manufacture bank facts.
- **Operations:** test PostgreSQL and workers, job retry/idempotency, storage, query bounds, performance under representative cardinality, logs without protected data, deployment compatibility and rollback. Keep a named reviewer, exact working-tree/revision identity, source hashes and evidence location.

## Decisions and unresolved investigations

- The user has selected the 2.9 foundation as the desired UI direction and authorized backend changes; this plan proposes retaining the current modular monolith and progressive domain cutover. An alternative is a new parallel app, but it duplicates authentication, workflow integration and migration effort. Directly embedding the prototype would carry synthetic state and unverified security into production and is unsuitable.
- Confirm by route and service inspection whether 2.9 introduces domain requirements that differ from existing policy (particularly loss financial acceptance, control testing, branch KRI, privacy cases, board packs and vendor lifecycle). Resolve each semantic difference in the domain brief before changing data or decisions; the prototype alone is not a source of bank authority.
- Establish the owner and destination of every pre-existing uncommitted change before editing its files. Preserve it in the baseline and integrate or retire it deliberately; do not reset the workspace.
- This is a program-level design and sequencing plan, not a claim that the full 67-route implementation has already been specified at code-step level. Each domain requires an executable, evidence-backed plan once its route/contract inventory is complete.
