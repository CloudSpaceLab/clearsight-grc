# Bank operating demo

The user requested realistic seed data across Forms, Vendors, Programs and Work, based on the supplied banking requirements and sample registers. The refresh must also expose practical simplification opportunities. This follows the vendor-compliance overview release in PR #218.

## Design

Use a small connected operating population, with five Program families: third-party risk, IT risk and security, privacy, operational resilience, and regulatory compliance. Reuse the existing privacy Program and canonical domain workflows. Each sample record must support an identifiable task, decision, evidence requirement or reconstructable completed outcome. A library of unrelated acceptance exercises is not the default business demo.

Six connected journeys provide the initial operating population:

1. Vendor onboarding and periodic review: applicability, current reused evidence, declared missing certification/test evidence, expired PCI evidence, independent review, a privacy decision and governed activation conditions.
2. IT review plan and access remediation: a scoped review, a finding with separate execution actions, one access blocker, owner implementation and an independent outcome check.
3. Payment-service continuity: a supplier dependency, a stated sample recovery target, a test that misses it, remediation and a separate retest.
4. Branch/control self-assessment: a short grouped return, a failed physical or payment control, risk-team challenge and repair evidence awaiting verification.
5. Privacy screening: a scoped change/project reference, conditional questions and a documented privacy decision; missing safeguards remain open before the relevant authorization.
6. Regulatory preparation and operational follow-up: source verification and filing evidence remain separate; a synthetic incident/recovery example retains occurrence, recognition, reported recovery and verification as distinct facts.

Show varied states across the population rather than creating every possible state for every journey. Use five plausible fictional supplier services and a concise reusable form set. Existing real/user-created suppliers remain separate. Names, contacts, amounts, dates, findings and evidence content in the new package are fictional and visibly labelled. The existing customer organization and user identities are not renamed.

## Source use

The seven supplied XLSX files cover the third-party register, IT workplan, IT exceptions, asset risk, NDPA checklist, compliance inventory and Archer workflow requirements. The IT governance DOCX supplies common change references and architecture/evidence linkage. The operational archive supplies branch returns, KRIs, BIA, RCSA and loss/recovery patterns.

Public repository documentation records source filenames and structural anchors needed to explain a sample choice. Original files, private names, incidents, extracts and legal-case narratives remain outside the repository. A curated source catalogue may retain file digests and sheet/paragraph anchors. The sample policy is not an assertion of current law.

Source defects must not become seed facts: formula errors and placeholder rows are excluded; conflicting thresholds or recovery targets require a decision; repeated loss rows are not separate events; blank evidence, recovery dates and approval fields are unknown; unverified circulars and deadlines do not become binding runtime policy. Requested reminder periods, score scales and review targets are configurable sample choices, with their source and limitation recorded.

## Runtime and authority

Both the memory demo and PostgreSQL release use the same scenario definitions. Domain adapters may differ; business objects and intended outcomes must agree. Programs, forms, distributions, responses, vendor relationships, linked work, actions, decisions and verification are created through existing canonical services. Never insert derived Today rows, rewrite an assessment to look complete, fabricate external delivery, or claim an unscanned file was scanned.

The source's owner-completion/risk-acceptance distinction uses implemented actions and independent outcome checks. A parent finding uses the supported direct-action closure gate. Conditional privacy forms and linked decision records represent screening; they do not imply an unimplemented project-management module. Any DPO activation dependency must use existing versioned activation-policy and authority configuration, including its simulation and maker-checker lifecycle. No hard-coded DPO approval branch is introduced.

Verify the modern form-submission event handoff before relying on it for seeded vendor assessment states. A confirmed gap receives a regression and an idempotent adapter correction; sample creation must not conceal it by changing stored status directly.

## Managed installation and preservation

Use a versioned package/scenario key, exact tenant/entity, native source/external references or trigger keys, managed predecessor content and recorded versions. Record an initial sample timeline and preserve it on rerun. Installation reports creates, safe revisions, existing matches, customization skips and conflicts. Every write rechecks current version and required authority.

Preserve user-created, customized, paused, retired and unknown records. Never identify ownership from display names alone. Keep immutable response and audit history. Retire obsolete technical fixtures only when exact managed provenance/content and a supported governed lifecycle permit it; otherwise report the preserved object. Do not merge the two existing Northstar identities by name.

Move future scoring/exactly-once acceptance populations behind an explicit acceptance option or isolated test setup. Retain useful completed oversight history and its minimum-population semantics; ordinary Work already defaults to open items. New reusable forms belong to the appropriate Program where supported. Existing form/Program bindings are not silently rewritten to improve appearance.

## Simplification and limits

Prioritize existing records and evidence before asking again. Set service, review period and owner context once; use conditional follow-ups. The primary view shows object, specific gap/task, current state, owner, deadline/freshness and the next action. Source detail, full responses, policy mechanics and history remain accessible in detail.

Keep a source-to-journey and simplification ledger with observed friction, proposed correction, implemented outcome and deferred capability. Do not manufacture ITSM/ERP/EA connectivity, financial ledgers, nested task dependencies, legal-source validation or predictive metrics to fill a demo screen. Reuse supported records and show unavailable/unknown states honestly.

Alternatives considered: importing every spreadsheet row would preserve more raw content but reproduce duplication and incomplete source data; renaming existing fixtures would reduce visible test language without connecting the workflows. The connected scenario package addresses the user's operating use cases and makes incomplete capabilities testable.

## Acceptance

- Shared memory/PostgreSQL scenario coverage, exact scope, stable identifiers, repeat-install equality and interrupted recovery.
- Customization preservation, managed collision rejection, independent approval/review and current authority checks.
- Submitted configured failures visible on the vendor overview; reuse and expiry correct; collection/review/activation remain separate.
- Linked Program/Work/vendor context, open-action closure blockers, implementation awaiting independent verification and at least one supported completed sample outcome.
- No external messages, fabricated delivery/scan/integration receipts, transplanted private source records or invented current compliance claims.
- Copy regression, affected workflow tests, actual PostgreSQL tests and rendered Forms/Vendors/Programs/Work at desktop and narrow sizes, in both themes.
- Main merge/deployment verification and hosted inspection of the actual seeded population. Local fixtures are not a substitute for hosted seed verification or representative bank-user acceptance.
