# Protected API question drafts

The format-test endpoint checks the stored question type against the selected result type before reserving a test or contacting an endpoint. Yes/no questions accept BOOLEAN; decimal and percentage questions accept NUMBER. It shares the protected-draft compatibility rule, so a successful format test cannot be attributed to an incompatible question. This check does not activate a binding or authorize capture.

An API question draft is a form-authoring configuration, not a live integration or observation. Its endpoint remains in a separate entity-scoped table and is not copied into the form fields supplied to respondents. A form-level draft specifies an API only. A manual choice belongs to an individual framework adoption and never rewrites the form. Draft changes pin the form and question revision and require the verified form owner's enforced authority, configuration permission and optimistic version.

The protected form draft and manual adoption draft inserts also check the verified session expiry against the PostgreSQL clock at insertion. If a session expires while the authority check is pending, neither the draft nor its outbox event is written. This check does not establish transaction-time parity for every authority route or enable runtime execution.

The PostgreSQL draft store and HTTP handlers are not registered for runtime use. Approval, protected credential references, private-network policy, adoption-specific override, answer collection and execution are not implemented. A manual draft does not implement a framework-adoption override. No draft may be described as enabled or as proving a control result.

Migration 000143 creates immutable draft revisions and a scoped lookup index; its rollback refuses to delete recorded drafts. The store writes the revision and outbox event in the same transaction, and outbox events omit endpoints. PostgreSQL isolation tests cover concurrent writes, scoped access, unenforced authority, immutable history and rollback on an outbox failure. The draft write uses an actor/entity-scoped idempotency key and rejects a retry with changed input. Current form revision insertions share a row lock with draft writes; PostgreSQL tests cover stale revisions, concurrent form revisions and both transition orderings. The draft endpoint needs real authorization integration tests, coordination with authority and delegation changes, broader race checks and security review before route registration. Retention and capacity policy remain open.

The optional wizard on a saved form question gives developers a JSON response example and tests samples or public unauthenticated HTTPS endpoints. No credentials or query parameters are accepted. Tests do not save or activate an API connection; manual answers continue.

The developer instructions can be copied with the question and expected response example. Clipboard failure leaves the visible instructions available for manual copying. While a test is pending, the sample and endpoint cannot be edited, so the displayed result cannot be mistaken for a test of a changed value. These changes do not alter endpoint policy or activate an API question.

The endpoint field rejects query and fragment delimiters even when their values are empty, matching the server's URL restrictions before a format test is sent.

## Adoption-specific manual proposal

Migration 000144 records an explicit, immutable Program/adoption/form-question association with manual collection proposed. The record pins the Program and adoption versions, framework edition identity, and exact active form revision and question. It is created only for a pending adoption, under verified Program-owner authority and a separate fail-closed form-access check. The versioned draft and outbox event share one transaction, and a scoped idempotency key permits safe retry. PostgreSQL tests cover denied form access, wrong scope, stale versions, concurrent writes, outbox rollback and both orderings of adoption approval and association.

The record is not an approved override and is not consumed by response capture. The protected read and HTTP handlers are implemented but remain unregistered. The PostgreSQL service uses the existing scoped Form Library reader with active/current and Program checks; integration tests verify cross-entity denial. Authority-revocation coordination, independent review, activation, and execution semantics remain unimplemented, so these proposals are not exposed to users.

## Independent approval and runtime pin

An independent Program authorizer may review and approve an exact latest manual proposal under the pending adoption. The checker must differ from both adoption and question makers. Approval is immutable, idempotent and recorded with an outbox event; it does not activate the choice by itself. The form-level API draft cannot select MANUAL: manual selection is specific to adoption.

The distribution pin and runtime resolver are internal foundations only. A proposed pin can be written in a distribution-creation transaction only for an active adoption and an approved exact question, after a trusted distribution-authority callback. Resolution checks an authorized exact request, scoped Program, active adoption, independently approved latest proposal and matching form/question in the same transaction. PostgreSQL tests cover authorization denial, rollback, stale/pending/retired adoption, mismatched Program/form/field and locking against adoption retirement.

These functions are not wired to distribution creation, capture or scoring. The reusable form contract has no governed API-question binding; the distribution API has no adoption or approved-choice selector; and request-level source bindings can be supplied independently. Before enabling runtime manual answers, the system must pin the approved API binding and adoption choice atomically at distribution creation, prove the selected question-to-binding relationship, project the verified choice to the response workspace, and enforce it in server-side answer validation, source resolution, scoring, revision history and review. Capture authorization and all related state changes must share the transaction. No client flag may suppress a source binding. Approval and draft handlers remain unregistered until authority-revocation coordination and full lifecycle coverage are verified.

## Form-question binding proposal

Migration 000148 records an immutable proposal linking an exact draft form revision and question to an exact active Source Binding revision. It checks the current form-owner authority and requires a separately supplied, fail-closed binding access and response-contract validator. It never activates the association. The validator is not wired in production; source connection governance, independent association approval and effective dating remain open. PostgreSQL tests cover idempotency, wrong field, inactive binding, denied access and transactional rollback.

Distribution pinning and runtime resolution also require an independent trusted check that the approved association matches the exact question and binding. The production implementation of that proof does not yet exist. The helper remains unregistered and is not called by response capture.

## Binding proposal review

Migration 000149 records independent review of an exact latest form-question binding proposal. The current form-reviewer route must authorize the checker, who must differ from the question and association makers. Approval, audit revision and outbox are transactional and idempotent; approval does not activate an association or execute a source. PostgreSQL tests cover maker denial, reviewer route, stale version, unavailable binding proof and rollback.

A non-executing catalog verifier checks the exact active Source Binding, View and REST connection lineage, scoped active source, PAGE operation, freshness, singleton result schema and equality with the draft endpoint. For binding proposal and review, exact catalog and entity-source reads now use the caller's server-owned PostgreSQL transaction and lock the Binding, View, Connection, Source and legal entity. This protects those rows against concurrent changes while the command runs. The verifier is still a preflight, not activation or runtime proof: authority/delegation changes are not coordinated and catalog lifecycle activation is missing. The source catalog lacks lifecycle approval and activation services. A form transition creates a new form revision, so the approved draft association also requires explicit, version-pinned carry-forward with impact review in that transition transaction. No route or capture path consumes these records.

## Required form-transition contract (not implemented)

Submitting a form draft for approval creates a new `PENDING_APPROVAL` form revision. The submission transaction must freeze an explicitly selected, bounded manifest of approved binding proposal IDs and versions, the exact draft and pending form revisions, each question definition hash, protected endpoint fingerprint, source/connection/view/binding identities and versions, and approval identities. It must write the snapshot, immutable event and outbox atomically; missing or unapproved proposals fail closed. It must not infer association from a source name or automatically select every proposal.

A proposed scoped `GET /api/v1/forms/templates/{id}/revisions/{pending_version}/binding-impact` must require the current verified form-reviewer route and return the exact pending form version, a bounded question/connection impact list, the independent approval identities, and a deterministic digest of the frozen manifest. It must disclose any unavailable, stale, rejected or changed source revision. It is not an activation and must use no-store responses. The exact endpoint is a proposed contract, not a registered route.

A proposed transition command must extend the existing form transition body with `binding_impact_digest`. When a pending revision has binding proposals, the checker must explicitly provide the previewed digest; absent or mismatched digest fails closed. In one transaction the command must lock and re-read the pending form and frozen manifest, re-evaluate the checker route and maker-checker conflict, verify the exact binding approvals and their source/connection/view/binding revisions, compare the digest, create explicit associations for the new ACTIVE form revision, and write the material event and outbox. No association is active before that commit. A successful old-style transition with an ignored digest is not acceptable.

The current `TransitionLibraryForm` accepts only `expected_version` and `to`, creates a new revision, and does not freeze or present binding impact. The current form-transition authority guard resolves before the form repository transaction, so route and delegation revocations can race the check. The catalog row locks added to binding proposal/review are not yet used by the form transition. There is no transaction-bound cross-service snapshot or change-lock protocol. Implement and prove that protocol before registering preview, proposal, approval or activation routes. Do not use the current catalog preflight as an activation guarantee.

Required evidence includes maker-versus-checker and delegated reviewer cases; denied cross-entity sources and bindings; exact revision and digest conflicts; concurrent source/connection/view/binding retirement and authority revocation in both orderings; overlapping form edits, approvals and retries; rollback of form, association, audit and outbox on any error; secret and endpoint redaction; and end-to-end activation and later manual-override capture under a real verified identity. No production or demo cutover follows from the isolated foundations alone.

An unused internal question-definition fingerprint hashes the typed field and expected result type under a versioned domain. It rejects incompatible question types and bounds its input; changes to a typed field alter the digest. The helper assumes a validated, normalized persisted form field loaded inside the future transition transaction. It does not cover unknown serialized properties, section conditions or the form-level scoring profile; the exact full form revision must also be pinned and validated. The helper is not connected to the transition hook and does not establish source validity, approval, activation or observation execution. PostgreSQL JSON validation and the normalized typed model are prerequisites; hashing arbitrary untrusted in-memory strings is not an accepted use.

The internal impact digest now also binds the exact draft and pending revision IDs, both maker identities, reviewer identity, and the review authority rule and policy version. It rejects a reviewer who is either maker and rejects missing identities or authority metadata. The digest remains an unwired validation primitive; it does not fetch or freeze approvals, prevent concurrent authority changes, or activate a binding.

The developer contract states the live test response limits: a successful JSON response, a required typed result, optional bounded message, no duplicate or extra fields, and a 65,536-byte maximum. The same instructions are rendered and copied. This guidance does not enable saved or live assessment integrations.
